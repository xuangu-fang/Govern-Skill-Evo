# Govern: Continual Skill Evolution through Diagnostic Preconditioning

Agent 从一次失败中总结出的修复规则，可能解决眼前的问题，却让后续任务更容易出错。

**Govern 希望用诊断与历史经验对 Skill 更新进行“预条件化”：先判断一段经验应该怎样被学习，再把它写成可复用的行为规则，让局部改善能够逐步累积。**

这篇工作的主问题是：**Agent 如何从带有噪声、局部错误和不完整反馈的运行经验中持续学习，同时避免错误归纳、过度约束和跨任务回归？**

## 1. 这篇论文为什么值得做

Agent 的运行经验并不像一道有标准解析的习题。一个任务失败，可能是缺少知识，可能是知道正确做法却执行错了，也可能是工具出了问题。反过来，一条整体失败的轨迹里，也可能有值得保留的正确步骤。

因此，任务结果并不会直接告诉我们应该怎样修改 Skill。

如果把“失败”直接翻译成一条新规则，容易出现两种问题：把偶发错误当成规律，或者把局部有效的修复推广得太宽。例如，一次操作因为条件不满足而失败，learner 可能学到“以后都不要做这个操作”；规则确实避免了同样的失败，却堵住了其他任务的成功路径。

经验持续到来时，这个问题会进一步放大。每一轮都能提出一个看似合理的修复，当前 batch 上也可能变好，但这些修复未必能共同组成一个越来越可靠的 Skill。

你们的日志已经出现了这个现象：风控实验最后一批的修改在当前 batch 上被接受，但独立测试准确率从此前版本的 61.25% 降到了 54.38%。这里更值得研究的，是**为什么局部改善没有保留下来**。第五批结果是事后补测，适合帮助理解问题，不应被当作正式选出的最佳版本。

第一篇可以由此提出：

> **持续 Skill 学习的难点，是把局部、不完整、来源混杂的经验，转化成能够长期复用、又允许继续修订的行为规则。**

这让“受控自进化”有了具体含义：控制经验如何进入长期 Skill。合规是其中一种场景，工具使用、程序执行、风险判断都可能遇到同样的问题。因此，第一篇不必把成功×合规的二维分布作为主要卖点。

## 2. Setting：新经验不断到来，已有认识不断被检验

设定可以讲得很简单：

- Agent 的模型参数保持冻结，通过更新外部 Skill 改善行为。
- 新任务按 minibatch 到来，Agent 用当前 Skill 执行。
- learner 根据轨迹和可见反馈提出修订。
- 新一批经验可能支持过去的判断，也可能暴露反例或补齐此前缺少的信息。
- 学习过程既要改善新任务，也要保留仍然有效的旧行为。

这里最重要的性质，是**证据逐渐到来，而规则需要持续使用**。

第一批经验往往只支持一个局部认识。后续任务才让我们知道：它适用于哪些条件、什么时候不成立，以及此前的修复是否产生了副作用。学习器需要在“先作出有用更新”和“不要过早认定规律”之间找到平衡。

需要区分两个层次：

**连续经验学习。** 任务实例逐批首次出现，即使总体分布不变，也要考察改善能否累积。

**任务构成变化。** 后来的任务与早期任务不一样，学习器需要适应新的任务比例，同时保留旧程序。例如早期以 A 类工作流为主，中期增加 B 类工作流，后期再出现 A 类的新实例。

这两个层次已经足够支撑第一篇。真正改变 API、政策或环境规律，是更进一步的方向，不必现在一起承担。

另外，随机切成 minibatch 本身不是新贡献。SkillAdam 已有逐批更新的设置。我们需要强调的，是**这样的经验流中存在怎样的学习歧义，以及方法如何处理它**。[2]

## 3. 先理解预条件化：它改变的是“怎样沿这个方向更新”

### 从最简单的梯度下降说起

最简单的梯度下降，根据当前梯度决定更新方向：

$$
\theta_{t+1}=\theta_t-\eta g_t.
$$

$g_t$ 告诉我们局部往哪里走，$\eta$ 决定走多远。

但梯度的不同方向未必适合用同样的方式处理。有的方向变化很陡，走大步容易来回震荡；有的方向很平，走同样的小步又太慢。单纯调整一个全局步长，很难同时照顾这些方向。

预条件化在更新前加入一个变换：

$$
\theta_{t+1}=\theta_t-\eta P_t g_t.
$$

$P_t$ 是预条件器。它可以重新缩放不同方向，也可以结合方向之间的关系来调整更新。直观上，相当于先把“不好走的地形”换成一种更适合前进的坐标，再决定实际更新。

**预条件化不是与优化器并列的另一种东西，而是优化器可以采用的一种机制。** Adam 的自适应缩放就可以从这个角度理解；利用曲率信息的预条件器，则能进一步处理方向之间的结构。

因此，我们要借用的是这个思想：

> **原始反馈提供了更新线索，但这个线索需要经过处理，才能成为合适的更新。**

### 为什么能映射到 Govern

在 Skill 学习里，运行反馈还不是一个可靠的“梯度”。失败原因、适用条件和副作用，都可能不清楚。

如果所有经验都以同样方式进入 Skill，就像给性质不同的更新方向使用同一套处理方式：

- 偶发工具错误，被写成永久限制；
- 少量局部证据，被写成通用原则；
- 已失败过的修复，被重新提出；
- 当前案例的收益，掩盖了其他任务的损失。

诊断与历史经验的作用，是改变这些线索最终怎样写入 Skill。

| 原始线索 | 经过预条件化后的更新 |
|---|---|
| “这个操作失败了，以后不要做” | 识别失败条件，只在相应条件下改变操作 |
| “这一批失败较多，需要重写流程” | 区分程序缺陷与执行错误，保留有效步骤 |
| “这个修复看起来合理” | 参考过去相似尝试的收益和副作用，调整修复方向 |
| “旧规则遇到反例了” | 重新解释适用范围，判断应缩窄、替换还是撤销 |

以上是解释机制的示意，不代表日志中已经完整实现了每一种转换。

这个 framing 的关键是：**诊断与记忆要能改变更新内容，而不只是给建议打分或增加上下文。**

若方法只删除低分建议，它更接近过滤器。若它会改变问题解释、规则条件和编辑组合，预条件化就有了明确的行为含义。

### “高阶”应该怎样讲

普通更新从“当前哪里做错了”出发。你们还希望学习“过去怎样修改曾经有效、产生了什么副作用、现在是否仍适用”，再用这些认识指导下一次修改。

这提供了一个高阶优化的视角：**优化器也在积累关于更新效果的知识，并据此改变自己的更新方式。**

但这个功能类比不自动等于计算了 Hessian 或实现了数值二阶优化。第一篇最稳妥的说法是 **diagnostic preconditioning**；如果后续显式研究编辑之间的行为响应或交互，再考虑更强的高阶表述。

Muon 可以提供灵感，但它有明确的更新矩阵正交化操作。目前不需要为套这个名字，强行把语义聚类写成正交化。[4]

## 4. 我们的方法，可以统一讲成一个“有状态的更新器”

从日志呈现的工作看，现有方法最适合抽象为三个环节。具体模块怎样划分，仍应以实际代码为准。

### 当前诊断：先看清这次发生了什么

运行经验中既有问题，也有有效行为、反例和无法判断的现象。诊断的作用，是先把它们分开。

它不应看到一个失败标签，就立即决定增加什么限制。更有用的输出是：哪里出现了问题、什么已经做对了、哪一种旧判断受到挑战，以及当前信息还不能回答什么。

日志中先形成当前观察、再引入历史解释的安排，也有一个值得研究的意义：给新证据留下独立发声的空间，避免过去的认识把现在的现象解释掉。

### 历史认识：记住尝试的效果，也允许改变解释

记忆的核心对象可以是一个反复出现的问题，以及为解决它做过的尝试：

> 这个问题以前怎样修过？哪些行为改善了？哪些地方退步了？我们现在认为它在什么条件下有效？

这样，记忆就不仅是一份过去规则的集合。它保存的是**对修复效果的当前认识**。

例如，过去认为“遇到某种不确定性就停止”是合理修复；新任务可能表明，先查询信息再执行，既能避免错误，也能保留成功路径。需要改变的，是我们对这个问题的解释，而不只是再追加一条指令。

一次接受不应让某条规则永远正确，一次拒绝也不应让所有修复方向永远无效。这一点与 EviSkill 有明显重叠；我们的机会在于把历史认识怎样参与当前更新讲得更清楚、做得更有效。[3]

### 预条件化更新：决定学什么、推广到哪里

当前诊断与历史认识结合后，才形成实际的 Skill 修订。

它主要回答三个问题：

1. **这段经验支持修改 Skill 吗？**  
   有些问题值得修，有些还需要信息，有些可能来自环境或执行。

2. **应该写成多大范围的规则？**  
   证据只支持局部条件，就先写局部规则；不要急于上升为通用原则。

3. **这个修改会怎样影响其他有效行为？**  
   一项修复可能改变多个任务的路径，也可能与其他规则冲突。

随后通过执行检查修订效果，并把新的观察用于更新历史认识。整个闭环可以用一句话概括：

> **经验形成诊断，诊断与历史共同塑造更新，更新的实际效果再修订历史。**

用轻量形式化表达：

$$
\text{当前更新线索}
\;\xrightarrow{\text{当前诊断 + 可修订历史}}\;
\text{经过预条件化的编辑}
\;\xrightarrow{\text{执行反馈}}\;
\text{新的 Skill 与历史认识}.
$$

这个表达不要求现有代码必须拆成三个 Agent，也不要求新增很多模块。论文应该抓住共同机制，工程实现可以更简单。

## 5. 与已有工作的区别，应当放在哪里

三篇邻近工作已经覆盖了不少基础机制：

| 工作 | 已经建立的重点 | 我们不能只靠什么来区分 |
|---|---|---|
| **SkillOpt** | 有界文本更新、验证选择、拒绝编辑缓存、长期更新与优化器记忆 | 编辑预算、失败历史、优化器类比 |
| **SkillAdam** | 问题与修复尝试记忆、自适应编辑预算、逐批验证 | minibatch、Issue–Attempt 结构、稳定更新 |
| **EviSkill** | 证据绑定、局部回放、跨轮修订和局部编辑保留 | 证据引用、被拒更新复用、可修订历史 |

这些概括依据原文。[1–3]

所以，方法的区别最好落在：

> **不完整、冲突或来源不清的经验进入时，历史认识怎样参与构造当前更新，而不是仅仅保存和复用过去的信息。**

具体可以争取三个层次。

**第一，更新来源的诊断。**  
不是所有失败都对应 Skill 缺陷。我们能否更好地区分哪些经验值得学习，哪些需要进一步观察？

**第二，规则范围的调整。**  
修复方向大致正确，却推广过宽，是一种很重要的失败。我们能否利用成功行为和反例，把修复变成合适的条件规则？

**第三，历史解释的变化。**  
新证据到来时，能否更新对过去尝试的认识，并让这种认识真正改变下一次编辑？

这些目前是最值得发展的区别候选，不能仅靠重新命名就成为贡献。EviSkill 本身也关心证据支持的持续修订；比较时，应让它保留局部回放等关键能力。

一个有说服力的结果，是在相同经验和相近资源下，直接反思、直接加入历史与 Govern 得到了不同的修订，而 Govern 的修订在新任务上更有效。这样才能说明“预条件化”具体做了什么。

## 6. 方法接下来怎样打磨：优先让故事中的机制变得可见

这里不预设学生应采用哪一种具体实现。下面是与论文主线最相关的研究方向。

### 从“存得更多”转向“历史改变了什么”

Memory 是否有价值，应当看它有没有改变当前更新。

可以关注：过去的反例是否让新规则缩窄了范围？旧尝试的副作用是否让 learner 换了一条修复路径？此前没有充分证据的方向是否在新经验中重新变得可行？

如果历史只是被放进上下文，而编辑没有受到可解释的影响，故事会比较弱。

### 从“是否修改”推进到“修改的抽象层级”

同一种经验可以产生不同层级的知识：

- 某个上下文中的局部处理；
- 一类任务的执行程序；
- 跨任务的通用原则。

方法可以进一步研究：证据范围怎样决定规则层级，以及新证据怎样推动规则收窄或扩大。这比单纯限制编辑条数，更贴近“有边界的学习”。

### 从“修复失败”推进到“保留有效行为”

一条失败轨迹里的正确部分，不应被整体否定。成功经验也不应只用于计算分数，它们可以帮助回答：本次修改不能破坏什么，某条限制是否过宽。

这个方向很适合连接你们早期的过度约束观察，也能在不依赖合规指标的公开任务上检验。

### 从“看起来相关”推进到“理解编辑的副作用”

当前轨迹对比可以帮助理解变化，但多项编辑同时生效时，某个结果未必能归到其中一项。

后续可以选择少量重要或相互干扰的编辑，更仔细地检查它们的作用。如果能形成对“哪些修改通常帮助哪些问题、又会损害什么”的稳定认识，预条件器的含义会更强。

这也可能成为高阶优化路线的入口。不过，应先判断这个信息是否有用，再决定需不需要矩阵、交互模型或更复杂的数学形式。

## 7. Benchmark：采用公开任务，改变学习与评价方式

第一篇建议采用：

> **公开 benchmark 的任务和正确性标准，加上一套能够看见持续收益与回归的学习协议。**

这样既能和已有 Skill 方法比较，也能突出我们关心的问题。无需为了方法论文，从头建立一个大型环境。

### 推荐组合

| Benchmark | 建议用途 | 选择原因 |
|---|---|---|
| **ScienceWorld** | 优先探索连续更新与机制实验 | 有任务家族和大量变体，适合重复学习程序并检验条件泛化 |
| **AppWorld** | 标准表现与工具工作流验证 | 多应用 API 操作、可重置环境、状态评价，接近程序性 Skill 的实际用途 |
| **ALFWorld** | 可选补充 | 与现有工作有交集，可检验另一种任务环境 |
| **已有 τ² 改造** | 小规模机制案例 | 已有基础，适合观察条件归纳和过度限制，但不宜独自承担主结果 |

任务特性与使用入口见参考资料。[5–8]

建议先用 ScienceWorld 检查协议和机制，再用 AppWorld 检验能否迁移到更接近真实工具使用的工作流。主次也可以根据实际 pilot 调整。

选择 benchmark 的关键，不是任务够不够难，而是有没有**可复用、又受条件影响的程序**。如果任务失败主要来自基础能力不足，Skill 更新很难发挥作用；如果固定 Skill 已经接近满分，也没有足够学习空间。

私有信用卡实验可以继续作为工业方向。第一篇不必为了公开发表，寻找一个公开表格数据集来替代它；单次分类与长轨迹 Agent 程序学习之间，还有一层需要说明的距离。

## 8. 实验怎样服务故事

实验最好逐步回答三个问题：正常条件下是否有用，持续更新时是否能积累收益，反馈不完整时机制是否发挥作用。

### 第一层：保留标准任务比较

先在公开任务上比较最终 Skill 的原生指标，证明方法有竞争力。保留固定 Skill、简单反思，以及 SkillOpt、SkillAdam、EviSkill 等强基线。

不需要靠人工扰动才能看到所有收益。正常条件下的表现，是论文的重要基础。

### 第二层：让经验逐批到来，观察整条学习过程

可以使用两种流：

**随机混合流。** 每批有不同类型的新任务，总体构成基本稳定。看改善能否随着经验积累而保留下来。

**任务构成变化流。** 早期以 A 类为主，后来增加 B 类，再重新出现 A 类的新实例。看方法能否适应新任务，同时保留有效的旧程序。

最有价值的图，不只是最后一个分数，而是学习曲线，以及“更新轮次×任务家族”的表现热力图。它们能让读者看到局部收益、跨任务回归和后续恢复。

新 batch 应先由当前 Skill 执行，再用于更新。这样可以看见已经学到的东西，如何帮助下一批首次任务，而不只是当前 batch 的重复回放变好了多少。

### 第三层：减少反馈信息，检验诊断是否重要

第一版可以先做温和改造：保留任务整体结果，减少细粒度失败定位或部分诊断信息。

它更贴近你们的核心问题：learner 知道任务没有完成，却不能直接知道哪里值得修、什么应当保留。

临时工具故障或错误标签可以后续加入。不要一开始就同时修改任务、环境和评价，让结果难以解释。

有一个重要边界：如果更新器可以无限查看干净验证结果，不完整反馈的很多困难会被验证阶段解决。实验需要说明 learner 能看到什么，并让基线获得相同资源。具体实现可以由学生设计，正文不必展开成复杂审计流程。

### 一个特别适合我们的机制实验：证据跨批次补齐

选取少量共享程序、条件不同的问题组，让支持案例先到来，后续再出现反例或新的适用条件。

例如：

- 早期经验支持某个局部修复；
- 中间几批没有覆盖这个问题；
- 后来的任务暴露了修复过宽；
- 最后用新实例检查修订后的规则。

这个实验能直接观察：方法是否过早认定规律，是否把没有覆盖当成失效，是否能在反例到来后调整范围。

它应作为解释机制的子集，主结果仍在完整任务上报告。不要只挑选对 Govern 有利的案例。

## 9. 最值得验证的几件事

**历史复核是否比直接加入历史更有用？**

比较当前批诊断、直接加入历史经验、经过新证据复核后的历史认识。保持相近的上下文和验证预算。这是整篇故事最关键的对照之一。

**预条件化是否真的改变了编辑？**

用相同经验，比较原始修订建议与经过诊断和历史处理后的建议。看变化是否体现在原因解释、适用条件或规则组合上，并检验新任务效果。

**稳定性是否来自拒绝所有更新？**

回归更少，但新任务没有进步，并不能证明学习更好。需要同时看收益、保留与学习速度。

**优势是否只是更多计算？**

方法可以使用更多诊断，但要说明额外成本买到了什么。若简单方法在相同预算下也能达到同样效果，应考虑简化架构。

指标可以围绕三个方面展开：

| 方面 | 主要看什么 |
|---|---|
| 学习效果 | 下一批新任务表现、最终冻结 Skill 表现、整条学习曲线 |
| 更新可靠性 | 旧任务新实例的回归、过宽规则误触发、反例后的修订 |
| 效率 | rollout、回放和 token 成本，达到同等表现需要多少经验 |

并非每个机制都需要一张独立表。优先选择能够改变研究判断的实验。

## 10. 最后写成怎样的一篇论文

整篇叙事可以沿着下面的顺序展开：

**局部修复为什么会伤害后续任务？**  
用一个真实案例说明，当前经验提供的更新方向存在歧义。

**为什么需要持续检验规则的来源与范围？**  
新经验不断到来，支持和反例可能分散在不同批次。

**为什么诊断与记忆可以被理解为预条件器？**  
它们共同改变经验进入 Skill 的方式，包括是否更新、如何更新、推广到哪里。

**方法究竟带来什么？**  
在公开任务上展示持续收益、回归和成本，再用机制实验解释历史认识怎样改变更新。

贡献可以收束为三项：

1. 不完整运行反馈下的连续 Skill 学习问题与公开评估协议。
2. 由当前诊断和可修订历史共同塑造更新的预条件化方法。
3. 对累计收益、过度归纳和跨任务回归的系统验证。

标题暂用 **Govern: Continual Skill Evolution through Diagnostic Preconditioning**。如果最终结果更突出反馈可靠性，可以改为 **Govern: Reliable Skill Evolution from Imperfect Feedback**。

接下来最值得优先做的，是在一个公开环境上证明：**同一段经验，经过不同的历史参与方式，会形成不同的更新；其中某种更新能更好地迁移到后续任务。**

这个结果成立，故事就有了方法基础。之后再扩大 benchmark、模型和任务变化的范围。具体模块、归因算法和更新实现，应由学生结合真实代码选择，不必为了迎合 framing 增加不必要的结构。

### 邻近方法

**[1] SkillOpt: Executive Strategy for Self-Evolving Agent Skills**

- [论文](https://arxiv.org/html/2605.23904v1)
- 阅读重点：有界文本编辑、验证选择、拒绝缓存，以及 slow/meta update。
- 与我们的关系：优化器类比和长期历史已经存在，区别需要落在不可靠经验怎样塑造更新。

**[2] SkillAdam: Stable and Efficient Skill Evolution for Agents**

- [论文](https://arxiv.org/html/2609.08944v1)
- [代码](https://github.com/ruc-datalab/SkillAdam)
- 阅读重点：问题与尝试记忆、改进波动对应的编辑预算、逐批更新协议。
- 与我们的关系：minibatch 和 Issue–Attempt 都不是空白，需要更清晰的更新诊断机制。

**[3] EviSkill: Grounding Skill Evolution in Replayable Evidence**

- [论文](https://arxiv.org/html/2610.05030v1)
- [代码](https://github.com/Zhouyaner/eviskill)
- 阅读重点：证据与编辑绑定、局部回放、Working/Validated Skill、跨轮修订。
- 与我们的关系：这是目前最接近的工作，重点比较历史证据怎样改变当前更新，而不是泛泛比较“有无记忆”。

### 优化器类比

**[4] Muon 的作者设计说明**

- [Muon: An optimizer for hidden layers in neural networks](https://kellerjordan.github.io/posts/muon/)
- 适合了解数值更新矩阵的正交化操作。它可以启发对编辑干扰的思考，但不直接对应当前语义诊断流程。
- 更深入的预条件化背景，可以从课程中的 ill-conditioning、Newton method、adaptive gradient methods 和 natural gradient 入手。首先弄清“更新方向如何被变换”，不必一开始追求复杂证明。
