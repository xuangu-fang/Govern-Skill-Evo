# Govern-Risk：从复核经验持续更新风控判断手册
## 工业应用论文 Proposal v0.1

**风控系统不断积累误报、漏报和复核案例，却难以把这些经验持续转化成可靠的判断规则；Govern-Risk 希望让系统从运行反馈中维护一份能够纠错、有适用边界的风控判断手册。**

**建议英文标题：Govern-Risk: Continually Updating Fraud Review Playbooks from Operational Feedback**

版本日期：2026 年 10 月 11 日。本文用于学生讨论和研究推进，基于现有 Govern 实验与本次讨论；系统扩展和业务收益均是待验证的研究设想。

---

## 1. 这篇论文要回答什么

核心问题可以压缩成一句话：

> **在相同误报约束或复核预算下，持续吸收运行经验的风控系统，能否比固定判断规则更有效地识别欺诈？**

我们已有的切入点是：围绕一笔目标交易，结合历史行为和卡片信息，判断风险，给出支持证据、反向证据与不确定性；然后利用后续反馈，改进下一轮判断所遵循的 Skill。

工业论文里，可以把 Skill 解释为 **review playbook，即风控判断手册**。它描述哪些信息值得检查、哪些现象需要警惕、哪些正常解释不能忽略，以及经验适用于什么条件。

这让项目有了一个明确的应用对象：**持续维护风控复核知识。** 技术机制是否有效，最终由未来案例上的判断质量、复核资源利用和运行成本来检验。

本文暂将私有数据称为“滴滴内部风控数据”。最终业务名称应按实际任务确定：支付欺诈、信用卡欺诈、账号滥用等不应混用。如果私有任务与信用卡欺诈并不完全一致，可以采用更宽的“业务风险复核”定位。

## 2. 与第一篇 Agent 方法论文怎样分工

两篇论文可以共享 Govern 的核心机制，但分别回答一个独立问题。

| 维度 | 第一篇：Agent 方法论文 | 第二篇：工业应用论文 |
|---|---|---|
| 核心问题 | 如何从有噪声、局部错误和不完整的经验中，持续学习可复用的条件化技能？ | 如何将不断回流的风控案例转化为可维护的判断经验，并改善真实业务表现？ |
| 方法定位 | 诊断与记忆如何调节 Skill 更新；诊断预条件化的机制解释 | Govern 如何进入案例复核与经验维护工作流 |
| 主要贡献 | 学习机制、更新边界、跨任务稳定性 | 业务问题、系统设计、反馈利用与应用价值 |
| 主要实验 | 多任务学习、持续迭代、机制分析、与 Skill 学习方法比较 | 时间外效果、误报与漏报、复核预算、成本与真实案例 |
| 最重要的结果 | 机制使技能学习更可靠 | 相同业务条件下，系统得到可持续的增益 |
| 论文开头 | 不完美经验使技能更新不稳定 | 复核案例持续积累，但判断知识难以可靠更新 |

第二篇应把篇幅留给业务问题和应用证据。Preconditioner 的解释可以保留，但只需帮助读者理解为什么更新更加稳健。

对 SkillOpt、SkillAdam、EviSkill 的机制比较，应主要由第一篇承担。第二篇仍需交代相关工作和方法来源；实验可以选择适配当前案例任务的代表性 Skill 更新方案，重点比较它们带来的业务效果，而不是重新展开一套完整的方法创新叙事。

**这条应用线值得单独成篇的前提，是形成新增的业务问题、工作流和实验结论。** 第一篇的机制实验与第二篇的业务实验应各自支撑自己的主张。

## 3. Motivation：风控为何需要这种持续学习

### 3.1 经验很有价值，但局部经验容易被推广过头

可以采用下面这段作为论文引言的白话版本：

> 风控系统在运行中不断收到误报、漏报和复核案例。这些案例包含有价值的业务经验，但经验往往依赖具体条件。直接根据最近的错误修改判断规则，可能修复一种风险，却把大量正常行为也纳入怀疑；为了降低误报放宽规则，又可能遗漏真正的欺诈。我们研究如何从这些反馈中持续维护有适用条件的判断手册，使新经验进入后续判断，同时保留已有的正确判断能力。

一个假设性的例子是“短时间跨地区交易”。它可能是风险信号，也可能来自正常旅行或特定结算方式。系统需要学习的，不只是“跨地区交易可疑”，还包括什么历史背景增强风险、什么反证削弱风险，以及什么情况下信息仍不足。

**Conditional skill 在业务中的含义，就是把经验学成有适用条件的判断规则。**

这个例子只用于解释问题。正式论文应使用经过核实的真实案例，并通过预测结果证明规则的价值；解释写得合理，不等于判断正确。

### 3.2 最有研究价值的矛盾

风控需要迅速吸收新案例，又不能因为几个案例就改变大量正常业务的判断。由此可以提出三个问题：

1. 新反馈究竟暴露了判断方法的问题，还是一次信息不足、执行错误或偶然失误？
2. 一条新经验应当推广到哪些案例，又应当在哪些案例上停止生效？
3. 更新带来的局部修复，能否在后续业务中积累为稳定收益？

现有 Govern 的诊断、历史尝试记忆和候选验证，恰好可以服务这三个问题。工业论文应当用具体业务结果展示这种对应关系。

## 4. 现有基础：我们已经能做什么，还需要证明什么

根据当前实验 log 的 Day 42–44，私有案例实验已经具备以下基础：

- 输入围绕目标交易展开，包含目标交易信息、经过 180 天窗口筛选的历史事件和卡片信息。
- 输出包含欺诈判断、风险证据、反向证据和不确定项。
- 已完成 640 条演化案例、8 个 minibatch，以及 160 条未参与演化的测试案例。
- 已运行不带 Memory 和带 Memory 的 Skill 演化版本。

这里的任务是结构化案例判断。现有记录没有证明已接入线上业务处置，也没有证明它是多轮工具交互系统。

当前结果提供了一个值得研究的现象：

| 实验运行 | 版本 | 测试准确率 | 误报 FP | 漏报 FN |
|---|---|---:|---:|---:|
| 不带 Memory | 初始 Skill | 44.38% | 51 | 38 |
| 不带 Memory | 最终 Skill | 58.13% | 24 | 43 |
| 带 Memory | 初始 Skill | 44.38% | 53 | 36 |
| 带 Memory | 最终 Skill | 54.38% | 29 | 44 |

两次运行均在同一份 160 条测试案例上评估；初始运行的预测有差异。测试集包含 80 条欺诈与 80 条正常案例。

可以得到的判断是：**Skill 更新能够改变风控判断，但当前改善主要来自减少误报，伴随漏报增加。** 现有最终结果还不能证明 Memory 优于不带 Memory。

带 Memory 的中间版本曾在补测中表现更好，但它是在最终评估后追加检查的，适合用来分析收益为何丢失，不应将其直接当成正式选版后的最终结果。

Log 也包含分层加权的参考结果。这有助于观察业务分布对指标的影响；它代表被纳入权重计算的案件总体，不能自动外推到全量交易，更不能与不同案件集合上的网页实验直接比较。

这些结果目前最适合作为研究动机：

> **在当前批次上减少错误，并不保证未来业务中的误报与漏报得到更好的平衡。**

后续工业论文应重点解决并验证这一问题。

## 5. 系统形态：先完成案例复核，再争取业务闭环

### 5.1 最容易承接现有工作的版本

先做一个能够持续学习的案例复核系统：

> 当前案例与历史信息 → 按判断手册分析 → 输出风险判断 → 后续反馈回流 → 更新判断手册。

这已经能形成清晰的应用实验，不必等到拥有完整线上系统才开始。

关键是把“手册更新”与“当前案例判断”区分开：当前案例只能使用当时可获得的信息；它的真实标签在反馈可用后，才用于下一轮学习。

### 5.2 更有工业价值的目标形态

如果能够获得现有检测模型或业务规则的输出，可以进一步形成：

> 现有模型筛选风险案例 → Govern 分析需要进一步判断的案例 → 复核或后续结果回流 → 更新判断手册。

这个结构可以检验：固定前面的检测底座，在相同复核量或运行预算下，持续学习的复核层增加了多少价值。

| 系统部分 | 主要作用 | 希望验证的价值 |
|---|---|---|
| 现有检测底座 | 大规模筛选与风险排序 | 提供业务基础与候选案例 |
| Govern 复核层 | 结合历史、风险证据与反证判断案例 | 改善候选案例的识别与排除 |
| 手册更新机制 | 从后续结果修订判断经验 | 使经验在未来案例上持续发挥作用 |

业务底座、调用范围和反馈来源是否已经可用，需要由学生与业务团队确认。若只评估了离线案例判断，就按离线案例判断报告；若之后开展影子运行，可以报告运行表现，但不将其等同于实际拦截收益。

### 5.3 方法在第二篇里怎样讲

用一句话描述核心方法即可：

> **先判断反馈意味着什么，再利用历史经验确定修改方向与适用范围，最后根据实际表现决定是否采用新手册。**

Preconditioning 原本指利用额外结构，调整优化更新的方向和尺度。这里可以做功能上的类比：原始错误反馈只是一个“需要改进”的信号；诊断与记忆进一步决定是否值得修改、改哪部分、适用于什么条件。

这一解释应与实际实现一致。没有明确的曲率结构或理论结果时，不必声称系统计算了 Hessian 或实现了数值意义上的二阶优化。

## 6. 数据策略：三个数据各自承担一个验证任务

### 6.1 优先组合：内部数据＋IBM TabFormer＋IEEE-CIS

| 数据 | 已知特点 | 在论文中的角色 | 主要边界 |
|---|---|---|---|
| 滴滴内部风控数据 | 已有交易、历史事件、卡片信息及可靠标签案例 | 支撑真实业务问题与案例分析；争取时间回放或影子运行 | 当前实验规模和抽样结构，还需与实际业务总体对应 |
| IBM TabFormer 信用卡交易数据 [1] | 官方提供约 2400 万条合成交易记录，并支持按用户组织交易序列 | 公开复现“当前交易＋过去行为”及持续更新 | 合成数据；收益可能依赖生成机制 |
| IEEE-CIS Fraud Detection [2][3] | Vesta 提供的真实支付欺诈数据，包含交易时间及部分匿名化业务字段 | 提供公开真实数据上的效果验证与强基线比较 | 部分字段含义隐藏；完整历史身份关联有限 |

**内部数据回答业务价值，IBM 数据回答历史行为实验的可复现性，IEEE-CIS 回答另一份真实数据上的效果。**

上述角色划分是本 proposal 的研究建议，并非这些数据已经被验证适配 Govern。

### 6.2 不必强行统一所有输入

IBM 数据更适合围绕用户的历史交易构造案例。先确认其可用字段和标签，再确定历史窗口；无需强制沿用内部数据的 180 天窗口。

IEEE-CIS 可以承担较简化的交易案例判断。其公开字段中的一部分含义隐藏，不应自行赋予业务解释。利用卡与地址等字段构造的交易指纹，也不等同于可靠的真实用户 ID。[3]

IEEE-CIS 的公开带标签训练数据可用于重新建立时间划分；不要假设官方测试标签可用于本地评估。Amazon FDB 已提供基于带标签数据的时间划分参考，但其特征选择和构造标识属于额外处理，使用时需要明确说明。[3]

统一的是研究问题和评估原则：**反馈怎样进入后续判断，收益能否在未来案例中保持。** 每个数据可按实际能力提供不同深度的上下文。

公开数据的改造主要应发生在任务组织上：按时间构造案例、形成连续批次、限制可见历史、建立反馈回流。主实验保留原始欺诈标签。人工注入标签噪声或模拟反馈延迟，可以作为补充实验单独报告。

### 6.3 BAF 是有价值的替代项

| 备选数据 | 为什么值得考虑 | 适合的故事 | 局限 |
|---|---|---|---|
| Feedzai Bank Account Fraud，BAF [4] | 基于真实银行开户欺诈数据生成，包含时间动态、类别不平衡和偏差设置 | 持续维护跨业务场景的风险判断知识 | 合成数据；开户欺诈不是信用卡交易 |
| ULB Credit Card Fraud [3][5] | 常用的公开信用卡欺诈分类数据 | 补充检测性能比较 | 主要为 PCA 特征，只有两天交易，不适合作为语义手册与长期更新的主实验 |

如果最终定位是“业务风险复核”，BAF 可作为跨场景验证；如果定位是“支付或信用卡欺诈”，优先采用 IBM＋IEEE-CIS。

BAF 的不同变体用于检验不同条件，不应按多个独立业务数据源来计算。“三个数据集”也不是论文成立的硬条件，数据与核心问题的适配程度更加重要。

## 7. 实验应当证明什么

### 7.1 先判断，再学习，再测试未来

推荐的基本协议是：

> **使用当前手册判断当前案例；反馈可用后更新；在之后的案例中评估。**

更新时可以回放已获得反馈的案例，帮助检查候选修改；主结论依赖未用于这次修改的后续案例。

有真实时间就使用真实时间。随机 minibatch 可以验证迭代机制，但不能独自证明系统适应了业务分布变化。自然时间变化与人为构造的漂移，也应分别报告。

在此基础上，工业论文最值得回答四个问题：

| 研究问题 | 建议证据 |
|---|---|
| 判断质量是否改善？ | 同误报率下的欺诈召回，或同召回水平下的误报 |
| 复核资源是否用得更好？ | 固定候选池与可复核数量，比较欺诈发现数、复核命中率和成本 |
| 持续更新是否能积累收益？ | 未来时间窗口的表现、旧类型案例的退化、新类型案例的改善 |
| 手册更新是否有独立价值？ | 与静态手册、案例检索、直接经验累积及简单更新方案比较 |

### 7.2 主指标围绕业务取舍

Accuracy、F1 和 PR-AUC 可以报告，但最重要的指标应与业务目标对应。

- **误报受到约束的场景：** 比较正常交易误报率相同时，能识别多少欺诈。
- **复核资源受到约束的场景：** 比较相同复核数量下，能发现多少欺诈。
- **服务效率受到约束的场景：** 同时报告调用量、延迟、token 和成本。
- **有金额与业务损失信息的场景：** 可以评估金额相关收益，但交易金额不自动等于最终损失。

如果系统目前只输出二值判断，就先报告实际混淆矩阵和业务结果。只有获得可靠的排序分数或明确的策略调节方式后，才使用 Recall@FPR、预算曲线等评价。

现有均衡测试集适合诊断误报与漏报。主要工业结论应尽量对应自然业务分布，或明确说明加权估计覆盖的是哪一类案件总体。

### 7.3 基线要覆盖三类解释

| 基线类别 | 候选对照 | 要排除的替代解释 |
|---|---|---|
| 业务检测 | 可获得的现有模型、业务规则；LightGBM / CatBoost 等强表格模型 | 是否只是利用了已有检测能力或不同输入 |
| 案例判断 | 无 Skill 的 LLM、静态人工手册、历史案例检索 | 是否只需要更好的提示或更多上下文 |
| 持续更新 | 直接累计经验、简单反思更新、不带 Memory 的 Govern、可适配的 Skill 方法 | 诊断与历史记忆是否提供额外价值 |

比较应尽量匹配输入信息、反馈数量、候选池和预算。对于需要排序的复核场景，前端筛选规则也应保持一致或单独分析。

如果业务模型拿不到历史行为，而 Govern 能读历史行为，应提供历史信息增强的检测基线，或者明确分解输入信息与方法各自带来的收益。

### 7.4 反馈要有明确含义

人审意见、案调结论、退款或拒付结果，以及尚未收到反馈，是不同的信息来源。它们的可靠性和可用时间应按数据实际情况交代。

尤其需要留意：被复核的案例通常已经经过筛选；没有被复核、没有收到投诉，不一定意味着正常。仅在复核队列上评估，就将结论限定在复核队列；要推断全量业务效果，需要相应的代表性样本或可靠估计依据。

标签噪声、反馈延迟和缺失反馈可以成为研究内容，但不必一次做全。优先选择内部业务中真正存在、能够被确认的一项困难。

## 8. 方法还可以怎样打磨，才能服务这个故事

这里保留高层方向，不预设学生的具体模块或实现。

**第一，更新要对齐业务取舍。** 当前批次总错误减少，可能只是误报与漏报发生交换。可以探索让业务约束进入候选评价，例如改善误报时保护召回，或在固定复核量下评估候选。具体目标应由实际业务需求决定。

**第二，让正常案例成为学习边界的证据。** 有价值的手册既能总结风险信号，也能学习什么情况下同样的信号不能支撑欺诈结论。现有风险证据与反向证据的输出形式，适合承接这一方向。

**第三，关注历史经验被新反馈修订的过程。** 最有说服力的展示是：系统曾学到一条经验，后来遇到反例，调整了适用条件，并在未来案例上改善了判断。它比“手册越来越长”更能说明持续学习的价值。

**第四，控制知识维护的成本。** 工业系统需要衡量积累更多历史是否真的值得。可以探索精简相关经验、减少重复检查和合理安排更新频率；结果以业务效果与成本的关系来呈现。

这些是待验证的研究方向。应根据真正产生效果的机制确定最终贡献，不必在 proposal 阶段给每个方向都命名一个新模块。

## 9. 论文可以形成的三个贡献与叙事顺序

### 9.1 三个候选贡献

1. **持续维护风控判断手册的工作流。** 将当前案例、历史行为与后续反馈连接起来，使经验进入下一轮判断。
2. **有条件的业务经验学习。** 展示系统如何学习风险信号与反证、修订经验边界，以及保留已有的正确判断能力。
3. **在真实业务条件下的持续收益。** 在未来时间窗口和固定业务约束下，验证识别、误报或复核效率的改善，并报告成本。

只有获得相应证据的贡献进入正式论文。若最终没有显示持续收益，就需要调整方法或缩小主张。

### 9.2 推荐的 paper 故事线

| 部分 | 读者应当理解的内容 |
|---|---|
| Introduction | 复核经验值得利用，但直接修改规则会造成业务取舍失衡 |
| Problem Setting | 系统何时看到案例、何时获得反馈、更新什么、服务什么业务目标 |
| System | 复核与手册维护如何连接；诊断、历史经验和验证分别做什么 |
| Evaluation | 更新能否在未来案例和相同业务约束下优于对照 |
| Case Study | 一条经验如何产生、被反证、被修订，并影响后续判断 |
| Discussion | 哪类反馈与场景适用；尚未验证的业务环节与部署范围 |

最值得放进论文的案例，应能把一次手册更新与一组后续预测变化联系起来。配对回放可以显示关联；未单独隔离某条规则时，不将其效果描述为已证明的独立因果贡献。

## 10. 下一步怎样判断这条线是否值得扩大

优先做一组内部数据的时间回放，而非立即铺开所有数据集。

在真实历史顺序上，比较静态手册、案例检索和 Govern 的持续更新；尽量固定误报约束或复核预算。先确认三个问题：收益是否出现在未来案例上，误报改善是否以不可接受的漏报增加为代价，维护经验的额外成本是否值得。

如果内部数据暂时只有当前小规模可靠标签案例，可以先做概念验证，同时争取更长时间跨度或额外可靠标签。800 条案例可以启动研究，但当前 160 条测试上的有限欺诈数量，难以支撑非常低误报率下的稳定收益估计。

再用 IBM 数据完成公开历史交易实验，用 IEEE-CIS 补充公开真实欺诈验证。根据内部效果与实际业务接口，决定是否争取影子运行。

**这篇工业论文最值得争取的结论是：复核经验可以持续转化为有边界的判断知识，并在未来业务中带来可测量的收益。**
