## v21 小规模验证：案例与判定依据

本步准备验证材料，不运行真实模型。目的：检查历史双维认识能否改变 Fusion 的修改依据，并经 Evidence Review 核实后落实到 Skill 修改或有依据的 NO_EDIT。不是要求三个案例都产生新规则，也不据此证明自进化收益或方法创新已经成立。

保留 `current_understanding` 最多 **2,000 字符、超长拒绝**的现有条件，不截断，不修改 Prompt、运行逻辑、Gate 或调度。

### 1. 已冻结的材料

使用 v20 历史运行的学习侧投影：第 3 轮 Parent/Candidate 配对，接第 4 轮实际 Parent、Current Findings、公开 Policy/工具和原始执行事件。第 3 轮 Candidate 与第 4 轮 Parent 文本完全相同，SHA256 为 `68da4c19efa71e147df2a23ff8e9933b50a158b552e0724974e077bfabcfaa45`。

没有使用第 4 轮 Candidate、后续回放结果、Monitor、私有评判原因或最终数据库来制定学习结论。当前 Findings 是待核实的既有分析，不等于原始事实。历史同时存在三条修改，配对结果不能自动归因到某一条 edit。

| 案例 | 第 3 轮历史材料 | 第 4 轮当前问题组 | 历史事件 / 当前事件 | 主要检查点 |
|---|---|---|---:|---|
| 01 行李计费 | T009，另含 T010 对照 | single-traveler-baggage-booking | 63 / 64 | 成功不能抵消合规退化；不能把局部经验推广到所有舱位 |
| 02 多人拆单 | T013，另含 T016 对照 | group-booking-passenger-boundary | 66 / 67 | 不因任务失败否定已有合规做法，也不编造失败原因 |
| 03 保障条件不明 | T035，另含完整当前组的分支对照 | delivered-exchange-protection-condition | 43 / 76 | 保留未知及适用条件，区分已有文字覆盖与实际效果 |

合计 5 组历史配对、172 个历史事件、207 个当前事件、19 条当前 Findings。每组历史配对保留双侧完整轨迹，每个当前问题组保留完整原文与所有 Findings，不只取支持预设方向的片段。不同来源的事件数相加不代表独立样本数。

原有 Memory 未补写人工“正确认识”。后续需要真实生成并校验 v21 更新，不能把本文件的判定依据伪装成模型已学到的经验。旧 issue 的问题范围继续固定，不为适配案例标题而改写既有 problem；历史中混杂的内容也不能自动当作本案例的有效归因。

### 2. 案例 01：成功仍然成立，但合规退化

材料：[完整证据](../../../artifacts/methods/v21/v21_validation_cases/01_baggage/evidence.json)、[事件导航](../../../artifacts/methods/v21/v21_validation_cases/01_baggage/evidence.md)。以下事件号均指导航中对应历史配对的双侧事件。

**实际观察：** T009 从 `(成功, 合规) = (true, true)` 变为 `(true, false)`。两侧均完成 business 舱、regular 会员、两件行李的预订；Parent 的 E0013 将 `nonfree_baggages` 设为 0，支付 55；Candidate 的 E0013 将其设为 2，支付 155。两侧均有用户确认和返回的预订结果。另一案例 T010 是 basic economy、regular 会员、两件行李，收费两件的两侧结果均为成功合规。

**证据边界：** 可以定位行李分类与金额的差异，形成有条件的修订依据；不能因任务成功就认定收费方式可继承，也不能由这两例推出所有 regular 会员都免费或都应收费。公开 Policy 将具体行李分类留给内部合同，没有给出完整数值规则；不能声称“公开 Policy 明文规定 business 两件免费”。本轮没有直接修改行李条款，不能断言某条 edit 已被证明导致该退化。

**Fusion 判定：** 修改理由应保留已有正确的信息收集、确认与预订执行能力，同时回应该场景的合规限制，并保留 basic economy 反例。只复述“注意合规”，实际仍沿用不分场景的计费规则，不算有效利用历史。当前组另有姓名重复问题，应独立处理，不应混入行李 issue 的历史认识。

**Review / Editor 判定：** 核对双侧原始参数、费用、标签、舱位/会员条件、公开 Policy 与当前 Parent；允许证据支持的有界修订。不得扩大为所有行李免费，也不得虚构隐藏合同。若决定 NO_EDIT，应明确现有证据为何不足以授权具体修订及仍未解决的风险；不能用“预订成功”直接关闭问题。

本案例覆盖的是**任务成功保持、合规下降**，不是“任务能力提升、合规下降”。当前选择中没有后一种干净配对，不为补齐分类而合成真实案例。

### 3. 案例 02：合规改善，却不能据此解释任务失败

材料：[完整证据](../../../artifacts/methods/v21/v21_validation_cases/02_group_booking/evidence.json)、[事件导航](../../../artifacts/methods/v21/v21_validation_cases/02_group_booking/evidence.md)。

**实际观察：** T013 从 `(true, false)` 变为 `(false, true)`。Parent 一次为六人预订；Candidate 在用户确认后按 3+3 完成两次预订，获得两个预订号，总金额 270，覆盖六人。T016 则从 `(true, false)` 变为 `(true, true)`：七人单笔改为 5+2，得到成功合规结果。当前 Parent 已包含每笔最多五人、允许时拆单的文字规则（冻结 Parent 第 33 行）。当前组也有拆单得到两个预订号、但任务标签仍失败的观察。

**关键不确定性：** T013 两侧用户提供的生日不同：Parent E0002 的日期均为 2 月 1 日，Candidate E0002 依次为 2 月 1 日至 6 日。Candidate 使用了其本侧用户提供的日期。不能描述为“Agent 自己改错生日”，不能认定生日就是私有评判失败原因；也不能把这组配对当作只有拆单方式不同的控制实验。原文没有支持“漏订后半组”“没有确认”或“人数重复”的断言。

**Fusion 判定：** 应保留拆单做法获得的有条件合规支持，回应任务失败仍未解释的事实。不应直接恢复六人单笔预订，或只因合规标签改善就宣称方案已完全有效。参考 T016 也不能声称拆单在所有条件下保证成功。

**Review / Editor 判定：** 回查人数、确认、两次调用与返回、乘客字段来源以及当前已有条款。不能重复增加相同的“五人上限”，不能为了给任务失败找一个可修改点而添加没有证据的衔接规则。NO_EDIT 可以成立：现有条款覆盖了已支持的方向，剩余失败原因未知。如果提出新修订，必须指出当前可见且尚未覆盖的具体缺口，而不只是重复失败标签。

五人阈值在当前 Skill 中已有文字，公开 Policy 本身只说明存在内部人数边界。必须区分已有经验支持、当前文本与公开政策的不同证据身份。

### 4. 案例 03：条件未知时，区分任务失败与合规判断

材料：[完整证据](../../../artifacts/methods/v21/v21_validation_cases/03_protection/evidence.json)、[事件导航](../../../artifacts/methods/v21/v21_validation_cases/03_protection/evidence.md)。

**实际观察：** T035 两侧均为 `(false, true)`。工具只返回当前保障状态和履约方式，没有说明换货是否保留保障。Parent 在 E0021 由“无法保证保留保障”转向提出退货，但之后 E0022 确有用户明确同意，E0023/E0024 完成退货调用和返回。Candidate 说明未知、询问用户选择；用户仍坚持条件判断后，执行转人工。

**证据边界：** 不能把“未知”当作“换货必然不保留保障”，也不能遗漏 Parent 后来的明确确认而宣称“未经确认退货”。两侧合规标签均为 true，不能擅自改成合规退化。当前组还包含知情选择后成功退货、以及坚持条件后转人工但任务未成功的案例；相同可见状态不推出固定履约方式与保障结果映射。

当前 Parent 第 31 行已经说明：无法确定时说明限制并请求知情选择；用户不愿在未知条件下选择时转人工；用户已经知情选择时不强制转人工。

**Fusion 判定：** 应保留条件未知和用户选择的分支边界，不能为了追求任务成功猜测保障结果，也不能把本次合规转人工总结为“所有保障相关请求都转人工”。任务失败需要保留，不能据合规标签宣称用户目标已完成。

**Review / Editor 判定：** 验证当前条款是否已经覆盖该方向，并回查当前组的成功退货反例。合理 NO_EDIT 不代表证明现有 Skill 的任务效果充分，只说明证据尚不能支持额外规则；若确有新缺口，则只修改该缺口。禁止把历史建议重新包装成重复条款，或将有条件转人工改为一律转人工。

### 5. 统一人工判定依据

下表仅用于离线观察，不新增运行时状态、分类字段、Agent 或 Review。每项记录“符合 / 不符合 / 证据不足”，附输出位置与原始证据引用；不计算容易掩盖严重错误的总分。

| 检查项 | 可接受的表现 | 不接受的表现 |
|---|---|---|
| 两维观察 | 分别陈述任务结果与程序合规，保留冲突 | 用总体 ACCEPT/RETAIN、单一标签或工具成功替代两维判断 |
| 认识边界 | 区分已观察事实、待验证解释和未知，保留反例 | 将相关性写成局部 edit 因果、跨场景拼成已验证联合成功 |
| Fusion 的实际使用 | 修改理由与方向具体回应历史支持、限制和反例 | 仅提及 Memory，提出的方案仍重复已知问题 |
| Review 的核实 | 基于当前 Parent、适用 Policy 和原始双侧证据纠正或收窄提案 | 只复述摘要；把其他 issue 的证据认领为本问题结论 |
| 最终修改或 NO_EDIT | diff 保留支持的能力并回应已证实缺口；或说明不修改的证据理由 | 删除有支持的做法、重复已有文字、无证据增加限制，或无视已明确的问题 |
| 来源与输入 | 关键结论可定位原始事件，必要反例实际进入本次输入 | 用判定文档作证据；漏输入反例却归咎模型“不会归因” |

即使 Review 最后纠正了 Fusion 的错误，也要分别记录两个阶段的表现；不要把最终安全输出算成 Fusion 已通过。Fusion 直接作出有依据的 NO_EDIT 时，不强制补跑 Review/Editor，未执行阶段记为“未执行”，不虚构其通过结果。

“修改决策受历史影响”的可观察依据是：方案的保留部分、适用条件、修订方向或不修改理由明确受到历史限制约束。输出变长、换了措辞、出现“双维”一词，都不构成证据。若单次输出无法判断是否真正利用历史，应记证据不足，而不是断言 Memory 已产生独立因果贡献。

### 6. 下一步如何使用，本步尚不执行

1. 先用既有 v21 Memory 更新接口从可信第 3 轮档案产生真实认识并通过原有校验；保持 2,000 字符硬限制。不得直接复制本文件为 `current_understanding`。记录实际 issue/attempt 归属，案例焦点不强制成为新 issue。
2. 使用冻结的第 4 轮 Parent、完整 batch、Current Findings 和公开证据执行现有消费链路，重点人工检查这三个问题。共享的全部七组输入维持原 batch 契约，不把裁出的单组伪装成完整 batch。按现有选择形成 Review，不为了凑案例强制新增 Review。
3. 保存实际 Fusion/Review/Editor 输入与输出、输入证据清单、模型配置、Prompt 版本和 token 用量，再按上表逐项判定。不把准备材料 JSON 的字节数当成真实模型 token 成本。
4. 如需确认历史认识是否影响选择，可在同一 Parent、Findings、Policy、模型设置下，对一个存在疑问的案例补做旧 Memory 消费对照；原始证据可访问范围保持相同，并记录两侧实际 Review 读取范围。若检索范围也变化，单独报告，不能把差异全部归于归因文字。旧 Memory 与新 Memory 的信息组织本就不同，该诊断对照不是严格分离所有变量的因果实验。

若没有实际进入输入，先修装配；若证据齐全却未在决策中回应，才考虑最小 Prompt 调整；若证据本身不能定位原因，保留未知。三例都合理时，不为了彰显创新继续加机制。真正的任务成功/合规收益仍需后续 Replay 与更完整实验验证。

## v21 真实模型局部对照

日期：2026-10-09。材料与预先判定依据见 [小规模验证案例](VALIDATION_CASES.md#v21-small-validation-cases)。

本轮观察到：更新后的双维认识进入了 Fusion/Review，影响了问题组织、修改理由和历史证据读取；但没有证明它改善了最终修改决策。拆单与保障案例的边界判断合理，行李案例仍暴露出关键配对没有跨轮带入、已加载的有利历史没有被充分使用的问题。

### 1. 对照到底比较什么

通过现有 `build_memory_update_input` / `run_memory_update` 和 `run_memory_consumption` Python 入口运行，没有修改运行模块、Prompt 或校验器。模型沿用 `deepseek-v4-pro`，temperature=0、reasoning_effort=high。完整入口按批次运行 Fusion → 每个 PROPOSE 一次 Review → Compiler/Editor；没有另加 Review Agent。

| 项目 | 对照组 | 处理组 |
|---|---|---|
| 消费流程 | 相同的 v21 流程 | 相同的 v21 流程 |
| Memory | 第 3 轮学习档案中的原历史快照：6 个 issue，无新综合认识 | 从同一档案真实更新：8 个 issue，其中 4 个有综合认识 |
| 当前 Parent、Requests、Findings | 冻结的第 4 轮材料 | 完全相同，逐项复验 |
| 可访问的原始档案 | 原事件、轨迹、Policy/工具、配对 | 这些内容逐项相同，增加认识记录与来源关联 |
| 实际 Review 证据 | 由原 Memory 和 Fusion 选择决定 | 由更新后的认识和 Fusion 选择决定，范围发生变化 |

这是**旧历史快照与 Replay 更新后 Memory 的局部诊断对照**，不是 v20 方法与 v21 方法的公平效果实验，也不是只改变一句归因文字的严格消融。issue 数量、认识的新旧和来源关联均有变化；后续 Review 实际读取范围不同，不能把结果差异单独归因于归因文字。只有各一组消费运行，temperature=0 也不代表输出必然可复现。

保留完整七组 batch、39 条 Findings，重点判定三个预先选定案例。Memory 更新选择四个既有提案：三个焦点问题及同轮取消规则修改，并显式加入五组案例配对；沿用默认退化补入和来源闭包，实际加载 19 组配对。没有删除实际 edits 来假造一个更小的历史轮次，也没有调用新 Replay、读取私有评判原因或重做 Current Diagnosis。

### 2. Memory 更新的三次真实调用

| 调用 | 结果 | 总输出预算 / 实际输出 token |
|---|---|---:|
| update | 拒绝：attempt 的 `source_refs` 包含未加载事件编号 `1202` | 24,000 / 18,304 |
| update-retry1 | 相同输入与请求逐字节重跑；拒绝：`finish_reason=length`，24,000 token 全为 reasoning，未形成完整答案 | 24,000 / 24,000 |

第三次只通过已有 transport 注入接口调整这次调用的总输出预算，实际请求另存 `effective-request.json`；未修改默认配置或运行源码。输入、Prompt 和 schema 不变。成功调用实际输出低于原 24,000 上限，因此不能证明提高预算是成功原因，更不能据此声称默认入口已稳定。

**2,000 字符硬性拒绝条件始终保留。** 成功更新的四段综合认识分别为 719、620、623、689 字符；没有截断、人工修改答案或把失败输出继续交给消费端。前两次失败及全部用量均保留。

成功认识保留了这些区分：拆单后的七人任务成功合规，六人任务合规但失败；保障信息不足时转人工可以合规但仍任务失败；已有 trip-type 指引可在执行中观察到，但不能解释全部行李合规问题。它们仍是可修订解释，不是局部修改因果已经得到证明。

### 3. 三个案例的实际判定

| 案例 | 对照组 | 处理组 | 人工判定 |
|---|---|---|---|
| 行李计费 | 与姓名、trip type 合并送审；Review 4 为 NO_EDIT | 与姓名分开；行李 Review 6 为 NO_EDIT，仍未带入 T009 显式配对 | 问题组织有所改善，但关键历史学习与 Review 证据利用不充分；不能判为机制通过 |
| 多人拆单 | Review 9 为 NO_EDIT | Review 5 为 NO_EDIT，加载 T013/T016 等四组历史配对 | 两组均未由任务失败否定拆单、编造失败原因或重复添加人数上限；决定合理，未观察到最终决策改善 |
| 保障条件不明 | Review 8 为 NO_EDIT | Review 3 为 NO_EDIT，加载 T035 等四组历史配对 | 两组均保留知情选择与有条件转人工；处理组明确区分文字覆盖、观察到执行与因果效果，未观察到最终决策改善 |

两组中的 NO_EDIT 都不能自动当成正确。拆单和保障的理由回应了已有条款与证据边界；行李的关键问题在于理由没有充分处理已有观察，而不是必须强制写出一条行李新规则。

#### 行李案例：两个不同的问题同时存在

第一，真实更新输入加载了第 3 轮 T009 配对：任务成功保持、合规从 true 变 false。通过校验的 Memory 更新没有引用该配对，也没有把这次 business 两件行李退化形成有对应来源的新认识。处理组行李 Review 的 `pairs` 最终只有 T011、T015，没有 T009。因此，**更新输入的退化覆盖并不保证更新后认识或下一轮 Review 的配对覆盖**。

第二，不能进一步说“Review 根本没有读到零收费的正面例子”。复查实际输入发现，旧来源展开仍带入了一条更早的第 1 轮轨迹：同类 business、两件行李，`nonfree_baggages=0`，标签成功合规；当前第 4 轮轨迹则为 `nonfree_baggages=2`，成功但不合规。Review 理由重点讨论“不合规案例与一个合规案例均全部收费”，没有回应这条零收费正面观察。

两条确实已加载的调用为：

- 早期支持：`CURRENT/ed12295dba0354058acdf02017fda65a198b2cbbd49db08fea5fa9a469cb6c94/T022/R036/R1/E0013`。
- 当前问题：`CURRENT/2d95760687f3791920a05adf0378b3c6b300394c63663330a8fac0d39c50d521/T022/R036/R1/E0012`。

原文、参数、版本与标签已单独抽取到 [证据核查](../../../artifacts/methods/v21/v21_local_comparison_001/baggage-loaded-comparison.json)。它们来自不同轮次，不能伪装成 T009 的同轮 Parent/Candidate 配对，也不能据此宣称完整内部合同已知。但 Review 应回应这种有条件的历史支持，解释为何仍不足以授权修订，而非仅以合同不可见概括为没有可用条件证据。

#### 拆单与保障：读取了历史，不等于已证明增益

处理组拆单 Review 保留了早期六人、七人单笔调用虽然工具成功却不合规的反例，同时没有把一次拆单后任务失败解释为人数规则应删除。它没有编造生日错误的原因；本例两侧用户生日表述不同的混杂仍按预先判定依据保留，不能宣称局部因果已被隔离。

处理组保障 Review 明确将身份查询时序问题排除在所选条件保障 issue 之外，且不因转人工后任务失败而要求猜测保障映射或强制执行。这些判断符合预定边界。但当前 Findings 和 Parent 本身已含足够相关信息，对照组也给出合理 NO_EDIT，所以本轮不支持“新增 Memory 改善了这些决定”的结论。

### 4. 提案、最终修改与成本

Fusion 对照组提出 10 个 PROPOSE，处理组提出 11 个，均未在 Fusion 阶段主动 NO_EDIT。处理组多出独立姓名问题，不能简单把数量增加都视为变差；但大量已有文字覆盖或仅原因未知的方向仍送入 Review，没有观察到减少此类复查的收益。

最终消费结果及全部网关用量见下方完成记录；总 token 包含重复输入、缓存读取和 reasoning，不等于独立证据量或实际金额。失败调用也计入，不将代理 token 估计当作网关实测。

两组均完成现有消费入口并生成候选：对照组 10 个 Review 中 2 个 VERIFIED、8 个 NO_EDIT；处理组 11 个 Review 中 2 个 VERIFIED、9 个 NO_EDIT。两组均新增两条规则，针对同样两个当前问题：地址确认文本不准确、替换航班选择条件自相矛盾。二者都不属于本次三个焦点案例，也未关联历史 Memory issue。候选的顺序、措辞和具体表述不同，不能把这些差异解释成已验证的 Memory 收益。

### 5. 对下一步的约束

本轮支持继续采用现有轻量结构，不支持立刻增加 Agent、分类表、重复 Review 或强制逐 edit 归因，也没有依据放宽 2,000 字符限制。

优先处理已经观察到的两个环节：一是修改后退化在形成认识时被遗漏、导致下一轮缺少显式配对；二是 Review 对已加载的有利历史与反例回应不足。应先围绕行李案例做最小补强并复验，区分来源装配和语义使用，不能只加一句“考虑双维”便声称修复。

Fusion 是否应将“当前已覆盖、没有具体新缺口”的方向直接 NO_EDIT，可作为第二优先级检查；现有 Review 的保守否决仍有价值。默认真实调用还出现一次引用失败和一次输出耗尽，应单独检查稳定性；不能把结构失败混为方法语义失败。

在这些局部问题有明确处理结果前，本轮不足以作为“语义验证全部通过、可直接进入完整 v21 调度实验”的依据。所有候选仅为本地生成产物，未 Replay 验证，也未发布为活动 Skill/Memory。

## v21：Review 比较与 Fusion 判断的定向修订

日期：2026-10-10。接续[分阶段真实复验](VALIDATION_RESULTS.md#v21-staged-validation-report)。本轮按用户要求聚焦语义问题，没有增加引用修复器、自动重试或格式治理流程。

**结果：按任务与操作组织的原始调用对照，使行李 Review 本次首次明确引用、讨论此前遗漏的正面观察。Fusion 的提案依据有所改善，但两组对地址问题仍有不同判断。不能把这次局部改善写成归因或修改质量已经全面解决。**

### 1. 定位过程与取舍

旧材料中的正面调用 E139、参数正文 B185、标签所在轨迹 T13 分散在不同目录。目录跳转是可检查的呈现问题，但不是已证实的遗漏根因。本轮保持规范输入、原始事件、Policy、当前 Parent、引用别名和响应 schema 不变，做了以下真实观察：

| Review 尝试 | 结果 | 是否进入最终运行代码 |
|---|---|---|
| 全部原文按轨迹连续呈现，标签紧邻事件 | 仍遗漏 E139 | 否，代码已撤回，试验源码留档 |
| 原表示上要求先说明正反证据、后决定是否编辑 | 仍遗漏 E139，把 trip-type 支持代替了行李支持 | 否 |
| 同类工具调用全部平铺，含原参数和两维标签 | 仍遗漏 E139 | 否 |
| 同类调用再按任务分组，并要求先比较同任务条件、再讨论跨条件迁移 | 明确引用并讨论 E139，仍 NO_EDIT | 是 |

这不是同一请求的自动重试；每次是记录了改动的独立诊断尝试。失败的语义结果全部保留，没有只汇报最后一次。最后一次同时改变了分组与比较指引，不能单独归因给分组，更不能凭单次调用证明唯一根因或稳定性。

最后一次识别出：当前 E58 是 business、两件行李、两件非免费且不合规；历史 E139 是同任务编号下 business、两件行李、零非免费、$55，成功合规。它将这些观察与 basic_economy 的不同结果区分开。此前“没有任何相关正面观察”的遗漏在这次输出中得到改善。

其最终 NO_EDIT 仍强调隐藏合同与编辑目标不足。**引用并讨论了正面证据，不等于其全部拒绝理由已经充分。** 是否能形成有条件的修订仍需结合可执行前提判断，不能强制推导完整行李规则，也不能把没有现成目标视为排除 MISSING 的充分条件。

### 2. 最终 Review 改动

Review 提示为 `evidence-review-v21.8`，提示内的辅助表示为 `operation_comparison_v21.1`。v21.6 的连续轨迹呈现及 v21.7 的比较顺序候选未保留。

实现只增加一个确定性阅读视图：从所选 Findings 引用的工具调用/返回确定工具名，再枚举已加载轨迹中该工具的全部调用，按工具与 task_ref 分组，复制事件编号、轨迹、轮次、Skill 身份、两维标签和原始参数。**不按标签筛正例，不指定行李字段或案例答案，不生成语义摘要，不推断因果配对。** 完整事件、返回结果、用户交互、政策和工具上下文仍在原包中。

同一 task_ref 只用于组织阅读，不证明条件相同或受控配对。多个调用不强制一一对齐；模型仍须回查完整原文。没有相关 Findings 工具引用时，对照视图为空，完整证据照常读取，不虚构比较。

这个辅助视图不进入 Memory、Fusion 响应或编辑计划，不增加 Agent、Review 调用、效果分类或逐 edit 流程。新增 5 项视图完整性测试，相关 v21/v20/Replay 共 217 项通过；覆盖全部匹配调用、空索引退回完整证据、字面参数保真和篡改拒绝。解码会精确还原规范输入，并重建对照视图检查复制内容；删除行、重复行、改标签或参数均拒绝。原事件别名保持一致。

本例复制 15 次 book_reservation 调用，按 6 个任务编号组织。最终代理输入 **51,612 → 54,986（增加 3,374，约 6.5%）**。这是对可定位性的明确成本，不能说降低了输入 token。三组旧焦点 Review 均已通过无损预检：行李 226 个事件/15 个对照调用，拆单 263/20，保障 315/62；后两组代理输入分别为 58,192 和 55,553，较之前增加约 10.5% 和 12%。真实模型只复验了行李，不能宣称其他场景效果已验证。

### 3. Fusion 改动及真实观察

Fusion 提示为 `issue-fusion-v21.5`，替换原提案依据段落，每个原固定输入只增加 20 个代理 token，没有新响应字段。要求区分可见行为偏差与纯结果标签：后续修正、最终成功/合规不抹去之前偏差；一个观察可以支持有限复查问题，但不能建立普遍规则。方向应针对行为/决策关系，而非禁止某种表面特征；不得因信息未知凭空增加确认、拒绝或转人工义务。

Fusion 不必先有完整规则、已证因果或最终 Skill 文本，但需指出有材料支持的问题与可反驳的有限方向。NO_EDIT 需要问题本身的理由，不能仅靠最终结果或样本少；并不要求所有可见错误都必须改 Skill。

两组原输入各运行一次，新响应均通过既有校验：

| 输入 | 上次响应 | 本次响应 | 语义观察 |
|---|---|---|---|
| 旧历史 control | 2 PROPOSE / 8 NO_EDIT | 3 PROPOSE / 7 NO_EDIT | 行李进入有条件比较；姓名和航班方向更明确地保留假设。但地址仍主要因单例且已纠正被拒绝，不能据此宣称判断问题完全解决 |
| 更新历史 treatment | 引用失败，无有效结果 | 4 PROPOSE / 7 NO_EDIT | 地址偏差被保留供 Review；行李不再直接规定未知额度时必须拒绝，而要求核查边界；姓名仍须核对用户原始表达，避免表面重复泛化 |

格式通过仅说明响应可用，不作为本轮主要创新或语义改进证据。本轮没有运行这些提案的下游 Review/Editor，不能称其为已批准修改。

### 4. 用量与后续边界

本轮共 **6 次真实调用**：2 次 Fusion、4 次 Review（含未奏效的呈现/指引实验）。全部完整返回并通过原结构引用校验，未自动重试。请求沿用 deepseek-v4-pro、temperature=0、reasoning_effort=high、输出预算 24,000。

最终实现与成功定位试验核对：规范输入、别名、响应 schema 和辅助视图内容相同；只有展示编码标识、提示版本及空白字符不同。原 trial 的源码快照与校验报告保留，未奏效的实现已撤回，不会叠加进运行流程。
