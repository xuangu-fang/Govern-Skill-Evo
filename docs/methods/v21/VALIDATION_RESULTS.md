## v21 单轮真实闭环验证

日期：2026-10-10。接续[局部验证](VALIDATION_RESULTS.md#v21-grounding-validation)。实验目录：`artifacts/methods/v21/v21_closed_loop_001/`。

**Memory → Fusion → Review → Editor → Replay → Memory 已真实执行完成；结构与证据绑定通过，方法语义验收部分通过。Candidate 未整体改善，也未晋升。** 本轮最重要的发现是：修改后认识已经能区分行为改善、任务结果和未执行验证，但进入输入的跨案例退化仍可能没有形成后续可消费的认识。

- 起点为 `v21_staged_validation_001/memory/updated-evidence.json`：真实 Replay 更新后的 9 个历史 issue，非先前固定 treatment 的旧 Memory。与原 `v20_pilot_001 / round-04` Parent、完整 Current Findings、Policy 配套使用。
- 复用经哈希与环境清单验证的 36 个 Parent checkpoint；对本次 Candidate 新执行相同 36 个训练任务。保留源 run/round 标识是为了验证谱系，所有新产物独立存放，不覆盖原 round-04。
- 当前 Fusion v21.6、Review v21.9 与 Memory v21.6 沿用不改；无新增 Agent、机制字段、重复 Review 或逐 edit Replay。
- Fusion 返回 4 PROPOSE / 8 NO_EDIT。四项实际提案均进入 Review，结果为 3 VERIFIED / 1 NO_EDIT；Editor 生成 3 条 ADD。姓名 NO_EDIT 没有进入 Editor。
- 随后完成 Candidate Replay、修改后证据构建、一次 Memory 更新及零调用的 issue 消费检查。未运行私有 Monitor Gate，未发布活动 Skill/Memory head，未启动正式多轮调度或伪造新一轮 Findings。

原始请求、响应、编辑、配对轨迹和评估均保留。生成与 Memory 共 7 次真实调用，无重试、答案修补或临时修改 Prompt。

## v21 分阶段真实模型复验

日期：2026-10-10。执行范围为 1 次 Memory、3 次固定输入 Review、2 次固定输入 Fusion，共 **6 次真实调用**，没有重试。对应前三步的最小强化；实现说明见[退化保留](REGRESSION.md#v21-regression-retention)、[证据比较](EVIDENCE.md#v21-evidence-comparison)和[提案依据](FUSION_AND_INPUT.md#v21-fusion-proposal-basis)。

**结论：Memory 的退化保留获得一次正面验证；行李 Review 的关键证据遗漏仍存在；Fusion 减少了送审，但出现过度筛选风险和一次引用错误。不能据此宣布 v21 语义验证通过或直接进入完整调度。**

### 1. 验证设置与比较边界

通过既有 Prompt 构建器、transport 和 validator 执行。Memory 使用既有 run_memory_update 保存与复验；Review/Fusion 在各自阶段停止，不调用 Editor 或 Replay。独立请求可以并行执行，但各阶段输入相互独立，没有将新 Memory 偷换进冻结的 Fusion 输入。

| 阶段 | 固定输入/旧输出 | 新提示 | 总输出预算 |
|---|---|---|---:|
| Memory | 原 update-48k 的同一输入及成功响应 | memory_update_v21.6 | 48,000 |
| Review | 原 treatment Review 6、5、3：行李、拆单、保障 | evidence-review-v21.5 | 各 24,000 |
| Fusion | 原 control、treatment 的各自固定 Fusion 输入 | issue-fusion-v21.4 | 各 24,000 |

模型请求与返回均为 deepseek-v4-pro，temperature=0，reasoning_effort=high。Memory 的 48,000 沿用旧成功调用的有效配置，通过原 transport 注入接口设置；默认源码预算没有修改。2,000 字符硬限制始终保留。

六组比较均验证 user payload、input_ref、引用映射、响应 schema、模型与上述运行参数不变，只更新各阶段系统提示。原代码和实验来源均冻结哈希，结束后确认未变化。旧输出直接复用，没有重跑旧 Prompt；因此是每组一次的新旧观察比较，不是同时随机化的消融或稳定性实验。control/treatment 是历史输入的名字，不是本轮重新开展完整两组消费。

人工核查 T009 新认识发现，它单独保存 business 两件行李的比较：两侧任务均成功，Parent 记录 nonfree_baggages=0、支付 $55，Candidate 记录 nonfree_baggages=2、支付 $155 且不合规。认识明确内部合同不可见，这一配对不能建立通用 business 行李规则，也不能解释其他 basic_economy 例子；原因和确切边界保留未知。该新 issue 的 attempts 为空，没有伪造对应修改或将观察强绑给无关 edit。

**不通过的理由是未比较关键证据，不是 NO_EDIT 本身错误。** 不能强制其推导完整行李规则。结果表明仅增加通用比较要求，在这次真实调用中不足以修复遗漏；尚不能判断是长输入、证据组织、注意力分配还是判断偏差导致。

### 4. Fusion：送审减少，但不能当作质量通过

旧历史 control 输入上的新响应通过校验：**2 个 PROPOSE、8 个 NO_EDIT**，旧响应为 10 个 PROPOSE。两项送审是条件航班选择、乘客姓名拆分。其他覆盖方向转为 NO_EDIT，四条 OBSERVED_PROBLEM 均保留问题归属，未被藏入 unassociated_findings。

人工复查发现两点需要继续验证：

- 地址确认中将 Court 说成 Street 的可见行为错误被 NO_EDIT。理由主要强调用户已纠正、最终写入正确、没有违规且只有单例。这可以成为保守判断的理由，但不能自动否定确认文字的行为缺陷；本次尚未说明为何其不足以支持有限修订。不能把这项拒绝直接算作正确节省。
- 姓名提案要求避免 first_name/last_name 的重复 token。核实用户期望的姓名字段有依据，但把重复 token 本身当作普遍错误，可能超出单例证据的适用范围。该提案未经过本轮 Review，不能视为可直接实施的规则。

更新历史 treatment 输入上的响应完整返回，但包含 `current_finding_refs: ["F20", "F21", "34", "F30"]`，被原校验器以 **unknown F reference: 34** 拒绝。没有补成 F34，没有生成有效 result，没有送到后续阶段。失败原文和全部用量保留。

只作失败诊断读取时，该原文还提出在行李额度不可见时问用户或拒绝的做法，并承认不知道工具能否提供额度。这暴露了从未知追加确认/拒绝义务的风险，不能因为“建议更具体”就当作成功。该未通过响应不计入有效决策统计。

所有成功结果已再次由既有校验器复验；Memory 保存恢复不触发新模型调用。运行源码、冻结输入、旧实验 JSON 和验证材料哈希均未变化。没有人工修改模型响应、静默重试、Editor、Replay 或活动 Skill/Memory 发布。本步仅运行实验脚本和校验，没有改运行源码，未以旧的 212 项测试冒充新语义效果验证。

原计划的局部串联以阶段结果合理为前提。由于行李证据比较仍不完整且一次 Fusion 失败，本轮止于六次调用，没有扩大实验或接通完整调度。

### 6. 后续建议

保留 Memory 本次有依据的改进，优先定位 Review 为什么忽略已加载正面观察。下一次应固定同一行李材料，检查相关证据的呈现和可定位性；不继续泛泛叠加提示，不加入预设答案，也不直接要求编辑。Fusion 应把引用生成稳定性与语义问题分开处理：格式错误不能人工修成成功，语义上还需检查“少提案”是否漏掉可修订缺陷，以及具体方向是否制造了无依据的普遍限制。

这些局部问题得到处理后，再用新 Memory 做一次受控串联。若之后生成候选，实际双维效果还需 Replay，不能用本轮文本判断代替效果验证。

## v21：缺陷依据调整后的三步真实验证

日期：2026-10-10。接续[缺陷依据与修改授权调整](EVIDENCE.md#v21-defect-grounding)。

**三步均已完成：姓名和地址的主要判断边界本次得到改善；跨问题检查部分通过，尚不能宣称修改授权已普遍可靠。** 姓名 Review 用原文推翻缺陷并选择 NO_EDIT；地址保留有限修改；代金券在 Fusion 有依据地停止；条件式航班选择的 Review 识别了真实偏差，但批准的停止/转人工要求还需要审视。

### 1. 冻结设计与执行范围

调用前冻结完整 treatment Fusion 输入、姓名/地址及两个迁移问题的引用范围、判定依据、源码哈希和最多五次调用的上限。使用 Fusion v21.6、Review v21.9，保持 deepseek-v4-pro、temperature=0、reasoning_effort=high、输出预算 24,000。没有根据响应修改 Prompt、替换案例或自动重试；Memory 的 2,000 字符限制不变。

本轮选择上一轮姓名误判所用的 treatment 来源，完整保留该批 Findings、Memory 和 Parent，不裁成只有目标案例的小输入。没有重跑 control。验收标准是缺陷判断及修改边界是否有证据，不是必须产生某个 verdict。

执行顺序为：

1. 一次真实 Fusion，复核姓名、地址的提案。
2. 根据这次真实 PROPOSE，经现有 GenerationInput 构造并运行姓名、地址 Review。
3. 保持版本不变，检查预选迁移问题：对条件式航班选择的真实 PROPOSE 运行 Review；代金券为 NO_EDIT，不人为追加 Review。

本次 Fusion 共 4 个 PROPOSE、7 个 NO_EDIT。行李虽仍 PROPOSE，但不在预定范围，未派发 Review。实际共 **1 次 Fusion + 3 次 Review**，不是一轮完整 generation，不生成 Editor 输入或 Candidate，不执行 Replay、Memory 更新及活动发布。

两个迁移问题曾出现在旧批量实验中，但未直接用于最新缺陷依据提示的调整。这是**开发集内迁移检查，不是完全未见过的盲测**。条件式航班选择检查仍可能值得修订的行为问题；代金券检查已有支持和当前覆盖下是否合理停止。

### 2. 第一步：Fusion 是否提出有依据、可反驳的方向

| 问题 | 决策 | 本次观察 |
|---|---|---|
| 姓名 | PROPOSE | 要求比较用户提供字段与实际传参，判断重复是否真是解析错误；承认期望值及失败原因未确定，没有直接要求删除重复 token |
| 地址 | PROPOSE | 保留 Court/Street 确认文字偏差及用户纠正，要求结合其他三段轨迹复查；没有把失败直接归因给 cedar 合同 |
| 条件式航班选择 | PROPOSE | 指出将原始总价基准换成候选之间差额的行为，并与 horizon 定价分开；但修订或转人工仍只是待核查方向 |
| 代金券分配 | NO_EDIT | 根据当前分配行为及已有条款，认为历史两类支付问题没有在本轮重现；将可见政策未说明该限制保留为泛化边界 |

姓名进入 Review 是合理的有限问题，不因最终 NO_EDIT 就判 Fusion 失败。Fusion 没有原始对话，不应被要求提前知道用户确实逐字段提供了这个名字。

地址提案还提到较宽的“核对 profile/order 显示”，不能直接视为已授权方向；是否有依据交由 Review。迁移中，代金券的 NO_EDIT 不是仅依据没有 OBSERVED_PROBLEM 标签：理由还指出具体有效分配和当前条款的对应。

### 3. 第二步：原始证据能否约束实际修改授权

#### 姓名：通过，原文推翻缺陷假设

Review 检查了用户明确给出的 `first_name='B Traveler1'`、`last_name='Traveler1'`，以及摘要展示、用户批准、实际调用和返回值。它认定 Agent 忠实使用了唯一可见的字段值；可见政策要求收集姓名和生日，但没有要求对多词或重叠词再次拆分/核对。

因此，success=false 不能证明姓名处理错误；缺少的是成立的行为偏差或独立要求。Review 返回 **NO_EDIT、gap=null**，没有再新增强制字段确认。

相比[上次验收](VALIDATION_RESULTS.md#v21-semantic-acceptance)，本次保留同样的 20 个原始事件、Findings、政策和 Parent，但 Fusion 提案与 Review Prompt 都变化了。因此可以说这一次组合行为改善，不能单独归因于 Review 提示，也不能据一次响应证明稳定性。

#### 地址：主要判定通过，保留措辞边界

Review 识别出用户请求 Court、Agent 确认时写为 Street，随后由用户纠正，最终写入正确；没有把“最终写对”当成早先没有偏差。它还利用其他成功与失败轨迹，说明同样的整体工作流并不保证任务成功，不能由这次文字错误推导所有失败的原因。

最终 **VERIFIED / MISSING** 的 gap 限于现有双地址确认环节：准确复述用户提供的目标，在请求或依赖确认前纠正不一致。没有改变写入顺序或引入 cedar 规则，也没有保留宽泛的 profile/order 显示核对机制。

其 reason 仍有“纠正后重新列出”的表述。正式 gap 没有要求用户再确认一次；这不能在后续 Editor 中扩展成已明确批准纠正值之后仍须新增确认轮次，也不能把准确复述扩大成禁止无害的格式规范化。本次通过的是有限修改依据，不是编辑效果已验证。

新 Fusion 选择了更多相关 Findings，地址输入由上次 22 个事件扩大到 88 个，旧事件全部保留。这个差异已记录，不能将结果完全归因于提示变化。

### 4. 第三步：跨问题迁移

#### 代金券分配：Fusion 层通过，未运行 Review

原始档案存在 basic_economy 使用代金券被工具拒绝，以及代金券重复使用后找不到支付方式的历史。当前预订调用则把代金券与礼品卡分配到合适的不同订单，避免重复使用；这些事实支持当前 Findings。

Fusion 依据这种具体行为与条款覆盖选择 NO_EDIT，并保留“操作限制并非由可见政策直接给出”的边界。它没有把历史整条轨迹的成功或合规标签当成每次支付调用都正确的证明，也没有因旧失败就重复提出已有方案。

本轮按真实路由停止，不追加 Review。**这里只验证了 Fusion 判断，不能写成代金券的 Review 也通过了迁移。**

#### 条件式航班选择：部分通过，修改授权范围仍偏强

Review 正确比较了：

- 原规则按相对原始 $400 总价的增量判断；LM323 增加 $160，LM324 增加 $100。
- 用户一度拒绝直接选择或调整规则。
- Agent 随后改用两个候选之间的 $60 差额，声称据此遵循原规则选择 LM323。
- 之后用户明确同意执行 LM321 + LM323，最终收费为 $160。
- horizon 的保留航段价格计算本身正确，不是这一问题的缺陷。

维持原比较基准、避免把改过的基准说成遵循原规则，有行为证据支持。但 Review 批准的 gap 进一步要求：在用户给出无矛盾选择或修订规则前不得更新；若用户拒绝解决或调整，则转人工。

问题在于它承认后来的明确批准，却主要以“批准没有恢复原阈值”继续支持上述要求。**错误地声称遵循旧条件，与用户后来是否授权具体方案，是两个需要分别判断的问题。** gap 允许用户给出明确选择，reason 却没有充分说明后来的明确选定为什么不属于这一情况。

可见转人工政策为：请求确实超出可用行动范围才转人工；工具可调用本身不能证明这一前提。因此，本次不接受整个 VERIFIED 授权为完全通过，记为 **PARTIAL**。这不意味着必须判 NO_EDIT、任何转人工都错误，或基准替换不值得修改；支持的是较窄的表达与决策缺陷，尚不足以无条件接受更强的停止/转人工要求。

## v21：已知问题修复与跨问题迁移验收

日期：2026-10-10。接续 [Review 比较与 Fusion 判断的定向修订](VALIDATION_CASES.md#v21-semantic-followup)。

**本步验收已完成，但没有全部通过。** 行李正面证据遗漏本次未复现；地址形成了有依据的有限修改；两个迁移案例的 NO_EDIT 有依据。姓名 Review 虽读到了反驳缺陷假设的原文，仍批准按重复词语增加强制确认要求，是本轮最明确的语义失败。不能以五份响应均通过结构校验替代这一结论。

### 1. 冻结范围与判定方法

本轮保持 Fusion `issue-fusion-v21.5`、Review `evidence-review-v21.8`、`operation_comparison_v21.1` 和 2,000 字符 Memory 限制。没有修改运行源码、Prompt、证据选择、响应 schema 或模型配置。所有请求在调用前保存；判定依据、调用上限及来源哈希在 `protocol.json` 中冻结，判定依据不进入模型输入。

- 复核上一轮两份真实 Fusion 输出，不重跑 Fusion。它们不是本轮的新观察，也不是独立稳定性样本。

共同要求：回应决定性正反观察与两维标签；区分整体结果、局部行为、跨轮观察与受控配对；核对用户意图、可用信息和当前 Parent；修改须针对成立的行为缺陷，NO_EDIT 须指出具体缺口，不能只依据结果标签、不确定性或已有文字。

### 2. 案例选择及实验边界

| 组别 | 案例 | 本轮输入来源 | 主要检验点 |
|---|---|---|---|
| 已知问题 | 行李 | 保持上一轮定位试验的规范输入，使用最终运行版本 | 正面历史是否再次被遗漏；拒绝理由是否回应条件性支持 |
| 已知问题 | 地址 | 上一轮 treatment Fusion 原提案，经现有 GenerationInput 构造 Review | 后续纠正不能抹去确认文字偏差；不扩展为未证实的地址合同规则 |
| 已知问题 | 姓名 | 上一轮 treatment Fusion 原提案，经同一入口构造 | 能否用原始用户表达反驳“重复词语就是解析错误”的假设 |

### 3. 已知问题结果

#### 行李：证据比较通过，决策理由部分通过

本次 NO_EDIT 明确回应并引用 E139：round-01 的 T022/R036，business、两件行李、零非免费、总额 $55，任务成功且合规。它同时讨论当前 E58：同任务编号、business、两件行李均非免费、总额 $155，任务成功但不合规；并保留 basic_economy 条件下全额计费仍合规的反例。行程类型的正面证据没有再替代行李正面证据。

这说明此前遗漏在本次调用中未复现，不等于已证明长期稳定。E139/E58 是跨轮观察，不是显式受控 Replay 配对，也不能据此建立“business 两件必定免费”的规则。

理由仍称任何 cabin/membership 条件化收费规则在没有隐藏合同的情况下都无法执行。这比证据能证明的范围更强：工具不提供完整额度确实构成限制，但输出没有充分解释已有同条件正面观察为何不足以支持有限经验方向。**本次不判 NO_EDIT 本身错误，也不要求强行写额度规则；将拒绝理由的这一推断记为 PARTIAL。**

#### 地址：局部 Review 通过，Fusion 分歧仍保留

原文链条是 E2 请求 `9 Cedar Court` → E14 确认时写为 `9 Cedar Street` → E15 用户纠正并确认 → E18/E20 写入及返回均为 `9 Cedar Court`。

Review 没有因最终写入正确而否定早先偏差，批准一个 MISSING 修改：地址同步确认应准确复述用户提供的地址。它保留“文字有误但未写错数据库”的界限，不改变身份验证、地址上下文查询或写入顺序，不推导 cedar 合同规则，也没有声称该偏差解释了 success=false。

这是可测试的有限修改授权，不是效果已经验证。后续若进入 Editor，不能将“准确复述”扩成无害格式规范化也被禁止，或用户已明确纠正后仍须额外再确认。

复用的 treatment Fusion 支持这一有限方向；control Fusion 仍主要以单例、已纠正、最终合规拒绝。后者的理由只算部分充分，不能因为另一组 PROPOSE 就认定 NO_EDIT 必然错误，也不能把两种 Memory 输入下的差异当成 Prompt 改进的因果证据。

#### 姓名：未通过，证据已读到但没有正确约束修改

原始用户消息 E14 明确分字段给出：

```text
First name: B Traveler1
Last name: Traveler1
```

E15 展示完整姓名，E16 用户确认，E17 调用忠实使用这两个字段，E18 返回同样字段。当前证据没有提供不同的期望拆分，也没有表明 Agent 改错了用户提供的名字。

Review 在 reason 中承认这一原文，却将字段重叠定义成必须再次消除的歧义；其 VERIFIED gap 要求：当多词 first_name 的末词等于 last_name 时，在展示摘要或调用前必须逐字段确认，不得依赖一般预订确认。

**这把一个表面模式提升为通用强制义务，没有先证明实际行为缺陷。** “可执行、可测试”“当前 Parent 没有姓名规则”或“没有把失败标签直接当成因果”都不足以弥补这一缺口。问题是语义判断，不是引用格式、原文未进入输入或工具视图漏选。

Fusion 的姓名提案也有风险：treatment 在问题陈述中先写了“避免重复 last-name token”，虽然 reason 要求核对用户原文，Review 仍未反驳这个预设。原始 Finding 的 OBSERVED_PROBLEM 标签和 Fusion 提案都应允许被原文推翻；本次链路没有做到。

### 4. 跨问题迁移结果

| 问题 | 模型结论 | 人工判定 | 支持及限制 |
|---|---|---|---|
| 保留航段结算 | NO_EDIT | PASS | 回应历史 summit 按原票价估算与最终结算不一致，比较当前 summit 使用搜索价格后匹配退款、horizon 使用原价后匹配收费；区分 T036 的选择问题与正确计价。依据包含真实执行，不只是规则已写入 |
| 标识符识别 | NO_EDIT | PASS | 比较旧混用 ID 导致查询错误与后续 reservation-first 路径；后者成功不等于可据此删除当前 user_id 获取要求。当前规则已覆盖两种情形，本包没有支持额外修改的新缺口 |

结算理由对旧 summit 失败的描述可由 E252/E255 原文核对，虽然结构化引用未逐项列出这些历史失败；当前正面执行和 horizon 反例有明确引用。其结论限于加载的执行条件，不能解释为所有渠道已经解决或特定 edit 的因果效应已证明。

标识符包没有当前 Findings，`operation_comparison` 为空，但完整历史保留并被利用。这里的 PASS 是没有支持进一步改写的缺口，**不是当前执行已验证正确**；不能用 Parent 文字覆盖替代当前运行证据。

这两例支持冻结机制在其他问题上仍可形成有依据的拒绝，并未暴露与姓名相同的新强制义务。但是两例都偏向已有覆盖/无需新增修改，不能据此证明它能在未调参问题中稳定发现并批准新的有效修改。
