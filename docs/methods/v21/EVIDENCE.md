## v21 第 2 步：接通修改后学习侧证据

日期：2026-10-09。状态：已实现证据装配、持久化、历史回查及独立离线入口；后续[第 3 步 Memory 更新](MEMORY.md#v21-memory-update)已实现并通过离线测试，后续[第 4 步消费适配](MEMORY.md#v21-memory-consumption)也已接通，新一轮 v21 generation source 可显式复验并继承此前档案。未切换 v20 运行入口。方法边界见 [v21 契约](METHOD.md#v21-method-contract)。

### 1. 本步实现

- [modification_evidence_v21.py](../../../src/skill_evolution/v21/modification_evidence_v21.py)：从实际 generation audit 和已完成的 Parent/Candidate 训练回放重建学习侧证据，保存版本与原始引用，向后续 Memory 更新提供可选择的输入。
- [prepare_v21_evidence.py](../../../scripts/preparation/v21/prepare_v21_evidence.py)：独立只读转换入口；不执行 rollout、重新评分、私有 Gate、模型调用或 Memory 提交。
- [test_modification_evidence_v21.py](../../../tests/skill_evolution/v21/test_modification_evidence_v21.py)：真实检查点格式的构造测试和失败边界。

本步仅建立数据通路：回放事件与双维标签可以被更新函数读取，之后也能按来源重新打开。它不生成“有效/有害”等标签，不更新 assessment，不把修改前的 Review 当作修改后有效性的证明。

### 2. 来源验证与投影

`build_modification_evidence` 先复验现有 generation audit，确认 Candidate 确由保存的审阅与编辑产生；使用调用方提供的可信训练 backend manifest，复验两侧输入、完整性标记与逐文件摘要。

配对继续检查初始状态、可见环境、用户模拟器输入及执行设置的一致性；这些私有内容只用于运行侧核验，不进入学习侧产物。学习侧沿用既有投影，只获得可见 policy/tools、原始可见事件、Level-0 成功/合规标签及来源。

不读取 `candidate-summary.json` 作为标签真值，也不以整批成功/合规计数替代逐次联合观察。失败、违规及两侧持平的运行均保留。

分组后的 `T001` 等标识可能是重新排列的匿名别名。实现通过 generation 中的 `experience_bindings` 显式映射到回放任务，再核对 Parent 原始事件、上下文、标签、版本和 rollout。不能直接按相同展示编号配对，也不通过语义相似度猜测对应关系。

### 3. 档案与局部读取

`ModificationEvidence` 保存：

- 本轮精确两侧 Skill、generation 和检查点摘要；
- 当前简明 Memory、提案、原有审阅及实际 edits；
- 逐任务配对来源、每次运行的双维标签和完整事件；
- 现有历史证据档案，以及显式导入的 v21 历史证据引用。

使用既有 `PAIR/...`、事件和 edit 引用；不新增经验效果状态。`REPLAY` 记录只是原始观察的来源类型，不是归因结论，因此不自动关联所有 edits，也不把整包结果复制成每条 edit 的功劳。

完整档案用于保存与回查，不默认整体放入模型输入。`open_memory_evidence` 接受现有问题、提案、来源记录或配对引用：

1. 读取所选问题下的尝试和来源，并跟随明确的来源/联合 edit 关联。
2. 保留关联记录中的支持、反证和必要的完整轨迹。
3. 若引用涉及本轮 Parent，沿明确来源映射加载对应 Candidate；引用任一配对侧时同时加载双侧。
4. 不展开无关问题、配对或整轮历史；未知引用直接报错，不静默忽略。

`parent_pairs` 明确标识诊断中的 Parent 引用和 Replay Parent 属于同一次观察。两种引用入口不构成两份独立证据。

读取接口也允许“旧 issue + 明确的新 pair”，不要求旧 issue 本轮已被 Fusion 选中。这只提供证据可达性，不自动判断新证据与旧方案的语义关联。第三步更新仍须说明关联依据。

### 4. API 与运行位置

```python
from src.skill_evolution.v21.modification_evidence_v21 import (
    prepare_memory_evidence, open_memory_evidence,
)

evidence = prepare_memory_evidence(
    round_dir=completed_round_dir,
    backend=benchmark.evolution,
    output=derived_output_path,
)

packet = open_memory_evidence(
    evidence,
    proposal_refs=[proposal_id],
)
```

`round_dir` 需要已完成的 `generation/generation-audit.json`、`parent_evolution` 和 `candidate_evolution`。`output` 必须位于源轮次目录之外，旧产物只读。已有相同输出可幂等复用，不同内容不能覆盖同一路径。

这是完整 Candidate 回放之后、语义 Memory 更新之前的接入点。第 3 步更新函数已消费此类局部视图；本步没有自动调用更新模型，也没有用 v20 的默认摘要函数充当 v21 更新实现。旧版 Evidence Review 的输入协议不在本步修改，后续消费适配仍需按计划实现。

历史 bundle 由调用方显式传入 `history`，不能扫描邻近目录就认定已提交。保存函数返回内容摘要引用，重新加载必须提供调用方持有的 `expected_ref`。这些引用和历史是否属于已提交运行，由未来调度器的提交记录或显式离线导入决定；摘要不是对历史语义真实性的证明。

## v21 Evidence Review 的证据比较

日期：2026-10-10。对应真实模型局部对照后的优化第 2 步，接续[退化证据跨轮保留](REGRESSION.md#v21-regression-retention)。

本步解决的是：原始正反证据已经加载，但 Review 的修改依据没有充分回应它们。保留证据与使用证据是两个不同的验收对象。只调整 v21 Review 提示，版本由 `evidence-review-v21.4` 升为 `evidence-review-v21.5`。

### 实现要求

在原有 `reason`、`gap` 和引用字段中完成比较，不增加响应字段或额外调用：

1. 回应对当前问题和修改方向有实质影响的正面历史及反例，包括未标记为 `known_counterevidence` 的相关成功观察。不要求逐事件或逐 edit 列表。
2. 比较实际行为、参数、返回结果及执行时条件；说明用户意图/授权、信息可得性、政策和工具背景中的关键差异或未知。成功与合规标签保留原轨迹归属，跨轮观察不能冒充显式 Replay 配对。
3. 区分实际观察、条件性支持和因果假设。仅列出引用不等于回应证据；相反观察为何限制结论，或者为何不适用于当前情况，应在理由中说明。
4. `VERIFIED` 必须落到当前 Parent 中有证据支持的行为缺陷和可执行、有适用条件的修改。隐藏的完整政策不可见，不自动否定有限经验支持；经验也不能覆盖可见政策或证明某条隐藏规则。不能为了通过单例增加规则，不能将偶然成功泛化。
5. `NO_EDIT` 仍须回应相关正面和负面证据，说明阻碍合理修改的具体缺口或当前覆盖情况。已有文字不证明执行有效；原因尚不明确也不必然排除有依据的有限修改。没有足够行为证据或缺少执行前提时允许不改。

Fusion、Memory 更新、证据选择、无损打包、校验器和 Editor 均保持既有逻辑。2,000 字符 Memory 硬限制不变。不增加独立 Agent、重复 Review、状态分类或自动语义评分。程序校验仍只能验证契约和引用，不能证明比较合理。

### 验收与后续真实验证

受控测试验证原始输入可无损进入 Review，双侧引用、反证和理由保留，`NO_EDIT` 只执行一次 Review、不调用 Editor、不产生候选，保存后可复验。相关回归继续覆盖 `VERIFIED` 经 Compiler/Editor 生成候选及引用/编辑权限约束。构造响应不代表模型已经学会比较。新增 1 项 NO_EDIT 通路测试，连同相关 v21/v20/Replay 回归共 **211 项通过**（58.51 秒）。

后续小规模真实验证应固定本步三组原始输入，仅替换 Review 提示，复用原输出比较，不重跑两批完整消费。判定依据是：是否回应决定性的正反证据；是否按真实条件解释可比性和限制；是否区分观察与推测；是否对当前 Parent 给出有依据的修改或具体的 `NO_EDIT` 理由。不得以 `VERIFIED` 数量或是否修复当前案例作为唯一标准。三个案例没有强制预期 verdict。

本步没有真实模型调用、Replay 或活动 Skill/Memory 发布。真实模型是否改善，留待计划中的分阶段验证。

## v21：双维证据修订的四步验证

日期：2026-10-10。接续 [单轮闭环](VALIDATION_RESULTS.md#v21-closed-loop-validation)，实验目录 `artifacts/methods/v21/v21_evidence_revision_001/`、`artifacts/methods/v21/v21_evidence_revision_002/`。

**结论：四步执行完成，工程链路通过，语义验收部分通过。最终仅采用第二版 Memory 证据呈现调整；跨案例经验修订改善，但 Fusion/Review 的姓名缺陷判断及问题边界仍未通过，不能据此宣布 v21 已能稳定合理复用经验。**

### 调用前明确的目标与边界

按既定四步推进：定位并冻结验收依据、最小修改、固定证据更新复验、跨案例消费验证。保留 Issue—Attempt、单次 Memory 更新、原有 Fusion/Review、2,000 字符限制。通过标准是对不同条件下的成功/合规证据形成可修订认识，并合理约束后续修改；不是特定任务被引用，也不是七组退化必须全部归入某个 issue。

文中的 T 编号仅在对应 artifact 批次内有效；跨批次关联以完整 trajectory/pair 引用、版本和原始内容为准，不能按相同短编号合并。

### 第一步：定位与证据关系

已核对完整 canonical 输入、实际 wire 输入、模型原始回答、Memory 合并和 issue 消费视图。七组退化的两侧轨迹、事件、版本和两维标签都完整进入输入。原始回答已遗漏相关航班退化，写回没有删除原先生成的认识。现有语义 Prompt 已明确要求比较相关退化并保留双方原文，不能将原因归结为缺少这条要求。

需要区分两个问题：

1. **语义选择发生遗漏。** 航班原案例与跨案例退化都可支持本轮新建的同一 issue，但输出只吸收原案例。T022 原始配对存在，模型没有把它纳入认识。
2. **部分历史问题不可写。** 取消、团体预订、购买保护等旧 issue 本轮仅出现在 memory_catalog，不具有本次更新权限。不得为追求覆盖率重复建 issue 或混入已加载问题。其缺口不能仅靠增加“必须记住退化”的要求解决。

配对身份、角色标签、事件索引和事件正文原本分散在多个目录；这是可检验的阅读负担假设，不是已经证明的唯一根因。一次输出变化也不能排除模型采样差异。

| 固定证据 | 应保留的认识 | 不应推出的结论 |
|---|---|---|
| 当前轮航班原案例与相关案例 T003/T022 | 避免擅自替换比较基准的行为支持，与另一条件下未完成任务的限制共同存在；原始用户授权和条件差异需解释 | 直接证明某条 edit 导致失败，或因合规就宣称处理方式整体有效 |
| 当前轮行李 T009 | 成功下降、合规上升，但未执行预订；历史收费反例仍成立 | 收费规则已修复，或缺少姓名时必须绕过收集要求 |
| 当前轮地址案例 | 确认文本改善、最终写入及标签无相应改善 | 任务成功问题已解决，或将具体街道写入规则 |
| 当前轮其他退化 | 按行为和原 issue 范围判断相关性，保留未知；目录中已有的问题不可重复创建 | 将所有退化塞入新航班/行李/地址 issue |
| 另一轮团体预订 T013/T016 | 拆分有合规支持；另一个拆分任务失败，原因不能由结果标签单独确定 | 因任务失败整体否定拆分，或把单例成功推广成已知内部契约 |
| 另一轮行李 T009 | 任务均成功却出现合规退化；收费分类的两侧行为及条件仍需保留 | 任务完成足以证明方案可继承 |
| 另一轮购买保护 T034 等 | 区分用户知情选择后执行与条件无法解决时未完成任务 | 仅为提高成功率绕过限制，或因失败增加普遍强制转人工 |

后四类用于检查一般化能力；历史批次先于修改冻结，未依 T022 的答案选择展示。它们是既有开发数据，不是全新分布的盲测。

### 第二步：最小呈现调整

新增 `pack_memory` 的临时 `replay_comparison` 视图，将**所有已加载配对**的双方标签、实际工具调用及有序原始事件引用并列，放在完整证据目录前。全部条目由原始数据确定，不做语义关联、评分、归因或证据筛选；无调用保持为空，不补造成功行为。原始事件仍全部提供。

表示可无损恢复 canonical 输入，并校验派生视图与原文一致；引用、角色、标签或覆盖被改动会拒绝。持久化 Memory、输出 schema、证据范围、语义 SYSTEM、Fusion/Review Prompt 均不变。Memory 请求版本改为 v21.7，表示格式为 paired_replay_v21.1，不新增运行状态。

主实验输入估算由 118,461 增至 130,822 token；跨批次输入由 170,793 增至 188,872。这里以少量重复索引换取可比较性，不能未经实测就视为有效优化。

### 第三、四步：固定验证安排

主实验复用 closed_loop 的修改后证据，只运行一次新 Memory 更新；不重跑 Editor/Replay。对照旧输出，检查双维认识与相关原始配对的 issue 可见性。

跨批次实验复用 staged_validation 的 round-03 原始更新输入，再运行一次 Memory 更新。其 Candidate 正好对应已有 round-04 Parent，可与真实配套 Findings 一起进入现有 Fusion/Review。对实际 PROPOSE 执行 Review，NO_EDIT 不补做 Review；不执行 Editor，不预设必须修改。当前轮主实验的新 Candidate 没有新诊断，不能拿旧 Findings 冒充其下一轮输入，因此只做零调用消费可见性检查。

两批输入、条件、模型设置和验收依据均在调用前冻结于 protocol.json；过程中不追加语义 Prompt、不改答案、不按不利结果重试。结构覆盖与人工语义验收分别报告。


### 固定证据复验：第一版暴露的错误与第二版调整

两版均各运行一次主批次和历史批次 Memory 更新；没有重试不利答案。第一版为 `artifacts/methods/v21/v21_evidence_revision_001/`，第二版为 `artifacts/methods/v21/v21_evidence_revision_002/`。第二版是在第一版实际错误定位后单独冻结的新呈现实验，不是隐去失败后重跑。

第一版保留了 T022，但历史团体案例出现错误归因：把 Candidate 使用与其本次用户输入完全一致的生日，写成 Agent 改错了生日。两次运行的用户自行提供了不同生日，不能将 Parent 的用户输入当作 Candidate 应当复制的事实。原始用户事件本来全部在完整目录中，错误已经进入模型原始回答，不能归咎于写回丢失。原文对照保存在 `001/transfer-dob-counterexample.json`。

因此第一版不按“记住了 T022”判为成功。第二版仅在配对视图内补充**各自运行的全部用户消息原文**，与各自调用及标签一起展示。双方原文不会混合或自动解释为因果；全部原始目录仍保留。没有增加语义 Prompt、案例规则、归因字段、独立 Agent 或额外 Review 流程。

| Memory 复验 | 第一版 | 第二版 |
|---|---|---|
| 航班跨案例限制 | T022 纳入认识且 issue 可回查 T003/T022；部分措辞过强 | 保留成功下降、合规不变、用户拒绝选择及两侧不同行为；不宣称单条修改因果 |
| 当前轮行李 | 保留成功下降/合规上升与未执行预订 | 同样保留；明确收费修改没有得到执行验证，旧收费反例仍成立 |
| 地址 | 区分确认措辞修复与任务标签 | 同样区分，不把具体地址写成通用规则 |
| 历史团体拆分 | 保留双维冲突，但错误声称修改了用户生日，语义失败 | 不再声称生日被改错；保留成功下降/合规上升与原因未知；成功拆分配对仍可回查 |
| 历史行李 | 退化可回查，但被放入较宽泛的旧 trip-type issue | 单独表达行李收费问题，保留任务成功不变/合规下降；不猜测隐藏收费契约 |
| 历史购买保护 | 知情选择可执行与拒绝选择后转人工共同保留 | 同样保留；不因合规就宣称任务恢复，也不建议绕过知情选择 |

两版主批次均从七组退化中保留 T009 和 T022 的 issue 关联，剩余五组未因此自动变成可写历史 issue。历史批次的三组退化均有双方引用；这是覆盖检查，不是语义正确性的证明。两版完整输入、引用映射、输出 schema 和 SYSTEM 与旧请求一致；派生视图可还原原始输入。所有认识均通过原有 2,000 字符限制。

第二版主批次实际输入 136,361 tokens、输出 15,735；历史批次实际输入 195,557、输出 16,180。相对旧输入代理估算，新增呈现约增加 20.6% / 19.3%。本次是用输入成本改善比较条件，不是 token 优化；若规模扩展，仍需另外验证按需读取，不应直接增加更多重复材料。

这些结果仅为开发案例上的单次描述性观察，不能证明展示方式单独导致改善，也没有确立稳健的跨分布泛化。


### 实际历史消费：第一版结果

第一版执行 1 次 Fusion 和全部 5 个实际提案的 Review，未经 Editor/Replay。来源校验通过。Review 输出为 2 VERIFIED / 3 NO_EDIT，但人工语义验收**未通过**，VERIFIED 不能替代证据检查。

- 团体：Fusion 受到生日误读影响，提出数据完整性修改。Review 根据当前 Parent 的拆分规则及实际行为拒绝新增修改，但没有明确修正错误的历史生日归因。
- 姓名：Review 将“用户明确给出 first_name=B Traveler1、last_name=Traveler1，Agent 原样使用”认作字段切分缺陷；再用不同用户输入条件下的旧成功记录支撑额外确认，缺陷依据不成立。姓名规则虽 VERIFIED，仍判语义失败。
- 航班：Fusion 把比较基准/条件问题关联到旧渠道定价问题，Review 识别问题边界不一致并 NO_EDIT；没有真正建立合适的新问题依据。
- 行李：Review 读取到历史 business/两件行李的正面观察，并保留其条件；最后因隐藏契约及缺少确定规则而 NO_EDIT。避免编造普遍收费规则是合理的，但是否过度要求完整契约、忽略有限可检验修改，仍部分充分。
- 地址：Review 从用户原文与错误确认措辞支持有限修改，并明确最终写入已正确；没有由任务失败标签反推数据库错误。此项符合验收要求。

第一版共 8 次调用、654,582 tokens，包含上述失败；不只统计有利结果。


### 第二版消费：已经确认的限制

第二版冻结后产出 4 个实际 PROPOSE，全部交由现有 Review 处理；团体不再因“生日被改错”而产生修改提案。当前规则能够执行拆分、失败原因未知，支持暂停修改。但 Fusion 的理由主要援引当前 Findings 和已有规则，不能把这一变化完全归因于新的 Memory，更不能仅凭提案减少宣称学会了双维经验。

姓名提案仍被 Review 标记 VERIFIED。其理由承认用户给出了两个明确字段，却用另一次运行中不同的姓名参数与成功标签支持重复确认义务。原始用户表达并不相同，不能直接把参数差异认作 Agent 的切分错误。原文摘录存于 `002/name-counterexample.json`。此项仍为语义失败，不送入 Editor。

航班 Review 识别了比较基准被替换，也记录用户后来接受了新的比较方式；但仍在旧渠道定价 issue 下批准一个不同的条件解析 gap，问题归属和新增义务的依据仍不足够稳定。因此，相关观察不应记作整项跨问题复用通过。


第二版行李 Review 确实比较了同条件的历史正面记录与当前违规记录：商务舱、普通会员、单人两件行李时，调用参数除非免费行李数量和对应金额外一致；任务均成功，合规不同。它也使用经济舱的合规反例限制了“所有行李不能收费”的泛化，并提出有限条件下的修改假设。这体现了双维经验进入修改依据，而不只是保留反证。不过，提案仍附带了“其他组合也必须获得肯定分类”的要求，缺少相应查询路径，且有限观察不能确立普遍收费契约；因此判为部分充分，不把整个 VERIFIED 提案视作已验证规则。


第二版地址 Review 仍从原始请求与确认措辞的差异确认局部缺陷，并用正确最终写入和其他案例限制结论；没有宣称修复了任务失败原因。但其对用户纠正后再次确认的要求比第一版更宽，仍应受已有政策与实际授权约束，不把额外确认本身当作改进。

第二版共 1 次 Fusion、4 次实际 Review，4 个 Review 均输出 VERIFIED；人工验收不会因此判全通过。两个实验合计 **15 次真实调用，1,253,924 tokens**（输入 1,081,646，输出 172,278）。包括 4 次 Memory、2 次 Fusion、9 次 Review；没有 Editor、新 Replay、Gate 或版本发布，没有自动重试或改写模型答案。

### 修改范围

仅替换 `memory_consumption_v21.py` 中已有 Fusion / Review 判断段落：Fusion 提示 v21.5 → v21.6，Review v21.8 → v21.9。不新增提示章节、字段、分类、Agent、第二次 Review 或逐 edit 流程。证据选择、操作对照视图、输入/响应 schema、Memory 更新、2,000 字符限制及模型预算保持不变。

Fusion 现在明确区分报告的行为与推断的缺陷。`OBSERVED_PROBLEM` 和 Memory 都是可修订的解释；未加载原文时，应把可能偏差及可推翻它的证据作为 Review 问题，不能先把表面模式定为错误、再把消除该模式当作修改方向。

Review 在授权 VERIFIED 前，须核对缺陷是否由用户原始表达、实际行为和适用要求支持。原文可以推翻 Finding、Memory 和 Fusion 的判断；忠实使用用户明确信息，不能仅因结果外观异常就被定义成缺陷。缺陷假设被推翻且该问题内没有其他受支持缺陷时，使用原有 NO_EDIT 并解释，不发明预防性义务。

两处共同收紧：新增确认、拒绝或转人工要求，须有相关歧义、冲突、授权缺口或适用要求作为依据。“当前没写这条规则”“可以执行、可以测试”不证明新增义务有必要。

同时保留另一侧边界：后续纠正或用户批准，不抹去此前已经发生的真实偏差，也不能覆盖适用政策；因果机制尚未完全解释，仍可对有依据的缺陷提出有限修改。这样不会把姓名原文反驳缺陷的情况，混同于地址确认确实写错、后来才纠正的情况。提示中没有姓名字段、重复 token 条件、地址值或案例预设答案。
