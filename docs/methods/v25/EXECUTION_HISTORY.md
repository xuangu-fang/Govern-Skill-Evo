## Actor 的两个上下文

- `messages` 是正式历史：初始输入、实际执行的响应、真正回传的执行反馈。
- `format_repair` 是持久化临时上下文：最近一次完整但不合格的响应及其执行前校验错误。
- 每次请求使用正式历史加上临时上下文。完整不合格响应替换上一份临时上下文；网络错误、截断和空白输出保持当前请求不变。
- 程序得到实际执行结果后，将该响应加入正式历史并清除临时上下文；若执行失败，再加入真实执行反馈。下一次程序生成不携带以前的格式失败。
- `extract_code()` 的校验范围保持不变，包括单一 Python 代码块、语法和受保护路径绑定。校验反馈只说明具体错误，不增加任务解法、标准答案或评分纠错。

例如 `H → A 格式失败 → H+A+错误 → B 格式失败 → H+B+错误 → C 执行`，执行后的正式历史为 `H+C+执行反馈`。这些是不同请求；最终 C 可能受格式反馈影响，不能宣称它只根据 H 生成。

原始 `requests[*].messages`、请求目录中的 `messages.json`、响应/错误/用量、`attempts[*].request_messages` 均保留真实内容。`repair_feedback` 是准备供后续修复请求使用的反馈；是否实际发送，以请求归档为准。它不冒充永久历史中的 `feedback_to_actor`。

## 预算与恢复

每份待执行程序的生成请求共享 6 次总额度，包括首次请求、网络失败、截断、空输出及格式修复。它们都不占 30 次程序执行预算。只有程序实际执行后才进入下一执行槽并获得新的请求额度。

生成预算耗尽记录 `generation_incomplete`，保存检查点，不评分、不进入优化模块，也不因恢复重新发放预算。单次 API 和程序时限保留，无累计任务时限。认证等不可重试错误不因该策略变为可重试。

恢复优先消费已保存响应和执行结果，不重新调用已完成请求或重复执行程序。执行已开始但结果未知仍必须停止；临时格式上下文不会绕过这条限制。

## 原始审计与模型证据

`facts.build_facts()` 先按请求顺序还原并校验真实请求、临时反馈、响应、执行代码和正式历史，再构造模型证据。原始记录不因投影被删改。

模型视图仅保留实际执行的完整响应、实际代码、执行日志、实际反馈及最终评分。生成失败、临时格式反馈和 `api_requests/generation_responses` 计数不进入模型视图；成本统计继续读取原始归档。评分权限和标准答案隔离不变。

执行证据上的 `request_context=execution_only_v1` 明确表示：`request_messages` 是正式执行历史，不一定等于生成该响应时的完整 API 请求。这个标记也保留在孤立尝试引用中。

所有下游入口共用同一份证据：Grouping、Diagnosis、Preconditioner、Replay 的完整 runs，以及 Verifier／Repair 的当前和历史单条引用，都不会从原始 API 请求重新补入临时格式反馈。此规则适用于新协议产生的历史证据；旧协议归档保持原语义，不能将其混入新实验后宣称已完成隔离。

证据 ID 保留原始响应序号，例如 `P1:3`、`P1:4`，允许有间隔。P 改为 Q 时只替换前缀，最终提交引用同步保持后缀；引用必须属于实际证据集合，不能引用过滤掉的编号。编号间隔不是程序失败或实际执行次数。

时间线去重依旧无损还原**所选证据视图**。新协议的证据过滤本身有意省略生成过程，不称为完整真实请求的无损压缩。旧输入继续使用原时间线说明，新输入采用明确说明该边界的版本化内容。完整响应与实际代码仍分别保留，不增加跨任务共享或代码去重。
