# v21 第 1 步：双维归因认识的跨轮学习契约

日期：2026-10-09。本文记录第 1 步方法契约；第 2 步[修改后证据通路](V21_POST_MODIFICATION_EVIDENCE.md)、第 3 步[Memory 更新](V21_MEMORY_UPDATE.md)和第 4 步[Memory 消费](V21_MEMORY_CONSUMPTION.md)已实现并完成离线验证。尚未调用真实更新模型、接通完整 v21 自进化或验证语义效果。本文中的示例是设计说明，不是实验结果。

## 1. 研究定位与核心问题

论文主线是双维度 Skill 自进化：研究如何利用任务成功与程序合规反馈，指导 Agent 持续修改 Skill。Memory 是双维归因认识跨轮积累、修订与复用的载体，不单独承担设计通用记忆系统的研究目标。

v21 聚焦的问题是：

> 当一次 Skill 修改在任务成功与程序合规上得到不同反馈时，如何利用真实运行证据更新对历史尝试的认识，并据此指导后续修改，避免因单一维度的结果而错误强化或否定整份经验？

同一尝试可以在一个维度上获得支持，在另一维暴露问题。系统应在证据支持的范围内继承已有依据的做法，针对已知问题提出修订，对尚不确定的影响继续验证。两维反馈一致的运行同样可以更新认识；不一致是研究重点，不是唯一允许学习的输入。

待验证的主张是：在相同可用反馈与预算约束下，让双维认识持续更新并参与后续修改，比只记录尝试、总体结果或统一好坏结论，更有助于获得成功且合规的 Skill。本文不预先认定该主张成立，也不宣称已解决通用正确归因或稳定泛化问题。

## 2. 从 v20 继承什么，实际改变什么

v20 已经有双维诊断、问题—尝试记忆、原始证据审阅、反证保留和旧方案重试限制。v21 不把这些已有原则重新命名为新增贡献。

截至本文日期，本地默认运行路径存在以下事实：

- [runtime_v20.py](../src/skill_evolution/runtime_v20.py) 的 `build_v20_memory_update` 为生成的 edits 创建尝试，assessment 主要组合 Candidate 整批成功/合规统计、修改前的 Evidence Review 说明、Gate 决策及局部效果未确定说明；它不是基于修改后轨迹的语义认识更新。
- [benchmark_adapter_v20.py](../src/skill_evolution/benchmark_adapter_v20.py) 的 `build_local_attribution` 将 edits 与回放范围、整批统计关联，效果保持 `UNRESOLVED`；该结构绑定本身不构成行为归因。
- [v20 Memory 契约](V20_MEMORY_CONTRACT.md) 已允许新证据修订旧认识，也允许联合关联和不确定性。v21 要落实双维证据的学习与使用，不能只增加两个结果字段。

| 环节 | v21 的必要变化 |
|---|---|
| 修改后证据 | 将相关 Parent/Candidate 原始轨迹、两维反馈和版本来源接入 Memory 更新，并可在后续回查 |
| Memory 更新 | 根据新证据形成或修订对尝试的双维认识，不只追加结果统计或复制修改前判断 |
| Memory 消费 | 让 Fusion 与 Evidence Review 根据这些认识调整下一轮的修改依据，并回应已知限制 |

沿用现有 Diagnosis、Fusion、Evidence Review、Compiler/Editor、完整 Candidate Replay 和 Gate 的主要职责。v21 首版不调整 Gate 采用标准。

## 3. 什么是双维归因认识

这里的归因是有证据约束的行为分析：比较实际行为与两维结果，说明它们与修改之间有哪些可支持的联系、反证和限制。它不是每条 edit 的独立因果效应估计。

认识必须区分以下含义；它们是表达边界，不是新增字段或状态分类：

- **观察**：哪个版本、哪次运行执行了什么行为，成功与合规标签是什么。
- **解释**：原始证据支持怎样的行为关联；是否存在其他解释或反例。
- **待验证内容**：哪些效果、原因或可迁移范围仍不清楚；后续方案不能把这些内容写成已证实事实。

修改前的 Review 说明为什么值得尝试，不证明修改后已经有效。任务标签记录结果，不能单独说明原因；单次成功且合规也不证明提炼出的规则普遍有效。可见 policy 规定必要程序，经验不能因为某次违规成功就修改或解除该要求。

认识的粒度不得细于证据支持的粒度：

- 有依据时，可以记录某个行为或修改与观察的关联。
- 多条修改无法分开时，保留联合认识；共享证据不复制成各条 edit 的独立贡献。
- 只有整包结果时，只记录整包观察和局部影响未知；不得为每条 edit 强行分配效果。
- 观察不能可信关联到任何尝试时，保留在档案中，不强塞给某个历史方案。

## 4. 流程与职责：在现有更新中学习

```text
Parent Evolution → 当前 Diagnosis
→ Fusion（当前发现 + 历史双维认识）
→ 现有 Evidence Review → Compiler / Editor → 完整 Candidate
→ Candidate Evolution / Replay → 既有私有 Monitor / Gate
→ Memory 更新：读取学习侧真实证据，形成或修订双维认识
→ 提交 retained Skill 与 Memory → 下一轮
```

上述 Memory 更新是语义学习与记忆写入的一次工作，不再串接独立归因 Agent、第二遍 Review 或总结 Agent。即使实现需要一次语义模型调用，也应由该更新直接产出有来源的认识与增量记录，不先运行一套重复分析再重新总结。

既有归因产物如果可用，可以作为待核查认识及其来源使用；结构绑定不能冒充语义归因。实际行为和效果判断仍须有已加载的学习侧证据支持。不以取消独立分析阶段为由，退回“只抄结果分数”的更新。

当前 Diagnosis 继续独立发现问题，不由历史方案预先限定。后续 Evidence Review 仍负责结合当前 Parent 和原始证据判断修改是否有依据；Memory 本身不授予编辑权限。

## 5. Memory 更新的最小约定

### 5.1 输入与表示

更新使用相关问题及旧尝试、本轮实际 edits 和已有修改依据，以及相关 Parent/Candidate 学习侧轨迹、两维反馈和可见 policy/tools。精确版本、运行、事件及两维标签的来源在档案中可解析；后续审阅能重新打开这些证据。

对完整本轮回放独立检查两维标签，任一维度从 `true` 降至 `false` 的配对必须进入更新输入，并保留双侧原始轨迹，不能因未被修改前 gap 引用而遗漏。该输入覆盖规则不赋予某条 edit 因果责任，也不保证识别标签未变时的新增行为错误。实现及验收见[新增退化覆盖](V21_REGRESSION_COVERAGE.md)。

沿用 v20 的 `problem`、`approach`、`assessment`、`edit_refs`、`source_refs` 及问题/尝试身份。assessment 用简明自然语言表达两维观察、可支持的解释、仍成立的限制和未知，不要求固定模板、双维评分或效果枚举。来源引用指向档案中的真实证据，不能用自由文本摘要代替。

写回和复查以既有 `problem` 原文为固定范围锚点，普通更新不得替换该文本；认识修订进入相关 assessment，不同问题使用独立身份。联合提案或共享 edit 不授权复制整段建议到各 issue。输入派生的 `issue_source_refs` 区分该问题已有显式来源链与其他共享上下文，不作语义正确性证明；共享原文与反证仍须保留。实现及限制见 [issue 边界](V21_ISSUE_BOUNDARIES.md)。

同一次 Memory 更新还为每个被更新 issue 维护一段简明 `current_understanding`，综合有依据的方向、适用条件、双维问题/反例、相对旧尝试的变化和未知。它通过已有来源记录保存，旧认识和完整 attempts 继续归档；Fusion 优先读该段及尝试目录，Review 按现有 attempt 引用展开历史，并强制保留已知反例和历史配对退化。旧数据没有综合认识时保持完整读取。规则、版本与验证见 [当前认识](V21_CURRENT_UNDERSTANDING.md)。

### 5.2 真实修改后的学习

根据相关轨迹检查实际行为发生了什么变化，分别说明任务与合规反馈支持了什么、暴露了什么，并据此更新认识。已有修改依据用于帮助理解本次尝试，不作为期待结果的证明；目标以外的相关反证也必须保留。

若只观察到“确认已执行，任务未完成”，可以保留这两个事实；只有原始事件提供进一步依据时，才能写入“确认后未继续执行”等具体认识。不得仅凭结果差异认定确认导致失败，也不得由一份合规标签推断流程每一步都正确。

### 5.3 两维分别保留，认识可以修订

任务侧的新支持不能自动抹去合规侧反证，合规侧改善不能证明任务方法有效；反过来，一维失败也不能抹掉另一维已观察到的事实。

新证据确实改变某个判断时，可以修订其解释、范围或限制，并注明依据；不要求旧判断永久保留为当前真理。旧运行事实与历次认识仍留在档案中，不因新版本改善而改写历史标签。

### 5.4 新证据可以修订相关旧尝试

更新范围不仅包括本轮新生成的修改。新证据涉及已有问题或方案时，即使本轮没有重新执行同一条 edit，或该议题没有被 Fusion 选中，也允许更新其认识；必须说明关联依据，不能借相似措辞强行合并。

同一问题、同一行为方案及适用范围沿用身份；行为路径或适用范围实质变化时，建立新尝试并保留旧尝试。同一尝试关联多次运行时也要保留各自版本与来源。新版本结果不会自动成为旧版本的效果证明。

只处理有相关新证据的记录，不恢复逐轮全历史审阅。没有相关新证据的记录原样保留；没有新增认识时保留正文并关联必要来源，不追加重复叙述。没有实际修改时不伪造新的尝试。

### 5.5 保留共同来源

同一方案分别出现过“成功但违规”和“失败但合规”，不等于它出现过“成功且合规”；不同版本更不能拼接。两维边际统计也不能替代联合观察。

ACCEPT 与 RETAIN 都能产生学习证据。Gate 只决定部署哪个版本，不决定每份经验是否有效；一次 ACCEPT 不会永久认证某条经验，一次 RETAIN 也不会否定所有尝试。

## 6. 下一轮怎样使用认识

Fusion 读取现有简明问题记忆，不只依据一个维度的有利描述选择历史方向。引用某个尝试时，相关的另一维问题、反证和未知应同时呈现；不必为此展开全部历史原文。

Evidence Review 在现有局部核验中回查相关原始证据，并在正常修改理由中说明：本轮参考了什么已有依据，回应了什么已知限制，哪些影响仍需通过新运行检查。不增加“继承/修订/拒绝”等持久化状态或额外处置表。

在证据允许时继承有效做法，不等于必须拆出独立的有效片段；整体方案仍可重写。必要程序继续由 policy 约束，不能因为一次任务失败而被删除。未知不会自动生成禁止、确认或转人工义务。

允许探索尚未验证的候选；限制的是把假设冒充为已验证经验。重复旧方案需要回应其限制或提供改变旧判断的新证据，不能仅因为再次遇到同类失败就原样重试。若证据变化不涉及当前修改依据，也不要求候选必须变化。

## 7. 信息与工程边界

- 学习侧只使用 Evolution 可见轨迹、policy/tools 和允许访问的 Level-0 成功/合规反馈及其来源。不能读取隐藏任务机制、私有数据库、evaluator 原因或 Monitor 轨迹/分数。
- Gate 完成状态及 ACCEPT/RETAIN 可留在版本提交历史；不作为 assessment 的有效性依据。流程上先取得 Gate 回执不意味着语义更新有权消费私有评价。
- 相关证据有界装配，保留必要上下文、联合关系与反证；不将每个问题自动扩展成全轮、全历史输入，也不截掉反证以继续运行。证据不足如实记为不足。
- 沿用原子提交、来源验证与可恢复边界。更新失败时保存阶段产物，不发布新 Memory head 或用旧认识伪装成功；同一提交重试不重复新增对象。
- 沿用 v20 对 NO_UPDATE / UNABLE 与 NO_EDIT 的区别：没有有效 Candidate 的轮次不伪造 Replay 或完成提交；有有效 Candidate 的完成轮次可以更新相关 NO_EDIT 议题。首版不额外增加独立的“无候选记忆维护轮”。
- v21 使用独立入口、配置和产物目录；稳定模块通过显式适配复用，保留 v20 行为和既有产物。历史产物只能标明来源后只读转换，不冒充 v21 真实运行，不直接 resume 旧版本运行。

## 8. 复杂度约束

首版不新增双维目标表、四象限操作分类、效果评分、置信分、尝试生命周期状态机、自动淘汰、独立关联/归因/压缩 Agent、重复 Review 或强制逐 edit 分析。

不新增逐 edit 隔离 Replay，不要求拆分能力与合规修改，不另设一套修改前目标协议。已有修改与审阅依据足以作为修改后理解的起点。

这些约束删掉的是冗余组织形式，不是修改后的学习能力。仅扩充字段、复述两维标签或复制修改前理由，不满足本契约。若后续发现某个判断缺少必要输入，优先补最小证据连接，并记录原因，而非先增加模块。

## 9. 贯穿示例与验收边界

以下是构造示例；X、X′、X″ 是不同方案版本，不是已测得结果。

1. **X：成功但违规。** 轨迹显示完成删除，但跳过规定确认。记录成功事实与违规依据；不能据此证明跳过确认促成了成功，也不能把 X 当作可原样沿用的推荐流程。
2. **X′：失败但合规。** 修改后已确认；若事件明确显示随后未调用删除工具，可记录该执行缺口，同时保留本次合规观察。不能借 X 的成功证明 X′ 有效，也不能断言新增确认是失败原因。
3. **下一轮修订。** 在现有 Review 中据该缺口提出确认后继续执行的有界修改，仍须满足 policy 与可见工具条件；如果实际失败原因没有证据，就保留未知，不编造同一修订理由。
4. **X″ 的新观察。** 若同一次运行成功且合规，更新对新方案的认识并保存联合来源。这提供本次联合支持，不证明规则普遍有效，也不洗掉 X、X′ 的历史问题。

后续实现至少通过以下语义检查；这是离线验收清单，不是运行时新增流程：

- **形成认识：** 修改后原始证据能支持新的行为认识，结果标签不能单独替代原因解释。
- **修订认识：** 新支持或反证能改变相关旧判断；无关记录不变，历史事实不被改写。
- **维度边界：** 一维结果不抹去另一维观察；不同运行或版本的证据不被拼成联合成功。
- **粒度边界：** 联合或整包证据不被分配为独立 edit 功劳；未知如实保留。
- **影响修改：** 改变与决策相关的历史双维证据后，下一轮理由及必要时的候选随之调整；仅改写摘要或机械改变候选不算通过。
- **来源边界：** 读取摘要不冒充读取原文，证据可回查，不依赖私有 Monitor。

## 10. 交付状态与后续顺序

第 1 步交付本契约、文档索引及 Decision Log。第 2 步增加独立证据装配、保存与局部读取接口；第 3 步增加单次语义 Memory 更新、来源校验、增量合并与可恢复产物保存，并完成构造测试及真实证据请求预检。第 4 步已接通更新后的认识到 Fusion/局部 Review/候选生成及下一轮证据归档；为复用稳定 Compiler/Editor，只在 v20 模块增加显式装配适配入口，不改变 v20 默认行为或配置。未运行真实更新模型或完整 v21 campaign。

原定实现顺序及当前状态：

实验前补强已完成新增退化覆盖、issue 写回/复查边界，以及简明当前认识和历史消费；接下来接通下列完整运行及 Pilot。

1. 已完成：接通修改后学习侧证据及其历史来源。
2. 已完成接口及离线验证：在 Memory 更新中实现双维认识的形成与修订。
3. 已完成接口及离线验证：调整现有 Fusion/Review 对这些认识的使用。
4. 下一步：接通完整 campaign 的恢复和原子发布，离线核查并运行两轮真实 Pilot，展示认识形成、修订和后续修改响应的证据链。
5. 在相同反馈、模型、任务、Gate 与预算约束下比较 v20/v21，并检验新增认识的跨轮使用及双维使用规则的作用。

结构校验只能证明来源与接口有效，不能证明归因正确；Pilot 只能先确认闭环，机制效果还需对照、重复运行及独立评价。最终报告成功、合规、联合成功和实际成本，并检查已知问题重复、单维错误强化及认识更新情况。不以增加调用或获得额外信息造成的收益直接声称方法创新。
