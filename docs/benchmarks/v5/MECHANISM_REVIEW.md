## Benchmark v5 新机制候选与 Success 优先筛选方案

2026-10-11 · Screening Draft 0.1 · 仅完成机制筛选与首个原型选择

**首选 S-A：小批量作业排程中的状态依赖换型与批处理耗时学习。** 它值得进入单原型验证，但尚未证明真实 Agent 会遇到有意义的学习困难。本轮同时保留两个 S 备选和一个不同于 LG1 的 G 候选；不同时实现四个环境，不生成任务集，不调用实验模型。

本文件不修改 v4、旧 v5、既有评价器或历史成绩。最终评价继续遵循 [统一 S/C 协议](SC.md#benchmark-v5-sc-protocol)：S、C、S∧C；Success-only 的 C 与 S∧C 为 N/A。原始 Skill 与进化后 Skill 是后续研究的主要比较，Raw Experience 与 Oracle 不成为强制实验分组，Benchmark 不绑定 v21 Memory。

### 1. 筛选结论

候选编号只用于本轮讨论，不替换 LS1/LG1，不表示正式准入或新的数据版本。

| 候选 | 学习的业务规律 | 初步决定 | 最关键的未决问题 |
|---|---|---|---|
| **S-A 小批量作业排程** | 前后作业特征决定换型耗时，批量决定加工耗时；两者共同影响交付顺序 | **首个值得实现的 S 原型，有条件推进** | 初始未标定是否符合选定业务；是否已有准确预测/排程服务；通用排序是否已经足够 |
| **S-B 订阅变更的净结算与资金占用** | 变更生效时点、计费周期、优惠与抵扣共同决定应付和实际退款 | 暂缓，保留筛选记录 | 精确账单预览和自然撤销很可能消除跨任务学习必要性，容易重演 LS1 |
| **S-C 批量数据作业的资源与吞吐匹配** | 工作负载特征与计算、存储瓶颈共同影响有效吞吐和费用 | 后备，暂不实现 | 公共规格、运行监控和在线扩容是否直接解决；合成性能规律是否过度简化真实噪声 |
| **G-A 采购变更后的依据复用与增量重验** | 业务事实变化如何使已有核验依据失效，影响范围如何沿依赖关系传播 | 保留为不同结构的 G 候选，暂不实现 | “全部重验”及权威有效性查询是否覆盖全部任务；不能人为禁止合法保守路径 |

优先 S-A 的理由是：**已经发生的加工会消耗业务时间，事前正确认识规律可能影响最终交付；这种作用不必依赖禁止查询或撤销来制造。** 这只是合理的选择依据，仍需后续真实执行证实。没有候选在本轮获得“高难”“可学习性已验证”或“正式 Benchmark 准入”的结论。

不继续在首批候选中展开普通运费/承运时效组合。FedEx 的官方接口已经提供费率与预计运输时间，许多此类问题首先应通过合法查询解决；该接口并不等于整个仓储履约的完工预测，但不能把它本来提供的信息删掉后宣称产生学习挑战。[FedEx Rates and Transit Times API](https://developer.fedex.com/api/en-ms/catalog/rate/docs.html)

证据入口：[真实校准报告](CALIBRATION.md#benchmark-v5-calibration-report)、[D1/D2 最小试跑报告](DECISION_PROBE.md#benchmark-v5-minimal-probe-report)、[LS1/LG1 学习报告](LEARNING.md#benchmark-v5-learning-report)、[LG1 两轮闭环报告](SC.md#benchmark-v5-sc-closed-loop-report)。旧学习报告中的 P/完整服务口径仅作为历史记录，当前设计以统一 S/C 协议为准。

本轮将三个判断分开：**业务中存在这种结构；允许的反馈足以学习相关决策；真实 Agent 的任务表现确实因经验而改善。** 官方文档能支持第一项的一部分，纸面检查能发现第二项的缺口，第三项必须等待真实校准。

### 3. 所有候选统一回答的五个问题

1. **学什么，业务依据是什么？** 隐藏对象必须是稳定、有适用范围的规律，不能是任意 ID 对答案的映射。
2. **为什么认识它会改变任务结果？** 给出真实目标、关键条件、可执行路径，说明哪里必须作出有业务后果的决定，同时检查合法捷径。
3. **从哪些允许的反馈中学？** 区分正常工具观察、Train 结束反馈与维护侧真值，明确不向学习器提供什么。
4. **这些证据够不够分辨正确做法？** 列出合理竞争解释、区分对照、尚不可辨识的范围；不能只证明真规则能拟合训练案例。
5. **如何证明迁移，何时应淘汰？** 用未见条件中的实际 S/C 与条件反转检验；不能用换 ID、规则复述或单次猜中替代迁移。

公开或合法可获取的内容始终包括：用户目标、权限与授权、必要程序义务、安全与兼容边界、工具副作用、当前业务事实、计量单位、时间推进方式、可用资源及正常恢复路径。公开义务的存在与初始未知的适用细则须有明确边界。

允许未知的是特定企业或资源的初始未标定表现、稳定结算细则、可学习的证据适用关系；**已有权威手册、预览、状态查询和自动路由应保留。** 如果真实系统已经公开完整规则，就按公开知识任务处理，不能为了本研究宣称它不可获取。

### 4. 四张候选卡

#### 4.1 S-A：小批量作业排程中的状态依赖换型与批处理耗时

**问题一：学什么，依据是什么？**

Oracle 的制造排程资料支持序列相关换型、资源状态、批处理容量和批窗口等业务结构；同一资源可以按工序与设置等条件合批，作业顺序会改变设置开销。这说明“顺序×状态×批量”具有业务基础。[Oracle Shop Floor Modeling](https://docs.oracle.com/cd/E26401_01/doc.122/e48794/T473792T475172.htm)、[Oracle Sequence Dependent Setups](https://docs.oracle.com/cd/E26401_01/doc.122/e48756/T309464T309477.htm)

拟学习的是新接入加工资源的**实际耗时模型**：工装是否变化、工艺档位变化方向、两个设置活动同时发生时如何占用时间、同一设置下批量与加工时间的关系。规则作用于可见特征及它们的关系，不能为每个 SKU 配一项秘密时长。

官方系统本身也支持维护参数和排程。资料不证明这些参数天然隐藏，更不证明某台设备具有本文拟定的耗时。首个原型采用“新资源尚未完成性能标定，已有真实作业日志可积累”的**合成业务假设**；实施前需核对这一假设及工具清单，不能冒充成熟调度系统的默认行为。

**问题二：为什么会改变 S，如何完成任务？**

用户要求在公开交期前完成一组订单的规定数量与规格。初期只用一台资源、少量订单和明确的可用时段；库存、容量、允许合批条件和订单释放时间公开。Agent 读取订单及机器状态，拟定批次与顺序，提交实际作业，检查完成事件，必要时重排尚未开始的部分，最后核对交付并给出真实回执。

未知耗时会影响“先做紧急单还是先利用当前设置”“等待合批还是立即加工”。已执行加工所用时间不能回滚，但草稿可改、未开始作业可按正常规则撤回；不设置仅许提交一次之类的额外限制。查询不会因为模型思考较久而暗中耗尽模拟交期。

S 检查全部目标订单是否按约定时间、数量、规格真实完成，以及回执是否准确；提交计划或预测准确都不等于 S。没有焦点程序挑战，C 与 S∧C 为 N/A。安全边界由公开契约与环境约束处理，不把安全知识隐藏为难度来源。

**问题三：从哪里学？**

正常工具返回订单、资源状态、实际批次、设置与加工起止时刻、完成数量及公开费用。Train 结束后返回同一 S 评价器的结果及对应未达成目标，例如“订单 X 实际完成时刻晚于其交期”，引用已经发生的事件。允许保留成功轨迹，不能只给失败样本。

需能分开观察等待、设置、加工，或提供足够的匹配对照来分离它们。反馈不自动附送完整公式、未执行计划的精确完工时间或维护侧最优排程；如果业务本来存在这些查询服务，则保留，并重新评估候选。

**问题四：能否学明白？**

竞争解释至少包括：只看当前产品、看前后转换；对称/方向相关换型；两个设置开销相加/重叠；按件加工/按批加工；每订单重复设置/设置保持后复用。训练须包含单因素变化、反向变化、联合变化和批量跨容量的证据，不能让换型、数量与排队始终同时变化。

首版只学习少量离散特征与有限作用关系，不同时引入故障、质量良率、未知容量和维护例外。新资源类型、未经证据约束的阈值、未学过的工艺不直接放入应当成功的测试。第 5 节给出可辨识性检查表，而非声称已经完成枚举验证。

**问题五：如何检验迁移，什么会否决它？**

用新订单、不同数量/交期/初始状态、已学特征的新组合检验实际交付；设计公共条件改变后正确顺序反转的情况。改名、重排 JSON 字段或替换无关描述不应改变正确终态。

必须检查：最早交期优先、当前设置优先、同类集中处理、能合批就合批、全部拆开、保守估时、在线观察后恢复，以及现有精确预测工具。若其中任一简单合法策略覆盖整个有效范围，就接受它并降级候选。若 S0 已经稳定成功，也不通过偷偷收紧交期或增加秘密例外制造失败。

**决定：首选。有条件进入单原型实现；业务代表性、工具可得性、可辨识性与真实学习收益均仍待验证。**

#### 4.2 S-B：订阅变更的净结算与资金占用

**问题一：学什么，依据是什么？**

订阅变更可能涉及剩余周期折算、折扣、账户抵扣与退款时点。Stripe 官方文档说明这些因素确实会影响结算，并区分负向折算与实际退款；也明确提供账单预览。[Stripe Prorations](https://docs.stripe.com/billing/subscriptions/prorations)、[Create a preview invoice](https://docs.stripe.com/api/invoices/create_preview)

候选知识是特定套餐合同中“变更顺序×生效时点×抵扣适用范围”的组合规律，不是套餐名称到手续费的任意映射。价格承诺、收费授权、货币精度、账单状态和客户可访问的合同必须公开或可查；不能把消费者本来有权知道的费用藏起来。

**问题二：为什么会改变 S，如何完成任务？**

任务是完成指定服务切换，在公开服务连续性、可支付余额和预算要求下办理。路径为读取合同与账单、比较允许的变更方案、获取可用报价、按已授权方案执行、核对生效状态与实际资金。S 检查服务与资金终态，不增加“首选必须正确”的隐藏评分。

知识可能帮助避免把账面抵扣当作立即可用现金，或误判优惠在变更后的适用范围。但**当前没有证据证明这种理解必须依赖跨任务学习**：若预览与正常撤销已经足够，知识仅减少尝试，不改变最终 S。

**问题三：从哪里学？**

使用合法预览、逐项账单、支付/抵扣/退款状态及 Train 的目标完成反馈；区分“预计”“已入账”“可支付”时间。隐藏机制版本固定，不因 Agent 做法临时变化。反馈只说明执行过的账务事实与未满足的目标，不附完整计费规则。

**问题四：能否学明白？**

区分即时退款与未来抵扣、优惠先后顺序、按周期比例与固定费用、服务生效与结算生效。需要同合同异生效时点、同金额异资金状态、同优惠异适用范围等对照。不能用一种金额和一种变更路径推断所有舍入或边界规则；精确到分的迁移必须有相应证据与公开精度。

**问题五：如何检验迁移，什么会否决它？**

测试未见的周期位置、余额、合同特征组合与变更方向，并保留条件翻转；不只换账号。必须让“预览所有合法候选再选”“办理后查询并合法撤销”参与筛查。若可覆盖，保留为账务执行锚点；若有真实不可恢复的结算后果，需先有业务依据且公开其语义，不能为堵捷径虚构。

**决定：暂缓。与 LS1 风险高度相似，暂不投入环境开发。**

#### 4.3 S-C：批量数据作业的资源与吞吐匹配

**问题一：学什么，依据是什么？**

AWS 文档表明，存储表现同时受实例与卷的能力约束，I/O 大小等工作负载特征也会影响表现；相关规格已经公开。它支持多因素瓶颈这个业务结构，不支持把公开规格变成秘密。[Amazon EBS-optimized instance types](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ebs-optimized.html)

可考虑隐藏的是某个客户工作负载在允许配置下的未标定有效吞吐规律，例如并发增加后的饱和、任务规模与启动开销的关系。CPU/存储硬上限、兼容性、计费、数据访问权限与配置含义全部公开。缓存、压缩、倾斜等只作为后续可能的业务解释；首版不能把它们全部叠加，更不能把虚构公式说成真实云产品保证。

**问题二：为什么会改变 S，如何完成任务？**

目标是在给定截止时间和预算内完成一个授权数据作业并交付正确输出。读取作业规模、可用配置和价格，选择资源，启动后读取吞吐与费用，按正常能力扩容/重启/恢复，验证输出。S 检查业务输出、完成时间和费用；C、S∧C 为 N/A，不另设“资源利用率优秀”成绩。

知识可能帮助避免在存储瓶颈时只加计算资源，或在启动开销占主导时过度并行。预算应来自任务约束并公开，而不是看到模型成功后追加。所有配置都能按期且在预算内时，不应强求唯一最优配置。

**问题三：从哪里学？**

从真实执行的启动、处理进度、吞吐、资源使用和费用记录中学习，Train 反馈引用完成结果。允许正常压测、监控和恢复；不人为限制只能试一种配置。若短时间合法画像就能解决全部实例，应接受并降低跨任务学习价值判断。

**问题四：能否学明白？**

区分 CPU 限制、I/O 限制、启动固定成本、并发饱和等解释，需要保持工作负载不变只改一种资源、保持配置不变只改规模的对照。若数据倾斜、缓存状态与配置同步变化而无法观察，就不可归因。真实环境存在波动，不能用少量带噪点推导精确确定阈值；合成首版若采用确定模型，必须声明它的适用范围与现实差距。

**问题五：如何检验迁移，什么会否决它？**

测试同一已学负载类型的新规模、资源配比及公开预算/交期组合；让瓶颈在已学因素之间转移。不能把完全新算法、新硬件或未知缓存行为当作同世界泛化。检查“按公开最小瓶颈计算”“总用最大规格”“在线自动扩容”“低成本先压测”的覆盖性；只会预测更准却不影响真实 S，不足以准入。

**决定：后备。规则结构与 S-A 有区别，但仍涉及经验性能模型；先核验工具捷径和业务代表性，不与 S-A 同时建设。**

#### 4.4 G-A：采购变更后的核验依据复用与增量重验

**问题一：学什么，依据是什么？**

Oracle 的变更流程支持比较变更前后属性，审批规则可考虑金额变化、价差和非标准条款；内部与外部变更的版本处理也有所不同。这支持变化范围、核验范围和版本的关联，但不证明本文的隐藏依赖图。[Change Order Life Cycle](https://docs.oracle.com/en/cloud/saas/procurement/26b/oaprc/change-order-life-cycle.html)、[Internal and External Change Orders](https://docs.oracle.com/en/cloud/saas/procurement/26b/oaprc/internal-and-external-change-orders.html)

候选知识为“字段→业务事实→核验结论”的适用关系：某项事实改变后，旧依据是否仍支持当前处理；影响一个明细行还是整单；连续变化应对照哪个核验快照。与 LG1 的静态“多种凭证能否替代、组合”不同，这里关注已有依据随状态变化的失效与恢复。

具体依赖是合成企业配置，尚需过程材料或业务专家核验。当前授权、审批状态、谁可审批、必须使用有效依据和必要记录义务始终公开；不能隐藏授权是否失效。SAP 官方也提供按属性配置流程重启的能力，系统能自动触发重审；必须保留真实存在的状态与路由。[SAP Restart Purchase Order Workflow](https://userapps.support.sap.com/sap/support/knowledge/en/3053155Customizing)

**问题二：为什么会改变 C，如何完成任务？**

任务是处理已完成部分核验、随后发生变化的采购对象。读取当前版本、变更历史、授权与旧依据；查询权威状态；补齐实际缺失或失效的核验；将有效依据绑定到当前办理记录；完成授权范围内的变更或交接。

S 检查约定业务终态与准确回执；C 检查适用核验、授权、依据有效性及必要记录；S∧C 为合取。多做一次合法核验本身不扣 C。程序义务只在 C 计一次，不恢复 P_complete，也不通过“回答了正确失效集合”新增第三个成绩。

尚未证明它需要经验：**如果“每次全部重验”合法且能完成目标，就可能用一个固定策略覆盖全部任务。** 若仅靠真实重验时延/成本让它失去 S，那是未来需要重新审查的协调型候选，不能继续把它当作独立 G 学习已被证明。

**问题三：从哪里学？**

正常工具提供变更前后事实、历史快照、核验对象、当前授权状态与实际操作。Train 返回 S/C 和有事件依据的缺失义务、失效依据诊断；可提供授权、无副作用的历史案例审查。无需让 Agent 先实际越权来换反馈，也不返回整张依赖图。

需包含“变化后仍可复用”的例子和失效后正确恢复的例子。只有重验后通过的样本，无法排除“任何变化都必须全部重验”的解释。

**问题四：能否学明白？**

对每项拟测依赖，至少有相关/无关字段变化对照；对范围有相关行/其他行对照；对连续变化有相同起点下的单次/累计变化对照。价格与计量单位等联合变化可能抵消或改变业务事实，但是否按事实等价复用，必须有明确业务依据，不能由作者臆定。未覆盖的阈值或间接依赖不得强行进入测试。

**问题五：如何检验迁移，什么会否决它？**

迁移到新订单、不同明细数量、变更顺序与已学依赖的新组合；无关文字变化不应使依据失效。检查权威实时有效性查询、自动路由、全部重验、全部正常送审等合法策略。若它们稳定完成且 C 通过，则降为程序执行锚点；不能新增“不得多验”“仅许一次复核”等无业务依据的限制。

**决定：仅保留不同结构的 G 候选。未解决全量重验捷径前，不优先实现，不为了补矩阵强行准入。**

### 5. 首选 S-A 的最小原型边界

本节给下一阶段一个具体实现目标，**不是已生成的训练/测试任务，也不是已经冻结的规则**。

#### 5.1 只做一个小环境

| 项目 | 首版范围 |
|---|---|
| 业务角色 | 为一个新接入的小批量加工服务安排并实际完成订单 |
| 环境规模 | 一台设备、两项有业务含义的设置特征、公开容量与日历、少量订单；先不加第二资源、故障、质量随机性 |
| 公开事实 | 工装/工艺档位、初始状态、订单规格/数量/交期/释放时间、库存、合批资格、容量、已有工具与费用语义 |
| 拟未知知识 | 设置特征变化的耗时、变化方向、两个设置活动的耗时关系、批量与加工时间；固定于一个世界版本 |
| 允许操作 | 读取状态、拟定/调整未开始计划、提交批次、推进到下一业务事件、读取实际结果、正常撤回/恢复 |
| 时间语义 | 使用模拟业务时间；设置、加工和实际等待推进时间；模型 token、读日志和修改草稿不暗中推进交期 |
| 执行后果 | 已完成加工不能退回过去的时间；未开始作业能否取消等后果公开，不另加人为试错次数限制 |
| S | 所有目标订单的数量与规格正确、按各自公开交期完成，回执与状态一致；接受一切满足目标的合法计划 |
| C/SC | N/A，不强加焦点合规规则 |
| 诊断 | 完工时刻、迟到原因、设置/加工分段、可选耗时预测；均不成为新最终评价维度 |

这是业务执行环境，不应退化为只输出一道排程题答案。另一方面，也不需要为“像 Agent 任务”机械增加工具步骤：可用批量接口就提供批量接口。

#### 5.2 纸面检查：固定排序为什么可能不够

以下数字完全是**供评审的合成算例**，不来自 Oracle/SAP，不证明某种真实工艺的时间值；本轮未将它们写入任务数据。示例不承担完整可辨识性证明。

设一台设备当前处于低档，工装不变。每批最多 4 个标准单位，两个订单各占一批；每批实际加工 10 分钟，低→高设置 4 分钟，高→低设置 8 分钟。两个订单均在时刻 0 可执行。

| 公开条件 | 高档订单先做 | 低档订单先做 | 业务意义 |
|---|---|---|---|
| 高档交期 26，低档交期 28 | 高档完成 14；低档完成 32，低档迟到 | 低档完成 10；高档完成 24，两者按期 | 单纯最早交期优先会失败，利用当前状态可成功 |
| 只把高档交期改为 18、低档交期改为 36 | 高档完成 14；低档完成 32，两者按期 | 低档完成 10；高档完成 24，高档迟到 | 始终当前设置优先会失败，需要响应公开交期变化 |

这两种情况在同一规则下有不同成功顺序，且都有余量，说明不能只规定一个通用顺序。它们**没有证明 S0 会失败，也没有证明跨任务学习不可替代**：模型可能凭一般经验选对，或在执行中恢复。后续必须保留并真实检验这些可能性。

另一项待核验结构是合批：同设置两单各 2 单位且均已就绪时，合为一批可能节省一次加工；若其中一单尚未释放，而另一单即将到期，等待凑批又可能有害。释放时间与合批资格公开，不能靠隐藏到货制造意外。真实任务应包含宽松、中等、较紧但有余量的交期，不只收集卡边界案例。

#### 5.3 训练证据与竞争解释的最小覆盖表

每行代表一种必须覆盖的对照，**不等于固定两条任务**；一段正常作业轨迹可以提供多项证据，同类证据也可能需要多次。先检查覆盖与混淆，再决定最小训练规模，不按数量凑集。

| 待识别关系 | 至少需要的允许证据 | 要排除的解释/混淆 | 暂不允许声称的迁移 |
|---|---|---|---|
| 当前状态与转换有关 | 同一目标设置，从相同状态与不同状态开始；可见实际设置段 | “只看订单种类即可”“固定每单设置” | 未出现过的状态维度 |
| 方向相关 | 其他条件相同，正向与反向转换记录 | “换过去和换回来一样” | 新工艺档位的任意距离函数 |
| 两类设置的交互 | 仅工装变、仅档位变、两者同时变 | 相加/重叠；等待时间混入设置 | 没有联合观察却要求准确推断联合开销 |
| 批量与时间 | 同设置不同批量、容量以内与跨容量；可见批次及加工段 | 逐件线性/逐批固定；设置重复计入加工 | 未受证据约束的远端数量范围 |
| 设置能否复用 | 连续同设置的分单、合批和中途切换后恢复 | 每订单重复收取设置；单纯 ID 相关 | 新资源上的复用规律 |
| 交期与等待取舍 | 规律已覆盖后，改变公开交期/释放时间形成行动反转 | 永远合批、永远先紧急、永远先同类 | 未知需求到达过程或新故障机制 |

为了使联合观察可执行，允许正常的授权试加工/历史作业证据；其可得性须在业务契约中说明。不能假设每种学习方法都会主动执行作者心中的探针，然后把缺失证据归咎于模型。

维护侧应区分：**环境可供获得的证据足够**，与**某一次方法运行实际获得的证据足够**。若正常训练总不能到达关键对照，应修订训练机会或提供同等授权的历史记录；若某方法在充分机会下未探索到，则可作为方法行为诊断，不能声称它已经收到完整证据却不会学习。

#### 5.4 可辨识性的操作标准

以允许观察到的训练事实 E 为基础，维护侧列出若干业务上合理的候选模型 H，例如对称/非对称、相加/重叠、按件/按批。不要根据真实 Agent 的失败临时更换真规则。

保留能解释 E 的模型，检查其在拟测公共条件下的成功策略集合，包含正常查询、试探、恢复和观察后的分支执行。如果各模型之间不存在共同可成功的合法条件策略，则该条件尚未被证据支持，必须补区分证据或移出“应掌握后成功”的范围。反之，即使没有共同的静态预排顺序，只要通过允许观察后分支执行即可稳健成功，就应承认在线适应足够，不必强求识别唯一参数，也不能为制造跨任务学习需求限制该策略。

这只能证明声明的合理模型范围内的**决策可辨识性**，不能证明排除一切数学函数。模型范围本身也要接受业务审查，不能为了宣布唯一解而删去明显竞争解释。若模型范围包含真正随机噪声，需要另行处理不确定性；首版不引入该扩展。

**本轮状态：已列检查项，未实现枚举器、生成训练证据或完成可辨识性机器验证。** 第 5.2 节的算例只检验固定排序的局限。

### 6. 捷径审查与迁移设计

#### 6.1 不把正确的简单办法当作失败

| 检查 | 如果成立，如何处理 |
|---|---|
| 工具直接返回准确预测/报价/义务，或能生成成功计划 | 保留接口；若学习不再影响 S/C，则降为执行锚点 |
| 一个固定合法动作模板覆盖全部条件 | 降低学习机制优先级，不增加秘密例外封堵 |
| 同一 episode 内低成本试探与恢复足以解决 | 承认在线适应有效；不能虚构不可撤销或硬性次数上限 |
| 学到少量特征规则后可迁移到大量新任务 | **这是期望的学习成果**；检查规则的适用边界和真实迁移，不强制要求多轮才算难 |
| 只减少步骤/改善预测，而最终 S/C 不变 | 可作内部诊断，不能声称核心任务能力改善 |
| 只有隐藏授权、窄时间陷阱或不可靠评分才能让它失败 | 否决当前设计 |

对 S-A，未来需实际检查最早交期、设置优先、合批优先、保守计划、正常恢复和合法预测服务。纸面上给某个策略一个反例，不等于整个机制具有区分能力；真实 Agent 可能自发结合多个启发式。

#### 6.2 留出必须改变决策条件

| 迁移类型 | S-A 的拟议形式 | 判读 |
|---|---|---|
| 无关变化 | 新订单 ID、文本顺序、无关描述 | 应保持结果；只覆盖此项不算充分泛化 |
| 数量与边界 | 已知容量附近的新数量，同规则下不同批数组合 | 需要训练支持相关关系与精度，不要求猜未知阈值 |
| 因果条件翻转 | 改交期、初始设置或释放时间，让成功顺序变化 | 识别是否记住固定动作模板 |
| 组合迁移 | 已分别学到且交互有证据的设置/数量/交期新组合 | 验证规律能用于未见业务条件；不能凭空测试新交互 |
| 近邻反例 | 其他事实接近，但一个相关条件导致原策略失效 | 检查案例近邻记忆与过度泛化 |
| 适用范围保持 | 加入不相关字段变化，其他已学规则仍成立 | 检查修复是否无端扩张、造成回归 |

开发时已看过的条件和所有本文算例均为 Dev 资产，不能改个名字作为最终盲测 Test。此阶段只设计留出原则；正式 Evolution、Monitor 与独立 Test 在任务体系经过验证后另行冻结。

同世界迁移保持规律稳定；若未来研究业务规则漂移，必须另建世界版本、明确发生变化并提供新的学习机会。不能在 Test 中偷偷改规则，再把旧 Skill 失败解释为泛化不足。

### 7. 下一阶段的最小推进与停止标准

保持流程简单，只推进 S-A，一个阶段只回答一个问题。

#### 7.1 实现前：补齐两项具体依据

1. **业务与工具核对。** 明确一种小批量作业流程，核对状态、设置、容量、可撤回范围、耗时日志和现有预测工具。官方资料已经支持一般结构；新资源未标定、交期量级和具体耗时仍是待核验假设。若只能获得通用资料，后续应明确标作合成机制可行性实验，不能宣称业务代表性已获认证。
2. **证据覆盖与可执行性核对。** 按第 5.3 节列训练证据机会与拟留出条件，检查竞争解释。任何目标在真规则下都应有公开权限内的成功路径；接受所有成功路径，不要求唯一最优。区分纸面覆盖、环境实现核验与真实 Agent 表现，不能相互代替。

这两项是选中原型的落地条件，不是新增大规模调研项目。发现合法捷径已经覆盖核心范围时就停止，不继续为候选叠加限制。

#### 7.2 单原型工程核验：以后做，本轮不做

只实现独立 S-A 环境与 S 评价，不改 LS1/LG1 或现有运行结果。核验时间推进、批量与完成状态、正常取消/恢复、反馈来源、参考成功路径、上述简单策略以及可辨识性。训练与开发留出调用同一评价函数。

模型前检查应先排除“任务本来无解”“日志不能支持拟测决策”“捷径基线偷看私有状态”“准确查询已经解题”等问题。维护侧可用真规则求解，证明任务有可行路径；这个参考求解器不算无经验策略或真实 Agent 成绩。检查无经验捷径的基线则只能用公开信息和合法工具，两者分开。环境输入只暴露公开投影，不向执行模型开放维护侧公式或本文件；保护旧目录。工程检查不是新增最终指标。

#### 7.3 最小真实学习校准：以后做，本轮不调用

继续只用 `deepseek-v4-flash`。主比较为 S0 与按真实 Train 执行、反馈更新得到的 Skill，在同一份独立开发留出条件上比较；不强制四种经验条件，不先指定必须产生 S2。训练证据覆盖与预算先确定，不能机械复制 LG1 的“每轮两例”。

Skill 更新器只接收当前 Skill 和允许的 Train 轨迹/反馈，不能接收 Dev Monitor 的轨迹、分数、维护侧规则或最终 Test。Monitor 每题重置环境、使用冻结 Skill，不跨题积累经验；正常工具观察仍保留。研究者看过用于筛选的 Monitor 就承认其开发属性。更新方法属于被测方法，不写进 Benchmark 的业务定义。

Oracle 仅在归因不清时作为可选诊断：若给定完整规律仍无法完成，需区分执行困难与工程错误；若 Oracle 成功、学习后失败，不能直接认定机制不可学习，还应检查方法实际获得的证据和更新质量。额外模型调用须另行固定范围，不在本轮发生。

| 后续证据 | 决定 |
|---|---|
| S0 与合法简单策略已覆盖主要留出条件 | 降为基础执行/排程锚点；不通过加秘密规则救难度 |
| S0 存在由知识缺口导致的错误，允许反馈可区分，学习后在未见条件上改善并通过反转检查 | 保留学习型 S 候选；小试仅是继续验证依据，不立即宣布正式准入 |
| 有充分证据机会但方法没学会，完整规则下可成功 | 记录方法学习/探索不足，有限诊断；不能自动怪 Benchmark，也不反复调 Skill 直到赢 |
| 相容规则仍要求冲突动作、合法成功路径缺失、工具语义或评价错误 | 退回环境/证据设计，版本化修正，不计为有效业务失败 |
| 改善只在见过案例、换 ID 或规则复述中出现 | 不认定迁移学习收益 |
| 固定预算内发生 length 截断，轨迹与终态仍可评分 | 保留任务结果并附截断诊断，不能仅因截断改成缺测；不把它作为业务规则困难的证据 |
| 连接等错误导致状态或轨迹不可核验 | 按冻结协议列缺测/工程无效，保留原记录，不补造业务分数 |
| 供应方超过请求额度 | 单列预算不一致，不能直接用于同预算收益结论 |

模型预算、样本数和重复安排在单原型通过离线检查后预先冻结。中断后是否继续更新按相应冻结协议执行，本文不改变既有停止策略。本轮不凭空给出“必须低于某成功率才算难”的阈值，也不提出大规模模型矩阵。小样本报告配对结果和具体错误来源，不宣称统计显著性或跨模型排名。

正式准入还需证明：业务与信息边界合理、可学习的证据充分、真实终态 S/C 受学习影响、在未见条件与反例中成立、工程可复现。S/G 有可靠证据后再研究 I 的独立不足与 K 的修复副作用；不把一个排程任务和一个凭证任务拼接就宣布有双维学习价值。

### 3. 仍值得保留的行为线索，以及反证

#### 3.1 已知有两项需求，仍先消耗共享资金

闭环 T020 / JRA-C04：Parent 一开始获得两张票的完整条件，使用证书支付 Economy 188、礼品卡支付 Basic 224，全部完成。Candidate 的用户先说明“需要两张”，但只逐步提供第一张信息；Agent 未先收集第二张需求，在 m9 提出 certificate 100 + gift 88 示例，m11 采用该分配，m13 写入。用户此前只指定允许的两种资金，没有要求 100/88 分拆。第二张票披露后，礼品卡只余 182，无法支付 224，证书已消耗，用户不允许新增卡支付。[H43/H44]

**可观察问题**是全局需求尚未收齐就作出资金承诺。**限制**是披露节奏不同，且舱位支付接受规则并未由公开工具说明完整给出，不能作为同条件 Skill 因果退化。新候选必须允许询问第二项并如实返回，不要求 Agent 猜测尚未披露的金额。

反证：r1 P4-C05/C06 两侧均完成 88/176 的两票分配；r1 JRA-C05 Candidate 也正确执行 gift→Basic、certificate→Economy。简单两项分配很可能被一条规则覆盖，不值得原样扩成一批高难题。[H01/H07/H10/H16、H03]

#### 3.2 把条件选择的比较对象换错，或把条件视为循环

闭环 T003 / EE-C03：保留段 300，原总价 400；首选新段 260，完整方案 560、加价 160；后备新段 200，完整方案 500、加价 100。Parent m15 用两个候选之间的价差 60 代替相对原订单的加价，随后订首选。**但用户 m16 明确同意了 560 / +160 的首选方案，旧评分仍要求后备。** 原始“complete revised itinerary”也没明确先计算哪个候选，且价格基准隐藏。因此能保留“比较基准替换”的观察，不能直接把本次终局失败当作纯 Agent 失误。[H33/H34]

闭环 T022 / JSG-C03：两侧都算出了首选 +160、后备 +90；Parent 按阈值 100 选后备并获确认，Candidate 认为条件循环、要求用户直接选航班，最终转交。两侧 C 都通过。这里的线索是条件决策和授权边界，不是已观察到的 S/C 冲突；语言歧义仍须先消除。[H45/H46]

#### 3.3 单个写入都正确，组合终态仍被覆盖

RAP-C02（闭环 T030）、r4 RAP-C05/C08 中，订单临时地址和用户默认地址要求不同，Agent 分别传入正确写参数，但先改订单、后改 profile 导致订单地址被联动覆盖。[H23/H24/H28/H29/H47/H48]

原 [地址工具](../../../src/benchmark_v3/development/retail_address_propagation/environment/tools.py) 只公开 contract label，不公开传播方向；每个目标仅可写一次，两次后关闭会话，阻止正常修复。故“跨对象副作用”值得保留，而“猜标签映射、一次猜错永久失败”不能直接带入 v5。T030 Parent 曾把确认文本的 Court 写成 Street，但用户纠正后实际参数正确，不是该终态失败的原因。

#### 3.4 公开契约下出现过操作身份错误，但 Agent 已自行恢复

Flash 在 S2 variant 主实验中先用 OP-1 退货，再以同一 OP-1 换货，被工具拒绝不同 payload；查询后新建 OP-2，换货超时后查到已提交，最终 S=true。它确实把两个业务操作误当成同一操作，但纠正路径有效。[V01 e6—13]

此例保留为执行稳健性诊断。当前工具说明已经直接提示超时查询、不要换新 ID；其他饱和原型也有清晰的动作提示。长流程不自动意味着复杂决策；不能把一个恢复成功的错误扩写成“未知提交普遍很难”。

### 4. 为什么一轮 Skill 修改可能解决很多任务

[首轮 Candidate Skill](../../../artifacts/methods/v18/formal/v18_v4_formal_002/round-01/monitor_private/backend/candidate_skill.md) 可直接看到：gift→Basic / certificate→Economy、证书单次使用、写后重查余额、按 Horizon/Summit 选价格基准、每单最多五人等少量映射。它们补入的信息在多个实例中复用。因而至少有三种解释同时存在：

1. **补齐知识而非增加推理能力。** 政策、工具没有公开的规则由历史经验补回，许多任务只剩套用该映射。
2. **决策结构同质。** 更换旅客、日期、金额后，关键分支和动作模板仍相同；P4 成功对照表明不是所有金额分配都存在困难。
3. **成功判定集中于固定程序。** GIR/JRA 的取消阶段可由核实后的转交完成，补上规定检查可能提升 S；不能称为实际取消能力提升。

但四轮的原始 S 是 34→35、35→39、40→39、39→39（每侧 45），并非所有任务首轮解决。闭环实验 S 27→23、C 34→35，其中七个 S 退化对含上述漂移、停止和歧义。**能确认某些映射容易覆盖多题，不能确认整个 v4 过于简单，也不能把剩余失败全部算作业务困难。**

### 5. 四个候选决策点

以下 D 编号仅是候选清单，不是新增任务 ID，不改变 S1/G1 等既有原型编号。条件变化是拟议的决策对照，尚未生成数据或验证实现。每个候选先公开全部规则和可查询事实；Agent 可自主检索、询问和选择等价合法路径。

#### D1 — 在多项购买承诺前规划共享资金（S，优先）

- **证据与问题：** H44 的局部 100/88 分配造成第二项无资金。要验证的是“知道还有需求时，能否先补齐约束并规划全部承诺”，不是记住证书给哪一舱。
- **目标与可见信息：** 完成两项必要预订，只用允许资金。公开证书适用范围、一次使用/余额处理、礼品卡余额与退款恢复语义；用户首轮说明有两项，主动询问可获得两项全部事实。对照条件首轮直接给全，不允许用户拒绝提供必需信息。
- **决策与事实组合：** 立即处理第一项，或先询问第二项；资金分配须同时考虑两项金额、支付接受范围、一次性消耗、共享余额及“都要完成”的目标。前者对单张票可行，却可能破坏整体可行性。
- **可执行合法路径：** 收齐需求→读余额与适用规则→计算联合可行分配→确认两项方案→逐项办理并读回余额。以历史金额为诊断锚点：证书 320 支付 Economy 188，礼品卡 270 支付 Basic 224，保留 46。不额外加取消任务或焦点合规规则。
- **有意义的变化：** 保持请求顺序，交换两项的舱位接受条件，合法资金去向随之翻转；另设两项均可用证书、较大额必须由证书覆盖的条件，检查“证书永远给第一项/某舱位”是否失效。每个条件先证明存在合法分配，不用无解资金约束诱导失败。
- **评价与预期证据：** S 检查两项、金额、旅客和资金边界；C=N/A。记录首次资金写入时第二项需求是否已知、所选分配是否保留整体可行性。询问次数不直接扣分，正常追问不是失败。
- **进入试跑前：** 支付规则查询必须齐全；询问同一事实得到同一答复；披露顺序以明确定义的条件变化呈现。若清晰契约下顺利完成，D1 降为基础/中等规划锚点，不继续堆购买数量制造难度。

#### D2 — 用指定首选方案的完整报价触发后备分支（S，优先）

- **证据与问题：** H33 的比较对象替换，H46 的循环解释。当前不能区分是条件推理弱，还是语言/隐藏结算契约导致的合理犹豫；试跑应回答这个问题。
- **目标与可见信息：** 保留指定前段；“先计算首选 P 相对原订单的完整加价；若 P 加价 ≤ 阈值则选 P，否则选明确后备 F”。公开保留段定价、原支付、候选价格及费用组成，或提供可读取的完整报价。用户授权该确定条件，后备的金额上限也明确且可行。
- **决策与事实组合：** 原订单基准、保留段、替换段与必要费用共同决定 P 的加价；不能比较 P/F 差价，也不能用 F 的低价反过来否定触发条件。仍由 Agent 决定条件分支，而非用户直接报正确选项。
- **可执行合法路径：** 查原单和公开结算依据→分别形成 P/F 完整报价→仅以 P 对原单的加价触发分支→核对后备约束→确认并更新→读回。历史示例 P +160、F +100、阈值 150，应选 F。
- **有意义的变化：** 仅改变 P 报价使其从阈值外进入阈值内；选择必须 F→P。另用“直接提供完整报价 / 提供公开费用组成”区分条件选择和结算组合，不能把多个因素同时改变后声称定位了根因。
- **评价与预期证据：** S 检查保留段、正确分支、完整费用和最终状态；C=N/A。若用户明确变更目标，应形成新条件并同步评分，不能允许用户批准任意分支却仍按隐藏旧答案评分。
- **进入试跑前：** 用非模型人工推演证明请求无自指、金额定义唯一、正常询问能澄清。清晰表达后饱和，即确认旧困难主要来自契约歧义；不再人为改回模糊措辞。

#### D3 — 根据适用事实分别完成取消、拒绝或必要转交（独立 G，有条件准备）

- **证据与问题：** H06/H09 暴露“覆盖未知时停止办理”；H35—H38 暴露拒绝与转交终态的不一致；G2 现有校准饱和。尚无可靠证据证明**公开完整规则下**此方向已经困难，D3 是用于排除知识缺失解释的候选。
- **目标与可见信息：** 处理同一客户两笔简单取消请求，逐单给出最终处理。公开适用保单版本、覆盖原因、取消窗口、航班状态、所需证明、何时必须/可以转交。规则及证明有合法入口；用户陈述、证明和订单之间可能需要绑定，但不隐藏原因映射。
- **决策与事实组合：** 各单直接取消、补查证据、拒绝直退、必要转交；必须组合购买时版本、取消原因、客观状态和证据对象。不得由“都有保险”一律退，也不得由“其中一单不满足”一律停。业务优化保持简单，难度来源于程序适用和义务推进。
- **可执行合法路径：** 逐单确定版本和资格→证据足够且满足取消条件的，确认后办理→其他订单明确不得直退的依据，并按规则及用户意愿完成拒绝或转交。若等待补证是合法终态，事先写入契约，且不把可立即办妥的另一单也搁置。
- **有意义的变化：** 将一单从不覆盖原因改为有已验证证明的覆盖原因，其他条件不变，合法处置应从不直退变为可取消；将同一份证明的关联订单改为另一笔，应先取得匹配证明。不是换同义词或只增加一条也合法的路径。
- **评价与预期证据：** S 是逐单达到预先规定的服务终态；C 检查资格、授权及禁止行为；P_complete 检查适用证据核验、必要通知/转交。完整办理看 S∧C∧P_complete。不作为复杂 S，不因为观察到拒绝就归 K；必要义务集合不能随 Agent 错选分支而缩小。
- **进入试跑前：** 先闭合取消/拒绝/转交目标与用户停止条件，公开政策不再把核心规则称为不可访问的 internal contract。保险版本、证明要求是拟议机制，需业务依据核验，不能把合成规则当作真实保单。若只能靠隐藏规则或增加等待才能出现困难，停止此候选。

#### D4 — 维护临时订单地址与长期默认地址的不同终态（S，后备）

- **证据与问题：** H47/H48 等已出现组合写入的终态覆盖。但传播方向隐藏、一次写限制足以解释失败；先验证公开副作用后是否仍有规划困难。
- **目标与可见信息：** 当前订单寄临时地址，后续订单使用长期地址；公开每个修改接口对现有订单的影响、订单是否同步默认地址、是否仍可修改。读取传播规则不应返回无法解释的代码标签。
- **决策与事实组合：** 先改默认地址再设当前订单例外，或反向写入后复核修复；结合目标对象、同步关系和最新状态。正常可恢复环境中，两条路径都可成功，不能为了分出高低只允许唯一写序。
- **可执行合法路径：** 读取影响范围→确认两个不同目标→更新默认值及当前订单例外→同时读回两对象；若副作用覆盖了一个对象，允许再次修正。移除人为“一对象只能写一次、两写强制关闭”。
- **有意义的变化：** 同步订单与独立地址快照订单具有不同副作用；终态目标不变，但是否需要修正不同。这是操作依赖变化，**不保证最优顺序必然翻转**，不能把始终安全的通用顺序判错。
- **评价与预期证据：** S 检查两个地址及非目标对象；C=N/A。记录有没有漏查终态和是否成功恢复，写入次数仅作诊断。若“写后读回”就稳定解决，应保留为恢复基础题，不继续堆对象数。
- **进入试跑前：** 先确认该同步行为有可信业务依据，工具清晰公开且可修复。开发成本高于 D1/D2，暂不安排首批。

- **G2 未开封变体：不再视为强制切换分支的证据。** 它增加 ordinary 合法选项，但 wrong_shipment 仍成立。Flash 选 ordinary 并补取审批，原公开 `senior_above_cents` 又未限定审批只用于例外，不能直接把额外审批判作过度保守。[V02]
- **I1 变体：确有决策变化，但没有显现困难。** A 到达由 720 变 800，Flash 改选 C，并正确获得支付授权；保留为条件判断锚点。[V03]
- **K2：保留接手恢复的分类谱系，但复杂关联冲突尚无实证。** Flash 查得 B 未提交就只新增 C；该任务是初态已知的新目标，不是执行中动态变更。[V04]

### 7. 小规模验证的判读约束

后续使用 `deepseek-v4-flash`，不恢复三模型筛选，也不做模型能力排名。可先按每个进入候选的清晰基线和一个决策变化各执行 3 次；这是定位行为的工程小试建议，不是本轮已冻结的实验协议或统计准入阈值。

试跑前必须完成目标—模拟用户—公开信息—工具终态—评分的一致性检查，并记录一个合法完成路径。允许正常检索和必要追问；不能通过删除关键规则、不给可得事实、强制用户拒答、压低预算或制造无解状态获得失败率。执行预算沿用已验证无截断的配置作为起点，并继续检查供应方实际返回 usage；如再次截断，单列测量问题，不把它记为业务难点证据。

结果按以下方式决定是否继续：

- **一致通过，且解释符合条件变化：** 降为基础/中等锚点或停止扩展。可能被通用方法正确解决，本身不是 Benchmark 缺陷。
- **发生可解释错误，但能恢复完成：** 记录恢复能力与中间错误，不虚增终局失败；判断是否值得保留诊断。
- **规则可见仍反复在同一业务决策点失败：** 才值得增加少量独立条件检验，而非马上改 Skill 或复制大量同模板任务。
- **仅在歧义、缺失信息、提前停止、回执字段或输出截断上失败：** 修正测量，保留修订前结果；不将此作为复杂题准入证据。

待 Dev 候选稳定后再冻结未参与选择的条件组合和独立 Test。当前只有一个模型的小试只能说明该 Agent 在这些条件下遇到什么困难，不能证明跨能力 Agent 的总体区分度。外部业务真实性、独立 Test 泛化和最终难度梯度仍是后续独立验证项。
