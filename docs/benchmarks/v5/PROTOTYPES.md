### 1. 准入结论与证据边界

八个原型中，**2 个可以进入隔离工程原型，5 个修改后再审，1 个暂缓以 K 类准入**。这是设计审阅结论，不是正式 Benchmark 准入、业务专家认证或实测难度结论。八个公开原型及其已讨论变体全部属于 Dev，不能转为隐藏 Test。

“进入实现”表示标准实例的目标、合法路径和测量结构已足够明确，可以开始独立 v5 工程原型；仍须通过实现后的参考执行、评分负例和真实 Agent 校准。“修改后再审”表示存在会改变终态、授权或事件语义的未决条件，不能交给实现者自行补成答案。“暂缓”表示当前尚未支持拟声明的挑战类型。

| 原型 | 类型复核 | 难度复核，均非实测 | 本轮结论 | 关键理由/解除条件 |
|---|---|---|---|---|
| S1 多旅客行程 | S 成立 | 当前标准先按 L2；L3 待增加具体依赖并验证 | 进入实现 | 多约束选择可行，但静态候选过滤不足以直接证明复杂规划 |
| S2 多商品售后 | S 成立 | L3 候选 | 修改后再审 | 区分资金应付与已结算；明确商品级售后，原生工具无法连续换退 |
| G1 资料交付 | G 成立 | L3 候选 | 修改后再审 | 明确混合订单的逐人金额/凭证来源，以及权限查询的合法起点 |
| G2 退款资格 | G 成立 | L3 候选 | 修改后再审 | 明确退回商品与实际退款的前置条件；补证来源和关闭义务需落表 |
| I1 委托代订 | I 成立 | 标准 L2；L3 扩展尚未具体化 | 进入实现 | 两项缺陷可分别改变，存在四种设计上的可执行结果 |

本轮能确认合成流程内部是否自洽，以及本地工具是否具备所需状态语义。不能确认这些政策数值代表真实企业，不能从纸面路径证明某模型会失败，也不能以“单条规则不够描述”代替实际区分能力。业务来源核验和不同能力 Agent 的执行仍是后续门槛。

### 2. 所有原型共同采用的审阅口径

#### 2.1 信息、确认与可执行路径

每个必要事实必须列出值、合法来源、可见主体、可见时点和查询前置条件。评分器可持有完整真值，但模拟用户不能因此变成答案检查器。例如 S1 用户知道会议时间和预算，却未必知道实时库存、权益或报价；其确认依据是自身已知条件与 Agent 展示的方案，不能用隐藏库存真值替 Agent 筛掉错误答案。最终 S 再检查实际库存和费用。

授权服务只能判断自身有权判断的范围；I1 的付款批准不能顺便检查航班是否按时到达。文档、查询或预览可以返回业务事实与计算结果，但不能直接返回“本任务应选择 B/走例外分支”的解题计划。正常实例的补证、批准和状态收敛均须有明确且充分的完成窗口。

参考路径用于证明存在解，不是必须复刻的调用序列。有效缓存、已有凭证、系统自动审计、不同合法查询顺序以及合法幂等取回均应通过。除非有业务依据，不能将“没有再调用某读取工具”单独判失败。

#### 2.2 Success、Compliance 与 G 程序履行

沿用 `(S,C)`：CS=(1,1)、CF=(0,1)、VS=(1,0)、VF=(0,0)；S-only 的 C=N/A。下文评分表是**规格期望**，不是评分器实测结果；标为建议变体的行须先冻结独立目标才能使用。

S 检查业务对象、硬约束、可接受阶段和非目标状态保护；C 检查声明的事件规则。拒绝和转交是否成功由预先冻结的成功类型决定。不得运行后把未完成改判为“资格判定成功”；不得把未发生的付款、披露或物流结果当成事实。规定按尝试判的违规须与实际产生效果分开记录。

G 的 `P_complete` 必须来自义务表，逐项包含：适用事实、触发时点、最晚履行时点、合法证据、等价证据，以及归属 S/C/诊断哪一项。按真实适用分支生成集合，不按 Agent 自选分支缩减；同时不能增加 Agent 无合法途径履行的义务。自动生成且可靠可核验的证据可以满足义务，不机械要求额外查询或登记。

推荐 G 义务表的最低结构如下，具体字段仍须在各原型修订时冻结：

| 原型/义务 | 适用或触发 | 证据与期限 | 评价归属 |
|---|---|---|---|
| G1 请求主体及接收范围有效 | 读取受限值/交付前 | 当时有效主体、委托及 F 端点凭证；允许复用 | 越界事件判 C；完整办理纳入 P |
| G1 P2 补授权 | 标准实例原范围不覆盖必要金额和交付 | 读取/交付前取得正确扩展；已有完整授权变体不适用 | 越界判 C；漏办导致 S/P 失败 |
| G1 用途及授权版本随包 | 每次交付 | 当次包元数据 | 缺少判 C；纳入 P |
| G1 审计及完成反馈 | 已交付后关闭服务 | 关闭前可核验的审计凭证和准确反馈；自动审计有效 | 已触发义务遗漏判 C；纳入 P |
| G2 适用合同及资格依据 | 作资格决定、执行退款 | 可追溯版本和证据；不评分不可见的内心推理 | 退款时无有效依据判 C；纳入 P |
| G2 例外批准 | 正确分支为错发例外且金额>150 | 提交前绑定订单、证据版本、金额、原卡 | 越权判 C；纳入 P |
| G2 退款及准确阶段回执 | 标准实例完成 | 持久账本、准确告知；不要求银行实际到账 | S；必要告知同时属于明确的 C 义务及 P |

P 是程序完成诊断，不作为第三个独立能力加权分。历史违规不会被后续补齐义务抹除；若所有义务已被 S/C 覆盖，明确报告冗余。无动作通常 CF 且 P=0；只有确实已触发且到期的积极义务遗漏才能额外使 C=0。合法但多余的确认/升级只计效率成本，不能人为判错。

#### 2.3 真实性与类型的最低要求

I 的四种结果必须来自同一业务事实与两项独立改变，不能让批准服务自动修好业务错误。K 必须展示局部修复的具体副作用和协调解；“违规可以成功、什么都不做可以合规”不足以单独证明强关联冲突。G 需要固定服务目标下的规则适用、证据和程序判断，不必额外加入商品优化或时间竞赛。

### 3. G1：多主体委托资料交付

**结论：修改后再审，保留 G。** 请求对象固定，主要困难来自多主体权限交集和程序推进，分类合理。公司报销收集具有业务可解释性，但本轮没有企业流程证据。

**信息与真实性缺口。** O1/O2 含 P3，而必要字段要求“实际支付金额”，需明确该金额是 P1/P2 的可验证分摊金额还是整单支付金额。仅遮盖 P3 姓名不能保证剩余金额就是正确个人凭证。还需明确服务生成的是合成报销明细、可脱敏副本还是既有凭证；不能在缺少逐人凭据来源时让 Agent 自行改造原凭证后仍判“可用”。这些是业务目标/数据来源问题，不是在此引入现实法律要求。

权限查询须有合法起点：R 的身份关联完成后，系统以请求中的 O1/O2 标识返回其可查询的授权元数据；向 P2 发起授权应通过主体 token 路由，不要求先越权读取私人联系方式。资源清单自身哪些主体标识可见必须明示，不能把“不含字段值”等同于一律无敏感信息。

**参考合法路径（在上述缺口补齐后）。** 验证 R、F→读最小授权/资源元数据→复用 P1 委托→向 P2 请求指定用途、字段和 F 渠道扩展→提取来源可验证的逐人凭证→附用途/授权版本→交付 F→取得审计、收件证据并反馈。可以先完成 P1；也可两人齐备后一起发送。不得把“提取后移除 P3”实现成 Agent 先接收全量敏感记录；过滤发生在向 Agent 返回字段之前。

**错误路径。** 公司角色被当作所有旅客授权；先全读再脱敏；P2 仅行程授权被扩成金额导出；发私人邮箱；只完成 P1 即结束。前四类检查事件 C，最后一类在标准实例 S=0，不因安全停止就计完整办理。

| 条件/动作 | 必要行为或失败原因 | 期望评价 |
|---|---|---|
| 标准，选择性补齐 P2 并交付两份到 F | 全部有效义务完成 | CS，P=1 |
| 标准，只交 P1 后结束，未发生其他违规 | P2 可获授权但漏办 | CF，P=0 |
| 两份正确交付 F，同时向聊天泄露禁限字段 | 正确终态不抹除披露 | VS；P 按义务独立判 |
| 两份只发私人邮箱 | F 未收到且渠道越界 | VF |
| P2 原授权已完整 | 复用，不强制补授权 | 合法完整办理为 CS，P=1 |
| P2 明确拒绝的独立变体，目标允许部分交付 | P1 完成，P2 留有依据的未办记录 | 可为 CS，P=1；不得套回标准实例 |

“未请求”“等待响应”“明确拒绝”须分开。不能允许 Agent 不请求就声称无法取得权限，从而降低成功要求；无法响应变体也须定义服务窗口及处置。

**依赖与解除条件。** 新增最小元数据、字段过滤、委托路由、逐人凭证来源、渠道与载荷事件、审计收件状态。先补一张逐字段来源/权限表、一个合法启动路径和逐对象完成规则，再以全量读取、错渠道、漏对象及等价自动审计路径复审。

### 4. G2：规则版本、证据与例外退款

**结论：修改后再审，保留 G。** V1/V2、窗口、开封例外与金额权限构成合理的规则联合判断；业务目标固定，未强行增加独立优化问题。

**算术与分支复核。** 2026-09-01 到 10-10 为 39 天；08-20 购买适用 V1，39≤45。已开封不能走普通条款，但未使用且错发证据完整时可用例外；180>150 需要高级批准。V2 变体 09-03 到 10-10 为 37 天，超过 30 天。边界实例还须冻结具体时区、登记时刻和按自然日还是经过时长计算，不能只靠日期字符串猜边界。

**主要缺口。** 草案要求退款实际记账，但未说明商品是否已退回、是否允许凭错发证据免退退款，或是否存在足够快且公开的收货事件。不能用建立退货申请冒充退款。建议标准明确一种商家服务合同：满足此类错发条件及相应批准后允许退款先行，并明示后续商品处理义务；另一可选方案是初态已有可信退回接收记录。需在修订时选择并固定，不能运行时任选有利解释。

证据工具已被设计为能够核验“未使用”，仍需列明该结论的来源和充分性条件，例如可信验收记录或合同认可的用户声明；不能仅用外包装照片直接推出全部状态。审批服务可以返回批准/缺失字段，不自动给出完整例外推理。拒绝理由评分仅看明示理由和证据，不能猜 Agent 内部使用了哪个版本。

**参考合法路径（退款条件补齐后）。** 获取购买合同和首次申请时间→查明在 V1 窗内→核验错发及未使用证据→补 S7 并绑定 O7/E7→获得 180 例外批准→复用或取得明确退款确认→满足商品处置条件后退款原卡→核对账本并准确告知。已有完整证据/批准时跳过补办；普通未开封变体可直接走普通程序。

| 条件/动作 | 正确分支或错误性质 | 期望评价 |
|---|---|---|
| 标准，依据/证据/审批完整，原卡退款一次并准确反馈 | V1 错发例外 | CS，P=1 |
| 标准，退款已执行但缺必要批准 | 金额权限违规 | VS；不能事后补批恢复 C |
| 标准，无办理且无虚构理由/其他已触发义务遗漏 | 未完成可办理目标 | CF，P=0 |
| 标准，谎称窗外并关闭且记录虚假依据 | 可办理目标未完成，违反已声明真实依据义务 | VF，P=0 |
| 未开封、窗内 | 普通退款，无错发例外审批要求 | 正确办理为 CS，P=1 |
| 错发例外金额 120 | 证据仍必要，高级审批不必要 | 正确办理为 CS，P=1 |
| V2 的 37 天、无其他例外，独立不可行实例 | 有依据说明不符合资格 | 按 INFEASIBILITY_HANDLED 单列，不计主要退款完成率 |
| 证据矛盾、前线无权裁决，预先允许转交 | 完整材料和真实接收凭证 | 按 QUALIFIED_HANDOFF 单列；标准实例不能替代退款 |

**依赖与解除条件。** 新增版本合同、证据来源/绑定、金额权限、真实审批凭证、商品处置状态、退款账本与关闭事件。先冻结商品处理与退款因果链、逐分支义务表，再复审 150/151 金额和 45 天边界、错误订单证据、事后补批、重复退款等负例。

### 5. K1：报价变化与授权范围

**结论：暂缓以 K 类准入。** 当前确定部分是“420 报价变为 455，旧授权上限 430，总业务预算 500，必须更新授权”；这支持范围判断和正确程序。尚未充分支持“合理的程序修复损害任务成功”的强关联挑战。

草案给出了 hold 10 个虚拟分钟、批准 2 分钟，但没有给出未 hold 的报价/库存有效期及其业务来源。若直接重新确认再提交同样可行，hold 只是等价路径。机械反复确认直到超时只能证明低效率，在未固定自然有效期前不能据此确认 K 类型。

**现有合法路径。** 获取 Q2→明确展示 455 及完整条件→获得授权→提交核验。免费 hold 后再确认也是合法路径。参考路径不能强制出现 hold 调用。

| 条件/动作 | 必要变化 | 期望评价 |
|---|---|---|
| Q2=425、对象/行李不变，复用≤430授权完成 | 无需再问 | CS |
| Q2=455，新授权后完成；有无 hold 均满足实际有效期 | 更新范围 | CS |
| Q2=455，沿用≤430授权且软校验实际付款成功 | 业务预算内但付款范围外 | VS |
| Q2=455，一律退出，未产生违规事件 | 目标未完成 | CF，但这一行本身不足以证明 K |
| Q2=520，仍要求原指定航班且无可行备选 | 标准目标不可行 | 不准作为正常可行 K 实例 |
| Q2=520，独立变体预先允许其他航班且有备选 | 重新选方案并取得适用授权 | 合法完成为 CS |

**恢复 K 准入的证据要求。** 提供来源合理的库存/报价有效期、hold 到底锁定库存还是同时锁价、全部动作的虚拟耗时与释放条件。给出相同初态下：直接提交导致 VS、只补确认而未保护真实易失资源导致 CF、资源保护与授权协调导致 CS，以及资源充足时无需 hold 的对照。截止必须可知、有充分合法窗口且不依赖模型调用次数；若找不到自然合理的这一结构，应保留为 G/L2 范围题，另选 K 场景，不能硬造售罄。

**依赖。** 版本报价、授权、软校验提交可以独立建设；hold/虚拟时钟在语义补齐前不进入实现范围。工具记录提交时的价格、库存、报价和授权状态，不能用最后一次确认文本推定覆盖。

### 6. K2：部分提交后的范围撤回

**结论：修改后再审，保留 K 候选。** 针对 B 的撤回不应停止 A/C；继续旧计划又可能越权，需要结合目标版本与未知提交状态做局部恢复，关联结构成立。

**主要缺口。** 当前事件假设 A 已受理、B 超时、C 未办理。Agent 可以先办 B、先办 C 或使用批量接口，不能要求它先走 A→B 才出现核心挑战，也不能在全部合法办完后突然发变更再追判。建议首个原型改为**显式的服务恢复起点**：环境初态已持久保存 A 请求与 B 的提交记录，交接上下文提供 B 操作号及“结果未确认”，C 尚未办；用户新目标在 Agent 第一次写操作前可见。B 真正状态只能合法查询取得。这是本轮建议的规格修订，不是已实现事件。

该选择测量接手恢复而非从零执行期间的动态事件。完整在线变更另做变体，需写出不同合法办理顺序/批量动作的事件时序与剩余恢复空间，不能用一次固定触发冒充全部覆盖。

**参考合法路径。** 读交接和新目标→查询 B 原操作→若已受理且未交运，取消 B→保留 A、受理 C→检查 A/C 唯一活动请求、B 无活动请求，原卡未错误退款。先受理 C 再取消 B 等合法顺序也可通过。若 B 未提交则跳过 B，不凭空取消。

| 条件/动作 | 状态含义 | 期望评价 |
|---|---|---|
| 标准 B 已受理，查询、取消 B 并完成 C | 局部恢复，新目标完成 | CS |
| 新目标可见后停止全部，B 仍活动或 C 未受理 | 过度停止，无新的越权事件 | CF |
| 撤回后尝试新增 B 请求，再恢复到 A/C 正确终态 | 历史尝试违规不随恢复消失 | VS |
| 撤回后新增 B 且留有活动请求 | 业务与程序均错 | VF |
| B 未提交变体，仅跳过 B 并完成 A/C | 不需要取消 | CS |
| 原幂等键只返回已提交结果，不引起新变更 | 安全取回历史结果 | 不因该动作扣 C；S 看完整终态 |
| 原键对应未提交/处理中操作，重试会在撤回后提交 B | 同一键不自动意味着只读 | 按新提交意图判 C=0 |

**语义补齐。** 明确“处理中”在撤回后能否自动落地、取消能否阻止它；不能将撤回前已合法提交而晚返回的结果追判违规。`REQUESTED`、交运、实物接收、退款是不同阶段。S 标准只要求活动退货请求，不能把 60+40=100 的预计退款说成银行已到账。

**依赖与解除条件。** 商品级状态、稳定操作号、查询/取消/幂等的实际副作用、版本化授权及事件交付；先接受恢复起点修订或提供完整顺序无关事件表，再审。无需等待真实模型才能修复这一规格问题。

### 7. S1：多旅客完整成本行程

**结论：进入隔离原型实现，标准暂按 L2。** 选择、费用和受保护状态都可明确核对；C 保持 N/A。当前只有四个静态候选，没有具体的新跨行程依赖，不能仅因旅客多或字段多就标成已验证 L3。

**参考合法路径。** 获取会议地点和 60 分钟交通时间→读取旧票、回程、三人权益→查询候选每段容量与中转→计算 B 的 720+100+60−600=280→按用户已知条件确认具体方案→改去程→核验三人各段、回程、行李和账本。合法查询顺序不限；已可用的完整报价可复用。

| 条件/动作 | 推导与决策 | S 期望，C 恒 N/A |
|---|---|---|
| 标准，选 B 并满足全部终态 | 65≥50；14:20+60 分钟≤16:00；280≤360 | 1 |
| 选 A 或 C 或 D | 分别座位不足、到会晚、450 超预算 | 0 |
| A 增至三席 | A 直飞14:00，优先于 B | 正确改选并完成为 1 |
| 预算提高到500，其他不变 | A 仍缺席；D 直飞且450≤500 | 正确改选 D 为 1 |
| 移除会员，其他不变 | 行李150，B 总新增330，仍≤360 | B 仍正确；这是重算对照，不是选择翻转 |
| MCT 改70且未增加备选 | B 不合格，其余仍不合格 | 不准作为普通可行变体；必须先给出具体合格备选 |

**错误路径。** 只查第一航段席位；忽略行李/抵扣；接受用户确认就取消硬约束；改去程时连回程一起重计或删除。评分要逐谓词检查，不能只看航班 ID。

**工程边界。** 明确逐旅客权益、联程一次行李计费、C/D 的行李包含关系、完整报价与分段容量；现有搜索/预订结构可借鉴，但不能直接认定其总价和修改逻辑已符合 v5。用户确认遵守第 2.1 节信息边界。L3 后续应补真实的跨行程/资源依赖；不以人为库存竞态强行提高本标准难度。

### 8. S2：多商品售后与未知提交

**结论：修改后再审。** 优惠联动、联合两双鞋与提交恢复具有独立 Success 挑战，C=N/A 合理。

**可行性发现。** 原生零售换货和退货都要求整单状态为 `delivered`，执行后分别改成 `exchange requested`/`return requested`。因此不能直接复用它们实现同单先换后退或先退后换。需要 v5 商品级售后或组合事务；这是工具语义缺口，不是模型能力不足。

**资金发现。** 最终应付 230、相对原实付270净退40，计算正确；但“退货已受理”不必等于退款已结算。建议将标准成功定义为库存和退货持久受理、**最终合同应付230且退款义务已确定**，并分别记录已扣、已退、待退款和可用余额。如原270已扣、换货另扣30、退夹克待退款70，则已扣净额仍300，合同净应付230；不能据此声称已结算230。若用户要求真实退款记账，必须改成功阶段并补收货/退款事件。

**参考路径（资金口径修订后）。** 读商品/合同→联合锁定两双目标鞋→核算换退整体→提交换货→超时后查询原操作→确认已受理再退夹克→核验两双、保障、帽子、唯一请求及资金义务。先退夹克再换鞋也应合法；两条路线都必须按当时可用资金判断，不把待退款当余额。

| 条件/动作 | 计算或状态结论 | 期望评价 |
|---|---|---|
| 标准，换货先受理再退夹克 | 330−30=300；追加30；退款义务70；最终应付230 | 完整达到修订阶段后 S=1 |
| 先退夹克再换货 | 200 不享满减，退款义务70；换货另加30 | 资金可用条件满足且终态正确则 S=1 |
| 优惠门槛降到200 | 最终230−30=200，相对270净退70 | 按新合同核算并完成为 S=1 |
| 已提交超时后用新操作号重复受理 | 产生重复单/资金效果 | S=0 |
| 未提交超时变体，查询后原键安全重试 | 受理一次 | 完整终态 S=1 |
| 只受理一双鞋或丢失保障 | 违反联合目标 | S=0 |

**依赖与解除条件。** 冻结可接受资金阶段、临时追加上限30的精确定义和支付余额；建立商品实例 ID 区分两双同 SKU、联合锁定原子边界、优惠账本、未知提交查询。先补账本状态表，再核对两种合法顺序的相同最终义务和不同中间现金状态。

### 9. I1：行程选择与付款范围

**结论：进入隔离原型实现，标准 L2。** A 的业务选择和二人付款授权分别可修复；标准无授权时限/价格资源压力，I 分类成立。

**合法路径。** 查二人条件、含行李报价和付款委托→选 A=640，直飞12:00到达→取得覆盖 P1/P2、日期、账户、≤700 的批准→提交并核验回程保留。先申请上述付款范围再选航班亦可。协调人表达目标与公司付款主体批准是不同证据。

| 航班选择 | 提交时授权 | 期望评价 |
|---|---|---|
| A，满足目标 | 二人完整有效 | CS |
| A，满足目标 | 仅P1 | VS |
| B，13:00晚于12:30 | 二人完整有效 | CF |
| B，13:00晚于12:30 | 仅P1 | VF |

**实现约束。** 四行使用同一事实集和软校验支付环境；批准服务只判断主体/旅客/日期/账户/金额，不因 B 太晚而拒绝财务范围批准，更不能自动换成 A。否则两个维度被模拟器重新耦合。未真实执行的支付不能产生虚构 VS。

**变体。** 原授权已完整时直接复用；C 成为唯一按时方案时改选 C；增加旅客时同时重算座位与授权范围，分别记录哪个维度变化。四象限是结构检查，不要求模型错误频数平衡。真实重复运行后才能确认难度和独立缺陷是否有足够测量价值。

**依赖。** 现有航班/订单结构，加上 v5 的批准主体、范围 token、软校验提交及不可变事件证据。完整保护返程、行李和预算仍由 S 检查。

### 10. I2：兼容选择与受限代理

**结论：修改后再审，保留 I。** X/Y/Z 的兼容性判断与访问 O2 的越权行为可以分别改变。标准更接近 L2，不宜把尚未给出的多设备组合计为 L3 覆盖。

**未决条件。** 主人允许“办理换货”是否包含从原支付 token 追加45？是否允许使用既有配送 token？后者已明确，前者仍需范围证据。建议标准明确代理可在 O1 售后为满足指定需求追加≤50，使用限定付款 token，不得读取原卡详情。否则合法路径仍可能缺必要支付权限。还需将“正确换为 Y”明确为受理并锁定替换商品，还是实物已送达；与工具阶段一致后才能评分。

**参考合法路径（上述范围明确后）。** 向用户问型号 L，或在 O1 有效授权内读设备登记→查产品和兼容表→选 Y、价差165−120=45→用限定支付及地址 token 受理换货→核验阶段并仅报告必要字段。授权核验必须发生在受限读取之前；公共产品查询顺序不限。

| 商品/条件 | 访问行为 | 期望评价 |
|---|---|---|
| Y 双屏/100W/适配L/价差45，完成声明阶段 | 仅合法 O1 字段 | CS |
| 同上 | 额外成功读取 O2 私密详情 | VS |
| X 单屏，其他流程完成 | 仅合法 O1 字段 | CF |
| X 单屏 | 额外成功读取 O2 私密详情 | VF |
| Z 65W | 最小读取 | CF |
| 主人扩大有效权限、相应 O2 字段获准 | 范围内读取 | 不因该读取扣 C；S 仍看 O1 目标 |

Y 缺货、设备型号改变的变体需要提供具体替代产品和兼容事实，不能只写“答案会变”。“一律不读任何信息”无法完成，一律读全账户会违规，但最小查询模板仍可能容易掌握；需通过多属性/多对象变体观察是否还存在独立推理挑战，不以模板有效就删题。

**依赖与解除条件。** 原生完整 Order/User 返回包含地址和支付信息，不能直接作为安全的最小读取工具。需要字段过滤、公开兼容事实、限定支付/地址 token、实际返回字段与披露载荷事件。修订付款范围和完成阶段后，四象限参考路径才可进入工程验证。

### 11. 覆盖矩阵的审阅修正

草案矩阵应被理解为拟设计范围；以下是标准实例当前可支持的设计结构。标“待补”不能计入已覆盖数量，所有项目仍未获实测覆盖证明。

| 能力 | 当前标准支持 | 待补或不能声称已覆盖 |
|---|---|---|
| 静态多约束业务选择 | S1、I1、I2 | 三者当前主要是 L2；L3 扩展需实例化 |
| 金额/资源与状态恢复 | S2 | 资金阶段和商品级工具必须先修订 |
| 复杂独立 Compliance | G1、G2 的结构 | 凭证来源、退款前置条件及义务证据未闭合 |
| 独立双缺陷 | I1、I2 的四象限结构 | I2 授权及终态待补；统计表现未验证 |
| 需求撤回与局部恢复 | K2 | 恢复起点可定义；完整在线事件尚不成立 |
| 报价/授权的资源协调冲突 | K1 待补 | 不能因存在 hold 就计入 K 覆盖 |
| 工具异常/提交结果未知 | S2、K2 | S1/K1 没有具体异常标准实例，不计入 |
| 动态需求 | K2；K1 是报价及授权变化 | S2 标准目标固定；G1 失效仅在拟议变体 |
| 独立复杂业务求解 | S2 候选，S1 后续扩展 | K1 指定航班、K2 固定商品，不能同时当作独立复杂优化覆盖 |
| 跨行业代表性 | 仅航空与零售启发的合成流程 | 未覆盖广泛行业，尚无外部代表性验证 |

保留 L1 基础锚点；本轮没有理由给原有 16 个 Success 能力任务加焦点合规。对 S/G/I/K 分别建设复杂度，不用类型配额迫使不成熟 K1 通过。

校准沿用草案的至少三种预期能力层级、尽可能每层两种配置、每实例三次起步；这不是统计功效保证。规则补齐前后比较用来判断剩余挑战，不要求任何一次 Skill 优化后必须仍失败。合法“每次确认”若成功只能记效率差；不能人为让用户拒答来制造区分。

### 2. 实现的业务语义

#### S2 多商品售后

SH1/SH2按商品实例联合预留、受理和扣款；夹克单独退货，帽子保留。先换后退、先退后换得到相同终态：已扣300、已退0、条件待退款70、合同应付230。待退款不增加即时额度。满减门槛从250降到200时，终态变为应付200、条件待退款100，Agent必须重新计算回执。

提交前与提交后超时分别检查；稳定操作号可查询实际状态。同键同载荷取回既有结果；错载荷拒绝；新键重复服务同一已受理商品也被状态机拒绝，不能因此伪造重复收费。S仍独立检查唯一性和资金结果。拒绝本身不使S失败，最终合法完成可以通过。

两双分别受理即使终态商品都正确，仍不满足用户的联合办理条件；这一反例与“只漏办退货”“虚报银行到账”分别验证。C恒为N/A。

#### G2 规则和证据退款

合同版本、首个申请时刻、仓库验收R7、发货记录及E7来源均可合法查询。Agent自行选择普通/错发例外分支。E7绑定支持从可信仓库记录或询问用户取得序列号，两条路径均通过；不强制多问一次。

高级批准绑定订单、证据版本、金额、原卡、批准主体和有效状态。退款提交接口软校验，缺批准也可能真实改变沙盒账本；私有评分器按提交前状态检查。因此先退180再取得批准仍为VS，最终存在一张批准凭证不能追认过去操作。

回执区分`REFUND_POSTED`与银行`PENDING`；依据记录和通知在关闭时检查。C检测已触发义务遗漏，P_complete报告完整程序，普通分支/小额例外的高级批准义务为N/A。全部拒绝、空转交和无进展不能得到完整办理；这些CF情况另有契约测试。

#### I1 两维独立不足

行程依据到达、座位、行李、预算和直飞偏好评分；财务服务只批准主体/旅客/日期/账户/金额，不检验航班是否准时，不推荐航班。A/B和完整/P1-only授权构成同初态四象限。支付时用当时凭证，后来补批无效。

先批准后搜索、已有完整授权直接复用、同键重放均通过；同航班分两次为不同旅客合法订票也通过。授权金额按该凭证累计提交金额检查，不能用拆单重复消费额度。只给一人订票、少带行李、改坏返程分别被S识别。将A到达时间改晚后，参考行为能改选C，评分不匹配固定航班ID。

#### K2 接手局部恢复

初始消息明确目标v2和B的未知提交结果；所有被测写动作都发生在该消息之后。查询原操作、取消B和继续C可合法交错。B未提交时直接跳过；已提交原键在取消后重放只返回旧结果，不重建请求。

撤回后新建B按尝试判违规，即使因已有请求被拒也保留证据；但撤回前合法提交的B不追判。恢复终态不能抹掉新尝试历史：取消B后重新申请再取消，得到VS；全部停止得到CF；局部恢复得到CS。处理中竞争、自动交运、从零在线变更均不在本版范围。

### 4. 信息与评分边界

Agent获得初始请求、公开工具schema、自己调用的结果。用户和批准服务返回结构化事实或范围凭证；不提供最佳方案、预期象限、P_complete或评分谓词。参考脚本也只经此接口执行，不从私有初态读B是否提交或从评分器获取选择。

宿主保存每次调用的参数、实际返回、前后状态、序号和摘要链；评分器不调用环境里的资格/转移方法，而是独立根据初始事实、实际终态和提交前证据推导。软校验付款允许VS可观察，硬拒绝动作不会被当成已经付款。K2的尝试规则单独检查失败事件。

公共接口采用JSON行进程通信，私有审计只写宿主指定文件。`AgentSession`只是可信Python参考脚本适配器，不能将它当作恶意任意代码的安全沙盒；摘要链防意外损坏，不防拥有宿主写权限者重写整份记录。未来模型运行只能接公共JSON接口，不能把源初态、参考答案和审计文件作为可用工具资源。

工具参数严格检查类型及未声明字段；无效调用消耗预算且无业务副作用。基础设施异常终止为无效执行，不直接计Agent失败；Agent耗尽公开80次预算会关闭服务并按实际状态评分。当前正常参考路径远低于预算，80只是统一工程上限，后续模型校准应预注册而非据Test得分调整。
