# 研究文件组织与排版规范

适用范围：本仓库后续方法研究、Benchmark 开发、实验和文档维护。

先确定研究对象，再区分实现、定义、实验配置、运行数据和研究结论。每份材料只有一个维护位置，其他地方用链接引用。下文中的 `<版本>`、`<实验ID>` 等是占位符，不是需要创建的目录名。

## 1. 新文件放在哪里

| 材料 | 归属 | 进入 Git |
|---|---|---|
| 项目介绍、入门及总导航 | 根目录 `README.md`、`CONTRIBUTING.md` 与 `docs/README.md` | 是 |
| 方法实现 | `src/skill_evolution/<版本>/`；跨版本共用实现放 `shared/` | 是 |
| Benchmark 实现 | `src/benchmark_v1/` 至 `benchmark_v5/`；Governed 系列用 `src/benchmark_governed/<版本>/`；共用实现用 `src/benchmark_shared/` | 是 |
| 任务、划分、规则、模板及版本定义 | `benchmarks/<系列>/editions/<版本标识>/` | 是 |
| 方法实验的输入、配置、精选结果和报告 | `experiments/methods/<版本>/<实验ID>/` | 是 |
| τ² Benchmark 实验材料 | `experiments/benchmarks/tau2/<版本标识>/<实验组>/` | 是 |
| 独立 V5 Benchmark 实验材料 | `experiments/benchmarks/v5/<实验组>/` | 是 |
| 方法运行轨迹、请求响应、运行数据库和检查点 | `artifacts/methods/<版本>/<运行ID>/` | 否 |
| Benchmark 原始运行数据 | `artifacts/benchmarks/tau2/<版本标识>/` 或 `artifacts/benchmarks/v5/` 下的运行目录 | 否 |
| 本地验收输出 | `artifacts/validation/<验收ID>/` | 否 |
| 方法设计、协议与综合结论 | `docs/methods/<版本>/` | 是 |
| Benchmark 设计、协议与综合结论 | `docs/benchmarks/<版本或系列>/` | 是 |
| 通用维护规则及迁移说明 | `docs/repository/` | 是 |
| 跨版本研究提案与路线图 | `research/` | 是 |
| 自动化测试 | `tests/skill_evolution/<版本>/`、`tests/benchmarks/<版本或系列>/` 等对应模块目录 | 是 |

`src/` 保存“如何运行和评测”的代码；`benchmarks/` 保存“评测什么”的定义；`experiments/` 保存“如何做了这次实验及得出什么结论”；`artifacts/` 保存完整运行证据。不要根据扩展名归类：`results.json` 既可能是精选汇总，也可能是完整运行数据。

Governed V1–V3、Phase V1–V4 与独立 V5 的版本身份不同，不能只因数字相同就合并。现有 Benchmark 数据目录以 [系列导航](../../benchmarks/README.md) 为准；`standalone` 表示独立系列，不是临时材料目录。方法版本与 Benchmark 版本也分别命名：方法 V18 使用 Benchmark V4 时，方法配置仍放在 V18 下，并在配置中记录 Benchmark V4 的身份。

命令脚本按 [scripts 导航](../../scripts/README.md) 放入 `runs/`、`analysis/`、`preparation/`、`migrations/` 对应版本，Benchmark 命令放 `scripts/benchmarks/`，仓库维护放 `scripts/maintenance/`。不要把可复用实现放进脚本或数据目录。

## 2. 目录和命名

- 沿用所在系列的版本写法：方法为 `v01`、`v18` 等；Benchmark 使用现有 `v5` 或完整 edition 标识。不要为统一外观重命名已有实验身份。
- 新方法实验 ID 使用 `v<版本>_<阶段或主题>_<三位序号>`，例如 `v22_pilot_001`。日期使用 `YYYYMMDD`；同一实验多次执行用独立运行 ID 区分，避免覆盖历史运行。
- Python 模块、脚本及普通目录使用小写 `snake_case`；专题文档沿用大写名称，如 `DESIGN.md`、`PROTOCOL.md`、`REPORT.md`。配置按现有加载器约定命名，不为排版改变接口。
- 不使用 `new`、`final_final`、`copy`、`最新版` 区分版本；版本、日期和状态写在文档元信息或实验清单中。
- 只创建当前有内容的子目录。已有实际文件时不加 `.gitkeep`；确需版本管理的空目录才保留占位。
- 不在 `experiments/`、`src/` 或 `docs/` 顶层继续平铺版本材料，不新增旧路径快捷链接或兼容副本。

新方法实验可采用以下结构。树中的文件是示例，不要求每次全部创建：

```text
experiments/methods/v22/v22_pilot_001/
├── README.md                  # 问题、状态、配置及证据入口
├── config/
│   ├── config.json
│   └── manifest.json
├── results/
│   └── summary.json           # 精选汇总，不含完整逐次请求响应
└── reports/
    └── REPORT.md              # 本次实验分析与限制

artifacts/methods/v22/v22_pilot_001_run_001/
    ...                        # 轨迹、运行日志、数据库等本地证据

docs/methods/v22/
├── README.md                  # 版本导航
└── EXPERIMENTS.md              # 多次实验的综合结论与链接
```

既有目录可以保留已明确的内部层级；本规范约束后续新增材料，不要求为模板再次批量移动历史文件。

## 3. 文档怎么拆分、合并和排版

一个研究对象一个文档目录，一份主题文档负责一个长期问题。小幅协议补充、同主题的预算诊断和修订记录优先追加为章节；只有独立问题或独立维护需求才新建文件。V5 可参照 [当前专题索引](../benchmarks/v5/README.md)。

合并时保留原阶段、版本、实验条件、失败结果及日期，不能把不同设置的结论揉成一个结果。详细单次报告留在对应实验目录；专题文档通过相对链接引用报告，避免复制维护两套正文。README 只作导航、状态和入口说明。

统一使用 UTF-8、LF 换行和文件末尾一个换行。Markdown 约定：

- 每份文件一个 `#` 标题；主要章节用 `##`，子章节用 `###`，不跳级。
- 标题、段落、列表、表格和代码块之间留一个空行；不用连续空行或尾空格控制版式。
- 并列比较用表格，执行顺序用编号列表；命令代码块标注 `bash`，结构示例标注 `text`。
- 仓库内链接用相对路径；可运行命令说明执行目录、环境及输出位置。不要写个人电脑的绝对路径。
- 新增或移动文档时同步所在目录的 README；只有新增研究对象才更新总导航，避免总导航变成实验流水账。
- 图表及小型静态附件放在对应主题的 `assets/`，说明数据来源；大体积中间图和渲染缓存放 `artifacts/`。

研究文档可按下面模板裁剪。未执行时写“未执行”，失败时保留失败状态，不填写推测指标：

```markdown
# 主题名称

- 对象与版本：方法 V22 / Benchmark V4
- 状态：草案 / 已登记 / 已执行 / 已结束
- 更新日期：YYYY-MM-DD
- 对应实验：相对链接或实验 ID

## 问题与假设

说明要检验的问题、假设和可能推翻假设的结果。

## 协议与配置

记录数据划分、基线、评价指标、预算、重复次数和停止条件。
链接具体配置，说明执行命令、代码身份、模型及依赖环境。

## 结果与证据

写明有效样本数、失败或未执行项、指标及证据位置。
区分工程检查、历史重放与新模型实验。

## 结论与限制

只陈述证据支持的结论，说明不确定性和下一步。

## 修订记录

按日期记录实质变化，保留旧结论的适用条件。
```

## 4. 配置、结果和运行证据

- 沿用现有 JSON/YAML schema；新建 JSON 使用两空格缩进，YAML 使用空格而非 Tab。不要为格式统一改写原始运行文件。
- 实验清单记录实验 ID、方法和 Benchmark 身份、任务划分、随机种子、完整模型 ID、temperature、预算、重复次数和输出位置。
- 记录 Git commit；若运行时有未提交代码，同时保存代码摘要或差异证据。单个 commit 不能代表未提交工作区。
- 汇总结果应能追溯到运行 ID、输入配置和原始证据的位置及摘要。失败、缺失与未执行使用明确状态；未产生的数值用 `null`，不要用 `0` 冒充结果。
- 原始运行目录每次独立创建；重新分析另存报告，避免改写原始轨迹。允许修改历史实验代码以读取新路径，但要如实区分当前实现与历史运行时的源码身份。
- 日常记录追加到 `docs/04_EXPERIMENT_LOG.md` 并链接专题报告，不复制全部正文。两份现有实验日志本次继续保留，不删除、合并或批量修正历史内容。

## 5. Git 收录和快照规则

可提交代码、测试、小型测试夹具、Benchmark 定义、输入配置、人工审查及精选汇总。完整模型请求响应、逐步轨迹、运行数据库、检查点、缓存、环境凭据和外部仓库副本不提交。即使产物很小，也不应只因体积小就纳入 Git。

`.gitignore` 不会自动取消已有文件的跟踪，也不会检查 ZIP 内部。原始文件移入 `artifacts/` 后，需要确认旧位置的删除和新位置的忽略同时成立。精选报告若落在通用忽略规则覆盖的目录，应增加精确到文件的例外，并继续忽略同目录的新运行输出；不要整体放开 `attempt*` 或使用 `git add -f` 绕过分类。

新增迁移 ZIP 只保留必要的文档、源码和配置原件。不要把被忽略的运行数据重新打包入库；确需本地备份时放在 `artifacts/` 或外部存储。现有迁移收据保存路径和摘要即可：排除原始产物的快照，仍通过本地原件校验数据是否完整。克隆仓库不会获得被忽略的运行数据，需要另行取得才能做完整历史核验。

## 6. 每次研究工作的收尾

1. 按上表确定材料归属，在现有专题中复用章节和目录。
2. 写清协议、配置、实验身份和独立输出目录，再运行实验。
3. 将精选结果与原始证据分开，更新实验报告、对应 README 和日志。
4. 移动文件时同步代码导入、配置路径、脚本、链接及需要更新的当前摘要；删除旧入口，不新增快捷方式。
5. 运行受影响测试。涉及本次迁移记录时，可在具备本地原始数据的环境执行以下检查；摘要变化要审查原因并记录，不要直接覆盖摘要来消除报错。

```bash
# 在仓库根目录执行
python3 scripts/maintenance/verify_final_layout.py
python3 scripts/maintenance/verify_code_layout.py
python3 scripts/maintenance/verify_canonical_paths.py
git status --short
git diff --check
```

暂存所需变更后，再检查实际提交内容：

```bash
git diff --cached --stat
git diff --cached --name-status
git diff --cached --check
git ls-files -ci --exclude-standard
```

最后一条应无输出；它只检查被忽略但仍跟踪的文件，不能证明所有运行数据都已排除。还要检查新增路径和压缩包内容，确认新位置已纳入、旧位置已删除、原始证据仍在本地。历史 Markdown 的尾空格提示需区分本次新增与原有内容，避免顺手格式化受保护日志。

目录调整、依赖路径修复和对应导航可以放在同一次完整提交中。提交前确认是否混有整理之前的研究修改；只提交自己打算包含的内容。
