# v21：缺陷依据调整后的三步真实验证

日期：2026-10-10。接续[缺陷依据与修改授权调整](V21_DEFECT_GROUNDING.md)。

**三步均已完成：姓名和地址的主要判断边界本次得到改善；跨问题检查部分通过，尚不能宣称修改授权已普遍可靠。** 姓名 Review 用原文推翻缺陷并选择 NO_EDIT；地址保留有限修改；代金券在 Fusion 有依据地停止；条件式航班选择的 Review 识别了真实偏差，但批准的停止/转人工要求还需要审视。

## 1. 冻结设计与执行范围

调用前冻结完整 treatment Fusion 输入、姓名/地址及两个迁移问题的引用范围、判定依据、源码哈希和最多五次调用的上限。使用 Fusion v21.6、Review v21.9，保持 deepseek-v4-pro、temperature=0、reasoning_effort=high、输出预算 24,000。没有根据响应修改 Prompt、替换案例或自动重试；Memory 的 2,000 字符限制不变。

本轮选择上一轮姓名误判所用的 treatment 来源，完整保留该批 Findings、Memory 和 Parent，不裁成只有目标案例的小输入。没有重跑 control。验收标准是缺陷判断及修改边界是否有证据，不是必须产生某个 verdict。

执行顺序为：

1. 一次真实 Fusion，复核姓名、地址的提案。
2. 根据这次真实 PROPOSE，经现有 GenerationInput 构造并运行姓名、地址 Review。
3. 保持版本不变，检查预选迁移问题：对条件式航班选择的真实 PROPOSE 运行 Review；代金券为 NO_EDIT，不人为追加 Review。

本次 Fusion 共 4 个 PROPOSE、7 个 NO_EDIT。行李虽仍 PROPOSE，但不在预定范围，未派发 Review。实际共 **1 次 Fusion + 3 次 Review**，不是一轮完整 generation，不生成 Editor 输入或 Candidate，不执行 Replay、Memory 更新及活动发布。

两个迁移问题曾出现在旧批量实验中，但未直接用于最新缺陷依据提示的调整。这是**开发集内迁移检查，不是完全未见过的盲测**。条件式航班选择检查仍可能值得修订的行为问题；代金券检查已有支持和当前覆盖下是否合理停止。

## 2. 第一步：Fusion 是否提出有依据、可反驳的方向

| 问题 | 决策 | 本次观察 |
|---|---|---|
| 姓名 | PROPOSE | 要求比较用户提供字段与实际传参，判断重复是否真是解析错误；承认期望值及失败原因未确定，没有直接要求删除重复 token |
| 地址 | PROPOSE | 保留 Court/Street 确认文字偏差及用户纠正，要求结合其他三段轨迹复查；没有把失败直接归因给 cedar 合同 |
| 条件式航班选择 | PROPOSE | 指出将原始总价基准换成候选之间差额的行为，并与 horizon 定价分开；但修订或转人工仍只是待核查方向 |
| 代金券分配 | NO_EDIT | 根据当前分配行为及已有条款，认为历史两类支付问题没有在本轮重现；将可见政策未说明该限制保留为泛化边界 |

姓名进入 Review 是合理的有限问题，不因最终 NO_EDIT 就判 Fusion 失败。Fusion 没有原始对话，不应被要求提前知道用户确实逐字段提供了这个名字。

地址提案还提到较宽的“核对 profile/order 显示”，不能直接视为已授权方向；是否有依据交由 Review。迁移中，代金券的 NO_EDIT 不是仅依据没有 OBSERVED_PROBLEM 标签：理由还指出具体有效分配和当前条款的对应。

## 3. 第二步：原始证据能否约束实际修改授权

### 姓名：通过，原文推翻缺陷假设

Review 检查了用户明确给出的 `first_name='B Traveler1'`、`last_name='Traveler1'`，以及摘要展示、用户批准、实际调用和返回值。它认定 Agent 忠实使用了唯一可见的字段值；可见政策要求收集姓名和生日，但没有要求对多词或重叠词再次拆分/核对。

因此，success=false 不能证明姓名处理错误；缺少的是成立的行为偏差或独立要求。Review 返回 **NO_EDIT、gap=null**，没有再新增强制字段确认。

相比[上次验收](V21_SEMANTIC_ACCEPTANCE.md)，本次保留同样的 20 个原始事件、Findings、政策和 Parent，但 Fusion 提案与 Review Prompt 都变化了。因此可以说这一次组合行为改善，不能单独归因于 Review 提示，也不能据一次响应证明稳定性。

### 地址：主要判定通过，保留措辞边界

Review 识别出用户请求 Court、Agent 确认时写为 Street，随后由用户纠正，最终写入正确；没有把“最终写对”当成早先没有偏差。它还利用其他成功与失败轨迹，说明同样的整体工作流并不保证任务成功，不能由这次文字错误推导所有失败的原因。

最终 **VERIFIED / MISSING** 的 gap 限于现有双地址确认环节：准确复述用户提供的目标，在请求或依赖确认前纠正不一致。没有改变写入顺序或引入 cedar 规则，也没有保留宽泛的 profile/order 显示核对机制。

其 reason 仍有“纠正后重新列出”的表述。正式 gap 没有要求用户再确认一次；这不能在后续 Editor 中扩展成已明确批准纠正值之后仍须新增确认轮次，也不能把准确复述扩大成禁止无害的格式规范化。本次通过的是有限修改依据，不是编辑效果已验证。

新 Fusion 选择了更多相关 Findings，地址输入由上次 22 个事件扩大到 88 个，旧事件全部保留。这个差异已记录，不能将结果完全归因于提示变化。

## 4. 第三步：跨问题迁移

### 代金券分配：Fusion 层通过，未运行 Review

原始档案存在 basic_economy 使用代金券被工具拒绝，以及代金券重复使用后找不到支付方式的历史。当前预订调用则把代金券与礼品卡分配到合适的不同订单，避免重复使用；这些事实支持当前 Findings。

Fusion 依据这种具体行为与条款覆盖选择 NO_EDIT，并保留“操作限制并非由可见政策直接给出”的边界。它没有把历史整条轨迹的成功或合规标签当成每次支付调用都正确的证明，也没有因旧失败就重复提出已有方案。

本轮按真实路由停止，不追加 Review。**这里只验证了 Fusion 判断，不能写成代金券的 Review 也通过了迁移。**

### 条件式航班选择：部分通过，修改授权范围仍偏强

Review 正确比较了：

- 原规则按相对原始 $400 总价的增量判断；LM323 增加 $160，LM324 增加 $100。
- 用户一度拒绝直接选择或调整规则。
- Agent 随后改用两个候选之间的 $60 差额，声称据此遵循原规则选择 LM323。
- 之后用户明确同意执行 LM321 + LM323，最终收费为 $160。
- horizon 的保留航段价格计算本身正确，不是这一问题的缺陷。

维持原比较基准、避免把改过的基准说成遵循原规则，有行为证据支持。但 Review 批准的 gap 进一步要求：在用户给出无矛盾选择或修订规则前不得更新；若用户拒绝解决或调整，则转人工。

问题在于它承认后来的明确批准，却主要以“批准没有恢复原阈值”继续支持上述要求。**错误地声称遵循旧条件，与用户后来是否授权具体方案，是两个需要分别判断的问题。** gap 允许用户给出明确选择，reason 却没有充分说明后来的明确选定为什么不属于这一情况。

可见转人工政策为：请求确实超出可用行动范围才转人工；工具可调用本身不能证明这一前提。因此，本次不接受整个 VERIFIED 授权为完全通过，记为 **PARTIAL**。这不意味着必须判 NO_EDIT、任何转人工都错误，或基准替换不值得修改；支持的是较窄的表达与决策缺陷，尚不足以无条件接受更强的停止/转人工要求。

本轮没有修改运行源码，没有重复运行整套代码测试；完整性检查不等于语义自动判定。人工逐项结果保存在 assessment.json，不进入运行协议或新状态体系。

## 6. 结论与后续边界

主要案例本次表明：机制既能否定未成立的缺陷，又能保留真实偏差的有限修订。迁移没有全部通过，剩余问题集中在**从真实缺陷到更强程序要求之间的授权范围**，而不是姓名原文再次遗漏。

不再针对姓名添加规则，也不因局部改善直接宣称完整 v21 已验证。后续若继续强化，应只处理“此前错误解释”与“后来的具体授权”之间的区别，避免把前者自动扩展成后者无效或必须升级处置；保留本次结果，另立实验，不回写通过。本次仍未验证最新 Memory 更新进入完整下一轮，也未运行 Editor/Replay。
