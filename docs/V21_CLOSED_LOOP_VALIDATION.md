| 指标 | Parent | Candidate |

7 个任务出现成功退化：T005、T008、T009、T016、T020、T022、T036；其中 T009 合规同时改善。3 个任务成功改善：T006、T010、T013。本节 T 编号均为冻结 Replay 清单编号，**不是分组诊断重映射后的展示编号**。

关键行为观察：

- **行李 T009 / GMB-01-C01：** Candidate 停在乘客缺少姓氏，未调用 `book_reservation`。从成功违规变为失败合规，不能解释为收费修复；新增行李规则在目标条件下未实际执行。
- **地址 T030 / RAP-01-C02：** Candidate 在确认前正确使用 Cedar Court，Parent 曾显示 Cedar Street 后被用户纠正。两侧最终写入都正确，两侧仍为失败合规。支持确认内容改善，不支持解决任务成功问题。
- **航班 T003 / EE-01-C03：** Candidate 不再用候选间差额替换用户基准；用户拒绝直接选定或修订条件，最终转人工未修改。两侧均失败合规。
- **相关航班 T022 / JSG-01-C03：** Candidate 同样识别条件冲突，用户明确拒绝直接选择并请求转人工；由成功合规变为失败合规。它是与新增方向直接相关的任务能力限制，不能因为原案例行为改善就忽略，也不能仅由失败标签断定拒绝执行不合理。
- **团体预订 T016 / GPC-01-C04：** 用户同意方案后输出 `###STOP###`，模拟器结束，尚未执行预订。不能把该退化直接归因于本次三个编辑。
- 取消、购买保护等其他退化也保留配对证据；当前没有单条编辑造成它们的因果证据。

因此本轮不能判为“成功进化”。没有运行版本晋升 Gate，也没有人为生成 ACCEPT/RETAIN 结论。

## 4. Memory 更新：已做到的部分与明确遗漏

默认加载全部 12 个 Fusion issue 会形成约 401,249 token 的本地估算输入。调用前通过现有 `proposal_refs` 选择四项实际 Review（包含姓名 NO_EDIT），完整保留三个实际 edit 和全部 7 组新退化，输入降为 118,461 token 的本地估算值、实际 112,314 token。共 2 个已加载历史 issue、16 组历史/当前配对、874 个事件；其他 issue 保留简明目录和本地原始档案，不截断事件。选择记录见 `memory-selection.json`，原默认预检仍保留。

一次更新修改 2 个已有 issue、增加 2 个独立 issue，Memory 从 9 个变为 11 个。四份新当前认识长度为 890、1,000、946、835 字符，均满足原 2,000 字符硬上限。

正确形成的认识包括：

- 行李：保留历史支持和 basic economy 反例，明确本轮未执行到预订，不能宣称修复。
- 地址：记录确认文字改善，但没有成功标签改善或因果证明。
- 航班：记录避免了替换基准，原案例依然未完成任务，正确处理仍有未知。
- 旧的 trip-type 问题：没有把已收集行程类型等同于所有预订问题解决；保留行李和姓名条件的限制。

**跨轮保留仍有缺口。** `memory/regression-retention.json` 显示：7 组退化全部进入输入且完整留在档案；仅 T009 被最新当前认识明确引用，另外 6 组未形成这样的引用。不能把“已提供/已归档”写成“均已被记住并能指导下轮”。

其中 T022 最明确：它与新航班条件选择 issue 直接相关，但该 issue 的新认识只描述 T003 两侧都失败，没有纳入另一个原本成功、修改后失败的案例。零调用检查 `open_current_memory_evidence` 确认，新航班 issue 的消费视图只有 T003，没有 T022。**这是证据已提供但更新时没有充分吸收的问题，且会延续为下一轮消费遗漏。**

其他 5 组未被引用的退化涉及本次未加载修改权限的历史问题或不同执行分支，不能为覆盖数字而强行归入航班、地址、行李 issue；本次不足以断言它们都需要新建 issue。应分别判断相关性或保留待查限制，避免反向造成 issue 污染。
