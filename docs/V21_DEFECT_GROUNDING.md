Fusion 现在明确区分报告的行为与推断的缺陷。`OBSERVED_PROBLEM` 和 Memory 都是可修订的解释；未加载原文时，应把可能偏差及可推翻它的证据作为 Review 问题，不能先把表面模式定为错误、再把消除该模式当作修改方向。

Review 在授权 VERIFIED 前，须核对缺陷是否由用户原始表达、实际行为和适用要求支持。原文可以推翻 Finding、Memory 和 Fusion 的判断；忠实使用用户明确信息，不能仅因结果外观异常就被定义成缺陷。缺陷假设被推翻且该问题内没有其他受支持缺陷时，使用原有 NO_EDIT 并解释，不发明预防性义务。

两处共同收紧：新增确认、拒绝或转人工要求，须有相关歧义、冲突、授权缺口或适用要求作为依据。“当前没写这条规则”“可以执行、可以测试”不证明新增义务有必要。

同时保留另一侧边界：后续纠正或用户批准，不抹去此前已经发生的真实偏差，也不能覆盖适用政策；因果机制尚未完全解释，仍可对有依据的缺陷提出有限修改。这样不会把姓名原文反驳缺陷的情况，混同于地址确认确实写错、后来才纠正的情况。提示中没有姓名字段、重复 token 条件、地址值或案例预设答案。
