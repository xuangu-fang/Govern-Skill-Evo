# Spreadsheet Manipulation Skill (xlsx)

## Overview
This skill guides agents in manipulating Excel (.xlsx) spreadsheets using Python.

**Primary libraries**: `openpyxl` (structure-preserving read/write), `pandas` (data transformation).
Never use any other third-party libraries.

---

## Common Workflow

1. **Explore** the input file: list sheets, inspect headers, check dimensions.
2. **Write `solution.py`** with `INPUT_PATH` and `OUTPUT_PATH` defined at the top.
3. **Execute** `python solution.py` and verify the output file was created.
4. **Confirm** the target cells/range contain the expected values.

---

## Library Selection

| Use case | Library |
|----------|---------|
| Preserve formulas, formatting, named ranges | `openpyxl` |
| Bulk data transformation, aggregation, sorting | `pandas` → write back with `openpyxl` |
| Simple cell read/write | `openpyxl` |

**Warning**: `pandas.to_excel()` silently destroys existing formulas and named ranges.
When writing back to a spreadsheet that contains formulas, always use `openpyxl.save()`.

### Formula-Safe Source Reads

When an instruction depends on the calculated result or the error status of a source cell that
may contain a formula, load a second `data_only=True` view of the workbook and use its cached
value for that computation or conditional decision — for example, to detect an error value such
as `#N/A`, or to decide whether a computed result is zero or blank. Use the normal
(formula-preserving) view for structural reads and for all writes so required formulas are
preserved. Do not treat a formula string as the numeric or text result; if no cached value
exists, handle that case explicitly rather than silently writing the formula text into the
answer cell.

### Formula Answer Cells with Cached Results

When a task asks for formulas in the answer cell(s), do not rely on a formula-only write:
`openpyxl` does not store a cached result, so a later `data_only=True` read returns `None`.
Compute each formula's intended readable result in Python from the workbook's source values,
reading any source cell that itself contains a formula through a `data_only=True` view.
Write the required formula into each requested answer cell and save the workbook.

Then inject the computed result as the cached `<v>` value for each formula cell in the
worksheet XML, preserving its `<f>` element and setting the cell type to match the result:
`n` for numeric, `str` for text, or the appropriate blank type for a legitimately blank or
empty-string result. After saving, reopen the final output twice: without `data_only` confirm
each answer cell still contains the required formula, and with `data_only=True` confirm each
answer cell yields the expected readable value and type derived from the task inputs. A
legitimate blank or empty-string result is allowed.

Gate any repair or fallback on this `data_only=True` readability check, not on whether the
XML edit reported success. If either check fails, repair the formula or cached value and
recheck. If the `data_only=True` check still fails after repair, deliver the correct readable
value as a literal in that answer cell as a fallback, then confirm that fallback reads
correctly; only if the readable value also cannot be delivered, raise an exception naming the
cell with the expected and observed result. Keep the required formula as the primary
deliverable whenever the cached-formula path verifies.

## Category-Specific Conditions

When an instruction imposes a category- or column-specific condition — for example counting
only positive values for one error code, or applying a warehouse, date or other criterion that
the surrounding columns do not use — apply that condition in every computation path,
including when the other totals come from cached or precomputed aggregate cells.

- Never obtain such a component by summing cached aggregates that mix included and excluded
  rows: recompute it from the underlying source rows with the predicate applied, then combine
  it with the other totals.
- Restrict the condition to the category or column it names and leave the other columns'
  calculations unfiltered.

### Normalized Text-Label Matching and Whole-Number Branches

When an instruction names a text label to locate in a column, normalize each candidate cell's
text before comparing: strip surrounding whitespace, collapse internal whitespace runs, and
compare case-insensitively unless the instruction explicitly makes the label case-sensitive.
When the instruction asks for keyword, partial or substring matching, test for containment in
the normalized text instead of equality. Apply a row's derived replacement only where the label
matches. Where it does not match, treat the row's original text unchanged as that cell's
derived result, and still recompute and write the whole answer region on every run. When the
same rule branches on whether an accompanying numeric value is a whole number, decide from
numeric content, not stored type: read formula cells through the `data_only=True` view, coerce
numeric-looking text such as `'500'` or `'500.00'` and float values before the test, and treat a
value with no fractional part within a small tolerance as whole and one with a fractional part
as not whole.

### Date Windows and Full-Range Evaluation

When a requested result is defined by a date window — for example a rolling average over the
prior 365 days — evaluate the predicate over the complete source table rather than stopping
at the answer row. Include every source row whose date falls within the lower and upper bounds
of that answer row, including rows that share the answer row's date but appear later in row
order. Do not adopt a row-order or cumulative cutoff; add one only when the instruction
explicitly asks for a running total or an up-to-current-row result.

If the answer column or nearby cells contain example formulas or values, use their formula
references or cached values to confirm only the exact inclusive/exclusive boundary and
same-date handling, then apply that convention to every answer row. Do not let such examples
switch you to a row-limited interpretation: early answer rows, whose whole window already
precedes them, give the same result under a row-limited and a full-range reading and
therefore cannot distinguish the two. Keep the full-range window as the default and only
tighten the boundary.

### Open/Outstanding Status at Period End

When a task asks for the number of records open or outstanding at the end of each period using
a created date and a closed date, define a record's status at a period end from those two dates:
it is open then only when it was created on or before that period end and its closed date is
still blank or falls after the period end. A record closed within the period is not open at
that period end — do not substitute a period-start test that also counts records closed during
the period. When the answer columns are named for the end of each period, compute the status as
of that period end even if other wording in the instruction phrases the closed-date boundary in
terms of the first day of the period. Use nearby existing open-status formulas — for example a
count whose closed-date criterion is blank — and any example values to confirm only whether the
closed-date comparison is strictly after the period end or also includes the last day, then
apply that same full-source predicate to every period, deriving each count from the underlying
record rows rather than adjusting a previously computed count. If an explicit formula or
example establishes a different boundary, follow that convention.

### Limited-Resource Allocation and Named Ordering

When a limited resource — stock, budget, capacity — is allocated across competing rows under an
ordering the instruction names, sort the competing rows inside each allocation group by that
named column and only then break ties. Identify the column from its header text in the source
sheet rather than from a fixed position, and use each row's value in it as the primary key; do
not silently substitute a different date column, such as the requested-delivery date in place
of the named issued or priority date. When the named date is identical for several lines of the
same group, the tie-break decides the result: break ties by line number and then by source row
order, not by another date column. If a row's key value is missing or unparsable, keep that row
inside its group and fall back to line or source order for it rather than letting a sentinel
push it to the end of the group. Then walk the sorted rows, give each the smaller of its
requested quantity and the stock still remaining for its group, decrement that remainder, and
write 0 for lines that receive nothing. Keep the limited resource pooled only within the group
the instruction names (for example the order number together with the item) so unrelated
groups never share it.

## solution.py Template

```python
import openpyxl
import pandas as pd

INPUT_PATH  = "..."   # set to the actual input path
OUTPUT_PATH = "..."   # set to the actual output path

wb = openpyxl.load_workbook(INPUT_PATH)
ws = wb.active  # or wb["SheetName"]

# --- perform manipulation ---

wb.save(OUTPUT_PATH)
```

## Output Requirements

- Save the result to `OUTPUT_PATH`.
- Do not hardcode row counts or column letters — iterate over actual rows in the workbook.
- Preserve sheets and cells not mentioned in the instruction.

### Answer-Region Writes

Treat any existing answer region as a destination that may contain sample, placeholder, or
partially completed output. Recompute the requested result from the workbook's source data on
every run; do not guard the computation with a check such as 'if the destination is empty' or
otherwise skip writing because values already exist. Overwrite the required cells or records.
When the newly derived result is shorter than the existing content in the same answer region,
clear the leftover values there so stale rows cannot remain. Clear values only, without deleting
rows or columns or disturbing formatting, and leave cells outside the requested answer region
unchanged.
