# Diagnosis v5：R05、R06 固定输入重跑与新旧输出比较

2026-10-28。结论：**部分表述和边界改善，但没有稳定解决原因定位、附加规则扩张及规则冲突；两个案例尚不足以认定新版整体优于旧版。** R05 将原文本匹配方向改成金额判定假设，未对准原错误；R06 不再对标识符错误强行归因，但没有提出已有证据支持的排序假设，并新增了一条存在完成性风险的工作流要求。

只重跑 Diagnosis。两轮均首次请求成功、结构校验通过，返回 `revise`，各 3 个 Update；没有技术/格式重试，也没有语义重采样。没有运行 Preconditioner、Editor、Actor、Candidate、Replay、完整训练或最终测试。不能由本次输出比较推出任务成功率变化。

## R05：没有解决原因定位，出现新的规则扩张

[旧输出](../../../../../artifacts/methods/v25/analysis/diagnosis_v5_r05_r06_20261028_001/R05/old_output.json) · [新输出](../../../../../artifacts/methods/v25/analysis/diagnosis_v5_r05_r06_20261028_001/R05/diagnosis/attempts/001/parsed.json)

方向从“文本匹配、数值边界、公式缓存”变为“金额判定、数值边界、精确查找”。

### u1：承认竞争解释，但选择的修复没有对准实际错误

新 reason 明确说，无法区分 pennies 判定与 exact-equality/contained-text 搜索的作用。这比旧版将 P4 称为 otherwise identical 并直接推广一组匹配规则更谨慎。新输出也不再要求所有标签默认子串匹配。

但是，新 u1 实际要求：金额按分舍入再判断整数，补充货币字符串、括号负数、尾部符号、公式缓存等处理。这里存在三点问题：

1. 原程序已有去逗号、去美元符号、float 转换和 1e-9 容差，并非没有数值处理。
2. 原程序先要求文本全等，只有命中后才进入金额判定。事后核查原始输入：

| 行 | 原始 E 值 | F 值 | 文本全等 | 旧整数判断 | 新按分舍入判断 |
|---|---|---:|---|---|---|
| 10 | Georgia Its Tax/ga Tx *****0 | -816 | false | whole | whole |
| 11 | Georgia Its Tax/ga Tx Payment | -7999.29 | false | has pennies | has pennies |

仅按新 u1 修改金额判定，不改变前面的文本筛选，这两行仍不能进入赋值分支。这里分析的是原代码与输入的确定性关系，没有重新执行 Candidate，也不声称模型下一次一定保持其他代码不变。

3. 按分舍入、括号/尾部负号、公式缓存都没有对应当前错误的直接证据；例如将带亚分精度的金额按两位小数舍入，本身就是新增语义选择。

原输入没有展示错误行的完整值，所以不能要求 Diagnosis 预知这些值；但它可以把金额分支与前置匹配分支作为待区分机制，而不是只验证金额假设。新 c1 仍主要问金额规则是否采用及标签是否正确，没有检查错误行是否先通过文本筛选。

判断：**不确定性表述改善，实际修复方向未改善；扩张从文本规则转移到了金额规则。**

### u2：保留了有依据的数值边界修复

仍明确读取真实上下限，按题目顺序进行容量受限的分配并跳过零值。reason 将其表述为观察到的要求违反，并说明不能据此解释每一个错误位置。

判断：**合理方向保留，原因声明更准确。** 但尚未生成并执行新 Candidate，不能声称它再次修复了任务。

### u3：新增查找假设，规则本身存在语义冲突

新 reason 将 P12 的剩余错误标为归一化或重复键假设，但 Update 要求：

- 对两侧一致归一化，并忽略 stray punctuation 或 invisible characters。
- 保留源公式的 first-match semantics，但如果首个匹配的 payload 为空，就继续找后续非空值。

原程序已经在查询侧和源侧调用同一个 normalize。忽略标点可能合并不同标识符；“保留首个匹配”和“首个为空就跳过”也不是同一种查找语义，后者需要任务依据。

事后检查四个错误行涉及的键：B160 对应查询键为空；其余三行按原归一化可找到源行，重复键也都具有非空 payload。没有发现这四行由“首个重复键 payload 为空”解释的直接支持。这不是完整查找根因证明，也不是要求模型看到未提供的工作簿内容；它说明新规则仍处于未经支持的假设层面，不能把假设中的数据特征当作已知情况。

判断：**假设标签保留了探索空间，但没有防止附加规则改变原任务语义，也没有消除 Update 内部冲突。**

### 公式方向

本轮没有再仅从成功的 P7 扩写缓存注入规则，符合这次审阅目标。不能因此认定公式可读性目标错误：完整分析已发现它有历史失败支撑，只是那些历史没有提供给此次 Diagnosis。

## R06：部分边界改善，排序假设遗漏，仍有新扩张

[旧输出](../../../../../artifacts/methods/v25/analysis/diagnosis_v5_r05_r06_20261028_001/R06/old_output.json) · [新输出](../../../../../artifacts/methods/v25/analysis/diagnosis_v5_r05_r06_20261028_001/R06/diagnosis/attempts/001/parsed.json)

方向从“锚点、合并、标识符与分配”变为“探查工作流、锚点、合并”。

### 标识符与排序：停止强行归因，但未提出有依据的竞争假设

新 reason 将 P15 的 H12/H13 保留为 unresolved，不再把保留完整标识符说成已确定修复。这是改善。

不过，原消息已给出两项信息：任务说明要求先满足第一行再分配余量；程序把 requested-delivery-date 放在线号之前排序。这足以提出一个待验证的顺序假设，不必先获得完整行值。新版完全略过该方向，说明这次采样中谨慎表达也伴随了探索遗漏。

判断：**解决了部分过度断言，没有完成原因定位；存在局部过度保守。** 不能由单例认定整个 prompt 必然保守。

### u1：工作流澄清有依据，但新增“遇到异常内容也必须交付”的风险

P9:2 只探查、不写 OUTPUT_PATH，确实触发 output_file_error；Parent 的 Explore 步骤也可能造成误解。把探查、变换和保存合入一个程序，是可讨论的澄清方向，不能仅因最终任务通过就否定这个效率问题。

但固定 Actor 协议本来已经要求完整程序和最终保存，并禁止专门的打印探查回合。新增条款还写道：

> The script must still create a valid output workbook even when the inspection reveals unexpected content.

首次正常结束且生成可打开工作簿就会提交。这个无条件要求没有区分“能够按任务继续处理”与“尚无法完成任务”，可能鼓励在意外内容下仍保存未完成结果。新 c1 主要检查是否产生可打开文件，不能验证任务完成。这是规则风险，不是本次已观察到的新退步。

判断：**存在澄清价值，但额外条款又把产物可打开强化成完成目标。**

### u2：取消清空周围内容，但表头锚点条件仍过宽

新规则将起点前的单元格改为保持原样，删除了旧版周围留空及额外全文列聚合要求。这两处改善明确。

但仍写成“任务包含表头时，就把表头放在指定答案起点”，没有限定“题目明确把这个起点指定为表头位置”。在起点实际指第一条数据、表头已存在的其他任务中仍可能改变布局。

reason 从 J4/J5 通过推导 counts were right，也比这两格提供的证据更强；这些坐标通过不单独证明完整聚合逻辑正确。

判断：**部分解决，语义触发条件仍未收紧到位。**

### u3：修复跳过来源的方向保留，默认顺序与映射仍附带进入

继续正确针对“目标来源列已经出现某名称，就跳过整张源表”的行为。

但同时加入“按指令列举顺序，未指定则按工作簿顺序”和按实际表头映射。原证据没有隔离这些默认顺序的必要性，原程序本来也在使用表头映射。新版 reason 还把既有映射描述为 independently consistent；这不是独立验证。

判断：**核心修复合理，单条范围仍有扩张。**

## 对修改目标的判断

| 审阅项 | 本次判断 |
|---|---|
| 不人为限制每轮数量 | 两轮仍各 3 项，没有机械压成一项 |
| 允许合理假设 | R05 明确提出假设；R06 分配方向存在遗漏 |
| 观察与假设分开 | 部分改善，但 reason 的谨慎措辞未约束 text 的强规则 |
| 单条 Update 不无依据扩张 | 未解决；金额、查找、表头和来源顺序都有残留或新问题 |
| 重复与冲突检查 | 未解决；已有 normalize 被重复要求，first-match 与跳过首个空值冲突 |
| Checks 检验问题机制 | 部分改善；有目标错误变化问题，但关键竞争解释仍未得到区分 |
| 不从当前成功公式例自动扩写 | R05 本次做到；不代表公式目标不应学习 |
| 找到 R06 分配错误的可检验方向 | 未做到，仅标记 unresolved |

本次不支持“Update 数量导致问题”的判断：数量完全相同，方向和质量明显变化。R06 文本更短仍存在过宽默认，R05 长度近似仍可换成错误修复方向。

## 后续设计含义

暂不修改 prompt、不继续抽样、不运行下游。若继续改 Diagnosis，优先针对本次暴露的具体缺口：

1. **检查修复能否作用到错误路径。** 对有前置筛选的程序，区分未命中、分支分类错误、写回错误；假设可以提出，但 Checks 应能检验前置条件是否成立。
2. **让行为规则保留假设的适用条件。** 不能仅在 reason 写 uncertain，text 却加入无条件舍入、去标点、跳过首个匹配等语义变化。
3. **把“已有行为”和“新增行为”逐条核对。** 原程序已有 normalize 或数值转换时，明确真正改变的是哪部分；不能重新包装为缺失能力。
4. **保留未确认但有直接线索的竞争解释。** R06 的额外排序优先级应能成为检查方向，不必在缺少完整行值时直接放弃。
5. **区分保存文件和完成任务。** 工作流修订不能在意外输入下无条件要求产生可提交文件。

这些是两个固定案例的分析结论。未重跑旧 prompt、未做重复采样或任务执行，不能据此宣称 v5 的稳定因果效果、跨任务收益或测试成功率改善。
