# 已中断实验的连续时间线无损去重审计

结论：在已保存的真实轨迹和模型请求上，没有发现去重丢失信息、请求还原失败或改变证据边界。完整运行轨迹的去重减少约40%的输入字符，实施符合此前只做第1步的范围。但它尚未覆盖知识验证中单独引用的尝试，也没有让所有优化模块的输入变小到可以忽略上下文容量。

## 无损性与边界

- 两轮V25共59个Actor实例、97个响应事件、100次已归档实际请求：从初始消息、逐次响应和真实反馈还原的请求，与request.json和messages.json逐条一致。
- 连同SkillAdam对照归档，共89个Actor实例、151个响应事件、159次请求通过同一逐轮核对。
- 对全部12次V25优化器请求，使用该campaign冻结的timeline实现重新投影，结果与实际发送的HTTP请求messages完全相同。
- 对每个模块授权的原始输入，投影后再还原，整个JSON对象完全一致，包括证据ID、原始响应、实际执行代码、运行证据、Actor反馈及评分。累计84次完整运行证据核对、193次单独引用证据核对通过；这些数量包含模块间重复核对。
- 优化器重试附加的上一输出和校验错误没有被删改；Verifier截断后的5份请求输入相同。
- Preconditioner只选12个相关运行，而Grouping/Diagnosis包含15个、Replay包含30个，这是原有模块输入权限/选择逻辑，不是时间线删掉3个任务。
- execution中的日志不等于feedback_to_actor；评分仍位于outcome，未被追加进Actor请求。
- 708个读取源文件的SHA-256在分析前后保持一致。

这里的“无损”是结构和内容能够精确还原，不是声称改变呈现方式后LLM一定产生相同判断。

## 主要剩余输入在哪里

1. Grouping、Diagnosis、Preconditioner、Replay的完整runs中均已移除累计request_messages，实际去重生效。只保留初始消息和逐个事件，响应、执行代码、日志与反馈仍完整保留。
2. Replay包含Parent和Candidate共30个运行，去重后仍有326,707输入Token。其完整运行字段约包括：初始消息242,487字符、响应201,609字符、执行代码168,200字符、执行记录203,519字符、反馈36,359字符。这些是按约定保留的内容，不是遗漏删除的累计request_messages。
3. Verifier包含37条单独引用的尝试和1条diff；Repair包含8条单独引用的尝试和1条diff。由于未提供完整运行上下文，timeline有意保留其request_messages，没有强行删除、补入未授权证据或改用摘要。这符合现有证据权限边界。
4. Verifier仅保留的请求历史就有416,989字符，约占其消息正文的48.68%；Repair为62,838字符、31.26%。这些是字段占比，不能直接当作可全部节省的比例，因为必要上下文仍须至少保留一次。

## 重试与中断的解释

Verifier前4次finish_reason=length，每次completion_tokens=32,768且reasoning_tokens=32,768；第5次正常完成。这是已记录的输出上限问题，不能直接说成输入超过上下文，更不能证明无损去重有错。是否减少输入会改善思考时间和截断概率，需要另行验证，当前归档不能给出因果结论。

Preconditioner首轮失败是把INPUT_PATH写成了不被允许的引用，第二次通过。归档中不存在请求还原错误；这类输出格式/引用校验失败不能直接归因为时间线丢失证据。

把12次实际优化器请求（含重试）全部计入，反事实未去重输入共9,660,502字符，实际共7,670,583字符，减少20.60%。累计报告输入Token为2,434,481，其中Verifier的5次请求占1,375,765（56.51%）。这包括缓存命中Token，不等于账单费用。

## 建议

- 保留当前第1步实现；它是经真实归档验证的无损去重，不需要因这两轮中断撤回。
- 把先前“第一步能压掉大部分输入”修正为“这批完整运行模块减少约40%字符，全流程含重试减少20.6%字符”；不能宣称上下文问题已经全部解决。
- 如果下一步要改善输入规模，先关注Verifier/Repair单独引用证据中的重复历史。应先设计保持引用范围不变的共享上下文表达并离线测量，不能直接删除request_messages或补入完整未授权运行。此项是后续建议，本次未实施，也不要求马上做第2步公共内容共享或第3步响应与代码去重。
- 当前两组训练不改配置、不换Prompt、不改冻结源码；本次只生成此独立报告和可复核JSON。
