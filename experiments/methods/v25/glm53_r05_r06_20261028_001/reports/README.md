## 两阶段边界

第一阶段 `independent/`：Grouping、Diagnosis、Preconditioner、Editor、Replay、Verifier，以及原 R05 已有的 Repair 分别重放。R06 原归档没有 Repair，独立对照不人为制造 Repair 输入。Replay 使用原 Skill diff 和原 Parent/Candidate 轨迹。

第二阶段 `chain/`：分别复用原 R05、R06 Parent、Parent 执行和历史 Memory，接入第一阶段的 GLM Grouping，生成新 Diagnosis / Preconditioner / Editor，并用原 DeepSeek Actor 执行新 Candidate 的 15 道当轮任务，然后以新实际轨迹运行 Replay 与知识审核。R06 不接入新 R05 的 Skill 或 Memory，因此是两个独立局部链路，不是连续重训。输入、全部请求和参数恰好相同时可复用第一阶段有效响应，记录 `reused_response.json`，不重复抽样。

### 局部链路的传输超时调整

原 `chain/R06` 的 Diagnosis 连续 3 次 300 秒 ReadTimeout，没有有效输出。在停止原进程时第 4 次请求已发出，其响应未知，仍占用一次预算。原目录完整保留，续跑放到 **`chain_long_timeout/`**，只将方法模块的 HTTP 读取等待延长至 900 秒，原 4 个槽位继承，R06 Diagnosis 仅剩第 5、6 次请求；没有重置请求预算。R05 局部链路从第一次调用就使用相同的 900 秒设置。

两条链路的模型、high 推理、token 上限、输入、prompt、校验器不因这项调整而改变；Actor 仍使用原 DeepSeek 和原 300 秒请求超时。独立模块对照全部保留原 300 秒设置，不能把局部链路耗时当成同一超时条件下的模型对照。

续跑初次启动被原生读取器的配置一致性检查在发请求前拦截，见 `chain_long_timeout/R06/offline_resume_config_error.json`；为继承的中断槽位显式记录传输中断后正常续跑，没有增加模型调用。具体记录见 `chain_long_timeout/continuation.json`，实际调用参数见各 attempt 的 `request.json`。

Candidate 的 Actor、执行协议及 Docker Python/依赖保持原值。原 Parent 轨迹复用，未重新采样 Parent，结果不能排除 Actor 单次生成波动。不运行完整训练、280 题测试，不修改 Gate。

**局部 Candidate 的对照另有版本限制：原 Candidate 来自旧 Diagnosis v4，本次来自当前 v5 + GLM 新链路；此前 DeepSeek v5 只重跑过 Diagnosis，没有对应的完整 Candidate。** 因此新旧 Candidate 成绩是跨版本的实际表现对照，不能解释成只更换模型的因果效应。第一阶段的 Diagnosis 才是 v5 对 v5 的固定基础输入比较，其他模块也各自控制其输入和 prompt。

## 已核对的独立模块发现

### R05 Diagnosis

见 `independent/R05/diagnosis/attempts/002/diagnosis.json`。第一次调用读取超时，第二次产生有效输出；没有语义重采样。

- 与 DeepSeek v5 一样仍提出金额分支修复，改为 1e-6 级别容差、读取缓存值，用其他任务出现的浮点偏差支持当前假设。此前输入核查显示 P1 的两个错误行先被文本全等筛掉，金额容差调整本身不改变这一点。不能把其他任务的浮点值特征直接当成当前错误路径的根因。
- 查找更新较好：按照用户要求的 TRIM 语义保留单个内部空格，维持首个匹配，限制未要求的字符删除；没有 DeepSeek v5 的“保留首个匹配但跳过首个空值”冲突。
- 数值边界方向保留，但新增“找不到约束时保持每个受影响单元格当前值”的回退，会使要求的余额调整无法完成；缺少约束事实时不应凭空选择这种输出语义。
- Checks 提到了文本筛选的竞争解释，但 Update 没有修复该路径；合理假设可提出，不等于所有附带数据处理规则都有依据。

### R05 Preconditioner

见 `independent/R05/preconditioner/attempts/001/parsed.json`，审核的是原 Diagnosis v4 的三项更新，不能当成对本次 GLM Diagnosis 的审核。

- 新增把弯引号/撇号折叠为普通字符，理由是便宜地覆盖另一种可能情况；没有当前错误确由该字符变化导致的证据。这仍是审核阶段扩写行为的具体例子。
- 无约束值时新增“把所需金额分散到后续合格单元格”的回退，并自称未经验证；这不是由现有证据确定的分配语义。
- 公式更新明确允许：即使题目要求保留公式，缓存修复失败后仍可将该单元格改成直接值。它与同一更新中的保留公式要求冲突，也弱化了任务要求。旧 DeepSeek Preconditioner 没有放开这一替代。
- 对明确要求的非匹配行输出给予优先级是有任务依据的澄清，不能因其他扩写有问题而把所有调整一起否定。

## 局部新链路的过程观察

R05 第一次局部 Diagnosis 达到原 32,768 输出 token 上限，API 报告 32,768 全部为推理 tokens，visible content 为空、finish_reason=length。该次没有可评价的诊断正文，归为预算截断，按原预算重试，不增加 token 上限。

### R06 新 Grouping → Diagnosis

长超时续跑的 Diagnosis 在继承预算的第 5 槽位完成，单次约 383 秒，23,757 输出 tokens（含 21,529 推理 tokens）。这个耗时与此前 300 秒读取超时一起支持延长等待的必要性，但 HTTP 读取超时不等于完整请求的绝对时限，且不同请求的服务端耗时可能不同，不能证明前三次只要延长就一定完成。此前读取超时不能当作模型语义失败。

与固定原 Grouping 输入的独立 Diagnosis 相比，本次输出有以下变化：

- 现在明确提出 issued date 相同时按 line number 分配，补上了独立输出遗漏的合理排序修复。
- 合并方向变为读取黄色高亮选择来源列，将跳过来源的问题留为无法确定。它与新 Grouping 对映射/枚举的表述一致，提示可能存在上游归因传播；但两次 Diagnosis 也属于不同随机生成，不能仅据此证明 Grouping 导致该变化。
- 锚点更新新增从源列输出所有 distinct values，而题目列举的输出项只有特定三项；保持已有内容仍被写成块外空白。这是需审查的额外行为。
- 工作流更新明确要求以探查为目的的程序也保存可打开工作簿，存在将未完成变换的探查副本作为最终提交的风险。
- u3 同时改变完整键和排序，但 Check 仍试图从同一联合修改结果区分二者的作用，证据辨别力不足。

这些是候选更新的文本风险和机制假设，不是已执行后的结果。下游能否纠正、Actor 是否采用及是否影响任务，需以实际链路记录为准。

### R05 新链路 Preconditioner

审核保留文本更新 u1，仍以其他成功任务的去标点行为和“没有观察到过匹配”支持当前任务的归一化；这不能解决 E10/E11 先被整串相等过滤的事实。对 u3，它将触发条件从可见空白差异扩大到所有文本键，并把去撇号、句点纳入主归一化，保留二级标识符和更激进的未匹配回退；这属于审核阶段继续扩写，而不是仅收紧 Diagnosis。对 u4，它补上题目指定的有界遍历，修复“找到 bounds 却没有说明如何使用”的缺口，但保留了找不到约束时从数据推导非负边界的无充分依据回退。不能将这次审核一概评价为无效，也不能因其中有正确补充就忽略新增默认规则。

### R06 新链路 Preconditioner 与首个可核查退步

Preconditioner 保留锚点、样式选列及每次保存的更新；将分配更新改为根据题文及示例决定后缀是否共享库存，并明确禁止把 requested delivery date 插在题目给定的行号优先级之前。排序修复有依据；后缀解释受到题文和示例不一致的限制，不能仅凭 Parent 部分正确认定某种池化必然正确。

`train:370-43` 的 Parent 与原 Candidate 均为 69/70 格，新 Candidate 为 29/70 格，hard 均为 0。新程序只有工作簿探查、打印和 `wb.save(OUTPUT_PATH)`，没有任何插行操作；首个程序即正常结束并提交。与之对应，新 u4 明确要求“以发现结构为目的的程序也保存可打开文件”，Preconditioner KEEP，Editor 原样实现，而 Actor 协议明确第一次正常生成可打开文件即最终提交。由此形成了**错误更新→审核保留→Skill 中的危险要求→实际仅探查后提交→部分分数下降**的具体证据链。

这比单纯文本风险更强，但尚未做单条消融，不能证明 u4 是唯一原因：Actor 同时违反了固定协议及同一 Skill 中“探查和变换在同一程序完成”的要求，也存在单次生成波动。该例说明需要同时核对新增规则与固定执行协议、Skill 其他条款之间的冲突；不能仅用 hard 0→0 将其视为没有退步。证据见 `case_audit/R06/train_370-43/`。

`val:9569` 出现相同机制的 hard 退步：Parent、原 Candidate 均为 1280/1280，新 Candidate 为 1/1280。第一段程序只探查、未保存，收到缺少输出文件的运行反馈；第二段仍只探查，但补上保存，正常终止并提交，没有生成 AO 的结果。运行反馈要求修复文件错误，并没有要求忽略原任务；新 Skill 对探查也保存的授权与这一修复方向相吻合。两道观察到的失败增强了机制假设，但仍不能代替单条消融。

`val:2768` 则从 Parent、原 Candidate 的 15/17 提升到 17/17。新程序按 issued date、line number 排序，不再加入 requested delivery date；同时采用订单前缀库存池及代码/名称关联，所以这不是仅改变排序的受控实验。结合旧错误仅在 1006-B 两行、原 Parent 已使用前缀池却仍错两格的证据，排序修复是有具体机制支持的主要解释。新程序仍写直接值，没有履行题目要求的公式，故值评分通过不等于全部任务要求满足。

### R05 新 Candidate 的已定位问题

- `train:379-36` 仍为 14/16，错误仍是 E10/E11。新程序使用 `normalize_text(payee_cell.value) == target_text`，去空白和标点并未让含后缀的文本匹配。原 Candidate 的 16/16 改善没有复现。这支持“修复未作用于真正的前置条件”，不支持靠扩大归一化或数值容差解决它。
- `train:433-47` 为 124/189，低于 Parent 135/189 和原 Candidate 189/189。新程序确实找到并读取第 20、21 行的 min/max，不能再将本次失败记成未找到边界。它把正 residual 当作减量、负 residual 当作加量，与原满分 Candidate 的符号映射相反；主要新增错误方向在这里。Skill 只说按题目给出的方向遍历，没有明确要求该反向映射，故不能直接认定是 Skill 指使的错误。
- `train:58109` 从 Parent、原 Candidate 的 1/1 降至 0/1。新程序写了公式并试图注入缓存，但正则只移除 `<v>...</v>`，未清除实际已有的 `<v />`。输出 I6 XML 为 `<f>...</f><v /><v>5517</v>`，`data_only=True` 实读为 None。新 Skill 没新增公式缓存规则，Actor 固定协议本身已解释缓存要求；这属于 Actor 的实现缺陷，不能把它算成新文本/边界规则直接造成的退步。新程序也没有重新读取来确认缓存。

- `train:55427` 从 Parent 1456/1460、原 Candidate 1460/1460 变为 1442/1460。18 个错误中，15 格在 Parent 和原 Candidate 都正确输出 `#N/A`，新程序的邮编主匹配、去空格匹配都找不到键，随后执行新增学校名称二级匹配而写入数值；另 3 格 B912/B1082/B1193 延续 Parent 去掉内部空格后的过匹配，原 Candidate 已将它们正确保留为 `#N/A`。新结果修好 Parent 的空查询 B160，却引入 15 个新错误，净多 14 个错格。这里有**Diagnosis 新增二级键回退→Preconditioner 保留并扩展触发范围→Editor 写入 Skill→Actor 按该回退实际匹配→原正确 NA 变错值**的明确路径。对于“规则被采用且在哪些格子造成错误”，代码分支和单元格证据很强；对于“移除该规则重新生成是否必然恢复”，仍需另做消融，本次未做。详情保存在 `case_audit/R05/train_55427/lookup_mismatch_details.json`。

证据见 `case_audit/R05/`，上述判断来自实际程序与输出文件，不依赖标准答案泄露给方法模块。

### R06 新链路 Replay

本次 Replay 比固定旧轨迹的独立输出更准确：正确记录 11→13、3 个 hard 改善、1 个 hard 退步及插行题 hard 不变但单元格退步；明确识别两次“探查后保存即最终提交”，并指出库存改善主要对应排序而非后缀池化。合并题也没有沿用“Parent 没有追加”的错误，而是指出已有列映射与黄色选列得到相同的 11 列，实际差异在是否跳过已有来源。它没有因为 style-reading 更新被执行、结果变好，就将收益直接记到样式读取上，这是有价值的归因改进。

仍需保留两项边界：其“always-save mandate produced ... / accounts for”措辞强于单次联合更新能确定的因果强度，应该区分已经证实的程序终止机制与规则对生成行为的因果影响；它也没有指出库存分配虽值评分通过，却仍没有提交题目要求的公式。公式能力汇总不应把 Actor 自选的直接值回退自动视作已有 Skill 授权。随后 Verifier 将 7 条全部判为 SUPPORTED，没有触发 Repair，也没有收紧上述因果措辞。R06 局部链路已完成，未发布到原 Campaign。

### R05 新链路 Replay

Replay 正确记录 12→11、一项 hard 退步以及边界题和查找题的单元格退步，指出归一化已经采用却没有修好 E10/E11，识别出 15 个原正确 `#N/A` 被回退改写的错误，也将公式缓存失败与当前文本/边界更新分开。这些是比“采用了规则、总分变化”更有用的回放信息。

仍存在具体失真：它称“fallbacks fixed B160”，而实读 B160 的最终值仍为 `#N/A`。Parent 因空邮编且原 B 非公式而跳过该行；新程序在最终未匹配分支按该行其他列有内容写 `#N/A`，并非二级键回退成功找到了值。应记为 Candidate 修好了该格，不能将功劳记到回退解析。其约束扫描描述还加入了 limit/cap 标签，而实际代码只判断 min/minimum/max/maximum，提示仍有把 Skill 要求照抄为程序实际行为的问题。

对 E10/E11 内容、真实 min/max 行、输出 XML 等未包含在方法模块输入中的事实，Replay 保留 unresolved 是合理边界；本报告能进一步定位是因为额外读取了原始输入与最终输出，不能要求它凭不可见事实得出同样结论，也不应将这些离线发现悄悄加入本次调用。

R05 Verifier 将全部 6 条知识判为 SUPPORTED，未触发 Repair；B160 修复机制的误述及约束标签的实现描述均未被指出。两条新链路均完成知识审核。

## 基于独立对照的优化方向（建议，未实施）

| 模块/边界 | 本次直接证据 | 优先处理 |
|---|---|---|
| Diagnosis 的证据输入 | R05 两个模型都没对准 E10/E11 的文本前置筛选；关键行值不在前 5 行预览中 | 为错格涉及的输入行和依赖列提供有界原始证据，不能提供标准答案；区分缺证据与已有证据被误读 |
| Diagnosis 的修复选择 | R06 的题文给出先第一行后余额，而代码先按 requested date 排序；独立输出仍遗漏 | 保留有直接线索的竞争假设，检查修改是否能作用于错误路径；避免把推测中的数据类型扩写成通用清洗/回退规则 |
| Preconditioner | GLM R05 新增去标点、无边界分配、必需公式失败后改值；R06 全 KEEP 又漏掉原 DeepSeek 处理的保留边界 | 审核时逐项对照任务不可改变的要求和新增行为依据；允许修复假设，不允许以“尽力交付”覆盖公式、顺序、匹配等明确语义 |
| Replay | R06 再次误记“没有追加”；R05 把 Actor 自选的直接值回退说成 Skill 条款 | 分开 Skill 实际要求、程序采用的行为、能观察到的结果和因果推断；可计算的成功数与任务身份应优先来自程序汇总 |
| Verifier / Repair | GLM 漏检原未匹配填充值错误，但收到原冲突后 Repair 能修复 | 优先提高定位和证据核对，不能因 Repair 有能力就认为审核闭环有效；也不能把 SUPPORTED 理解为所有语义结论被证实 |
| Grouping | 新分组有助于呈现排序竞争解释，也在合并任务中提前收窄归因 | 分组应整理共享行为与差异，保留未确定解释，避免在上游将猜测写成已定位的缺陷 |
| Editor | 两轮均主要忠实落实输入，首次 patch framing LF 错误均由原校验修复 | 暂无证据优先重写其语义职责；保留机械校验和有界纠错，不让 Editor 自行重新诊断 |

本次仍不支持按 Update 数量设硬上限：独立 Diagnosis 两轮都为 3 条，却同时存在好方向与错误扩张；R06 新链路增加到 4 条时既补上排序假设，也引入其他扩张。应逐条限制不必要行为、核对相互冲突和依赖，而不是把数量变少当作改进。

局部执行进一步支持这一判断：R05 的具体新增错误集中在一个 Update 中的二级键回退，R06 的两项明显退步对应单个工作流 Update 的提前提交风险；与此同时独立的排序更新有实际收益。这没有证明“多条 Update 本身造成退步”，但联合更新会降低总分和单条作用之间的可辨认性。无需限制每轮数量，应该能沿着每个 Update 追踪其行为变化、采用证据、任务要求及正负结果。

如果据此安排后续工作，建议先处理两类已经有具体失败路径的问题：一是审核新增规则对原任务语义及固定执行协议的影响（如二级键替代、探查即保存），二是让回放区分程序层面的已证实机制和 Skill 改动对生成行为的因果假设。错格相关输入的有界证据补充可作为单独实验方向；不需要先增加更多通用 prompt 条款，也不应把每个 Actor 实现错误都转成永久规则。以上均为建议，本次未修改模块。

不能将这些现象全部归为模型能力不足，也不能据两轮就证明 prompt 或架构的普遍缺陷。事实误读、输入缺口、任务要求让位于值评分、程序行为与 Skill 授权混淆是不同问题，应分别验证。暂不继续改 prompt，不据此替换正式模型或启动完整训练。

## 复现与证据
