## 1. 问题、实现与固定条件

**Question：** 保持完整认真初稿与当前 Parent 证据不变，有效作用认识能否进入具体更新决定，改变实际要求并由 Editor 落实？

新增 `effective_memory`、`effective_reconciliation`、`effective_update`、`consume_fixed_plan`。Memory 只新增必要的限制退役操作及其上下文；Fusion／Editor 沿用原紧凑输出形状，没有新增逐维自证表或独立 Review Agent。完整学习与仅修订已有认识是两个显式 profile，旧消息可按原方式重建。新机制在独立入口验证，尚未替换 `compact_cycle` 的默认 profile。

## 4. 固定初稿的实际消费结果

两次 Fusion 均形成合法结果。无历史分支保持初稿，历史分支实际将 u5 替换为 u6，并以新 m1 为依据；u1–u4 和 intent 字面不变，w1 替换为 w3，w2 保留。

| 对象 | 无历史 `current` | 有效 Memory `history` |
|---|---|---|
| Fusion 决定 | 恒等，`changes=[]` | 非恒等，`u5 → u6`，basis 明确引用新 m1 |
| 对初稿的解释 | u5 只在任务命名目的地时要求 move；照明没有明确放置目的地，w1 已保留歧义 | 将原 u5 解读为对所有任务过强的最终放置要求，利用持物 use 成功路径作条件化修订 |
| 实际新要求 | 无变更 | put／place／deliver 任务保留 move；look-at-under-fixture 任务增加取物／use 分支，允许持物 use 或先放到灯旁后 use，并写成不强制额外 take |
| Editor 原始文本 | 写出原五项要求 | 确实写入有效 u6 的任务条件分支及“不要求额外 take”措辞 |
| 原运行校验 | 因重复继承 w1／w2 被拒 | 因重复继承 w2／w3 被拒 |

两份 Editor 的 `watch` 都与输入 Plan 中继承问题的完整数组逐值相等，但原增量接口要求它们不被重新输出。原报告因此保留 **`comparison_incomplete`**，两个分支都是处理错误，没有在原目录发布 Candidate。没有重新调用 Editor 或删除原始响应中的重复项以回填成功。两次合法 Fusion 及要求版本仍原样保存，不能因为 Editor 失败抹掉已观察到的变换，也不能把该失败描述为更新策略没有效果。

本次已经观察到“有效认识 → 具体要求变化 → 原始 Editor 文本中的对应变化”，但有三项实质限制：

1. **变换还不够准确。** u6 同时允许持物 use 与先放到灯旁再 use，却统一写成不要求额外 take。原 Parent 及旧 7 步 Candidate 已显示后一条路径在 use 时未完成、随后 take 才完成。“不要求”并不是禁止 take，不能断言必然回归；但仍缺少按实际完成状态、持物／放置状态继续完成目标的清楚分支。w3 只询问未来是否有任务需要 take，也未充分表达这一已有状态差异。不能宣称变换完整正确。
2. **初稿解释也影响差异。** 无历史分支对 u5 作窄读，历史分支作宽读。原 Parent 已提示照明不同于普通交付，Memory 新增的是持物 use 直接完成的具体路径。不能把两侧全部差异归因于 Memory 独有作用。intent 字面不变，也不能证明其 deliver 表述与新条件分支语义完全一致。
3. **单次构造不等于效果。** 这次没有执行任何新文本，没有验证消除多余动作、保留旧成功行为或提升成功率。m2 纠错没有被用来机械加强动作过滤，m3 也没有被用来宣称清洁改善；这只是本次输出中的边界保留。
