# Diagnosis 阶段门与只读语义核查

Diagnosis 首次请求 HTTP 401，无模型输出；用户明确授权后，在同一 logical_call_id 下保留第 1 次失败并发送第 2 次同正文请求，得到合法 revise。五次总传输尝试预算没有重置。不存在两份有效 Diagnosis 择优。

u1 有三条独立要求：扩大搜索类别、首次到达检查及未查位置优先、首次覆盖的停止条件；u2 有三条独立要求：禁止已确认无目标的重复检查、第二轮前先查剩余类别/实例、循环时切到表面/电器。触发与动作在对应行内，两个真实多行 Update 均可由 A/B 消费，未手工拆分。

Goal 同时承诺完整非重复搜索和预算内找到目标，并写入扩大类别的策略方向，存在较强实现绑定；不修改 Goal，也不据此要求预定正确策略。它没有破坏两组共享输入的工程契约，因此不作为停点。

下列是研究者对共同输入的风险核查，不是模型已承认的原因，也不放入 Preconditioner 请求：

- Diagnosis reason 把 P3/P6 描述为从未扩展到未试的表面/电器类别，表述过强。P3:10 到 countertop 1、P3:11 examine coffeemachine 1；P6:15/16 到 sidetable 1/2，P6:21 到 dresser 1。实际缺口是覆盖不足且反复循环，不能说完全没有类别扩展。
- “empty”需区分字面空与没有目标：P3 cabinet 1 含 dishsponge，cabinet 3 含 peppershaker；P1 drawer 1 含 creditcard。重复返回不一定是空容器，但执行反馈没有目标。
- u1 “open it”套在所有 candidate receptacle 上时，可能给开放表面增加不必要开门前提。
- u1 的全体 reachable 候选/多目标数与 u2 的全局未见状态，不能由最近两对历史自动准确恢复。
- u2 同时要求不在最近历史与从未见内容；前者不推出后者。第二轮前完成剩余类别或实例，是需审查范围的强前提。
- c1 的“转向其他类别，而不是继续更多同类容器”可能与保持同类实例覆盖产生张力；历史 M6 具有相关混合响应，但不能预先指定唯一正确调度。

以上风险原样保留。按正式 V23 的引用规则，Original 实际选入 P1/P3/P6 的完整当前执行；P2/P4/P5 未独立引用为 Update basis，因此不会额外给某一组补入其轨迹。成功能力仍出现在共同 Goal/Checks 中，两组获得完全相同的 user content，历史 Memory 仍为冻结 v3 快照。
