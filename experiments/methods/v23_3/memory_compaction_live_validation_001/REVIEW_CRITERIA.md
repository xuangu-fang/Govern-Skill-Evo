# 生产生成的人工检查准则

这些检查在第三次请求之前确定。程序探针的固定答案与评分仍以 config 中预冻结内容为准；人工检查不用于修补探针答案或改变通过阈值。

1. **技术可用性**：HTTP 正常、finish=stop、最终 content 非空、JSON 可解析；Patch 不修补即可按 Original 应用，原编译器接受。若 Keep/停点，明确没有非空 Patch 应用证据。
2. **新视图的使用**：检查实际输出中的历史 source/step 引用在输入中存在。若依据涉及具体观察或候选菜单，检查是否位于完整窗口或明确提供的初始/窗口边界状态；仅动作序列或反馈可以支持的判断单独区分。
3. **缺失边界**：不得将窗口外状态填补为邻近状态，不得将菜单/观察缺失解释为动作/目标不存在。不能把完整 action trace 当完整 observation trace。
4. **历史概括与实际事实**：检查是否无条件照搬 knowledge，是否忽略与其相冲突的 actual Diff 或已提供反例。正面、负面或无法区分的响应不得被转写成普遍因果保证。
5. **必要行为与 Goal**：检查修改是否保持精确类别、必要处理/交付及适用的数量/灯具要求；不得用 Update Patch 偷改 Goal。没有 Editor/Actor/Replay，不能判断运行收益。
6. **状态解释**：区分“格式可读取”“非空 Patch 可生成并编译”“所见证据使用没有发现明显越界”和“方法质量已提高”。只能报告实际获得的层次。

通过这些开发案例检查后，最多建议以可选紧凑输入接入后续受控实验。未作同方法全文/紧凑配对，不能宣布信息损失无影响；未作完整 A/B 或行为回放，不能宣布 V23.3 优越或任务成功率改善。
