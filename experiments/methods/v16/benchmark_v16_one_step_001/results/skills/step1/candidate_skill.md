# Operational Skill

## Planning and navigation

- For airline requests, when evaluating a flight change that keeps an existing segment, derive the kept segment's price from the existing reservation or observed settlement context, not from search_direct_flight's current market fare unless the observed contract requires that repricing. Use the current available fare for changed segments, compute the full itinerary total against the original total paid, and obtain explicit confirmation before calling update_reservation_flights.
- For airline requests, when a user chooses a one-segment replacement based on an absolute total itinerary price-difference limit, price all segments in each candidate itinerary, including kept segments, using current or settlement-relevant fares rather than relying only on the old reservation line price for the kept segment. Compute the absolute difference from the original total and apply the user's preference order, then obtain explicit confirmation before updating.
- For airline requests, screen candidate flight changes against reservation invariants before applying user price preferences. Keep only replacement segments that preserve the reservation's origin, destination, and trip type. Then compute the complete itinerary price difference and apply the user's conditional preference among eligible options; obtain explicit confirmation before calling update_reservation_flights.
- For airline requests with multiple separate bookings and limited payment methods such as a travel certificate and a gift card, plan a non-overlapping allocation across every requested reservation before the first book_reservation call. Use a travel certificate for only the reservation it must cover or for one booking only, use other available payment methods for the remaining fares, and confirm the full allocation with the user. Do not reuse a certificate after it has been consumed or removed.

## Execution patterns

- For airline requests, do not issue a second tool call until the result of the previous tool call has returned. When multiple lookups such as user profile retrieval and flight search are needed, call each tool sequentially, wait for the result, and then continue.
- For retail requests, when one authenticated request changes both a pending-order shipping address and the default profile address under an address-synchronization contract, choose the write order that preserves the user-confirmed distinct addresses. When the observed contract indicates that later profile writes can propagate to the pending order, write the default profile address first and the pending-order shipping address last, and do not write either target more than once.
- For retail requests, when a user asks to change both a pending-order shipping address and their default profile address, authenticate the user, retrieve user and order details, call get_address_propagation_context before any address write, restate and obtain explicit confirmation for both distinct address changes, then call modify_pending_order_address and modify_user_address exactly once each, verify the returned addresses, and summarize the result without additional writes.

## Form entry and verification

- For airline requests, when a user gives a cost-conditional flight replacement preference such as 'use the primary candidate if the complete revised itinerary adds no more than the stated limit, otherwise use the fallback,' treat it as an ordered branch: select the primary candidate when the condition is met, otherwise select the fallback. Do not apply the inverse threshold to the fallback unless the user explicitly states a separate condition. If the wording is ambiguous, restate the intended branch rule and get user confirmation before concluding either option is ineligible.
- For airline requests, classify checked-bag fees using the cabin-specific free allowance before booking or updating baggage. For an observed business-class itinerary with two checked bags, keep the requested total_baggages, set nonfree_baggages to zero, and exclude baggage fees from the payment amount; obtain explicit confirmation before finalizing.
- For airline requests, before calling book_reservation, collect missing required fields such as user ID, trip type, passenger first and last name, and date of birth; verify the user profile, saved payment method, and flight availability with the appropriate tools; compute the total from the verified fare and any confirmed applicable fees; present a complete itemized summary; and proceed only after explicit user confirmation. Do not book if required details remain missing or ambiguous.
- For airline requests with multi-passenger labels such as a single initial and a traveler token, normalize each passenger into first_name and last_name fields. Treat the trailing traveler token as the last name and the initial as the first name unless the user gives an unambiguous, conflicting explicit first/last pair. If the explicit last-name phrase conflicts with the label, ask a targeted confirmation and do not call book_reservation until the first and last names are confirmed.

## Error recovery and stopping

- For airline requests, before calling cancel_reservation, verify all visible cancellation conditions: booking within 24 hours, airline-cancelled flight, business cabin, or confirmed insurance coverage for the stated reason. Travel insurance alone is not sufficient. If insurance is the only possible path and coverage for the stated reason cannot be confirmed from visible policy or tools, do not claim eligibility or cancel; if the user requests review or an exception, transfer to a human agent.
- For airline requests, when get_settlement_context does not return a usable settlement baseline or repricing formula, do not treat search_direct_flight fares or prior reservation line prices as a final settlement total. Present prices as estimates, avoid committing a preferred option solely on those prices when the user has a hard price-increase cap, and if the cap cannot be verified safely, stop and transfer rather than calling update_reservation_flights. After any update, verify the settled amount before reporting success.
- For retail requests involving a delivered order where the user's exchange request is conditional on purchase protection remaining active, call get_resolution_context before choosing exchange or return. Do not call exchange_delivered_order_items when protection preservation cannot be confirmed, including when the context shows only active protection without a continuation guarantee. State that the condition cannot be confirmed, apply the user's stated fallback return with explicit confirmation, and then call return_delivered_order_items; transfer if the request is outside available scope.
