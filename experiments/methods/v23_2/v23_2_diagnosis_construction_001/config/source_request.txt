# V23.2 P1-B：Diagnosis 策略构造规则的设计、最小实现与受控验证

## 一、任务目标

当前 V23.2 已完成：

- P0：冻结 R04、R05、R06 的输入、输出及评价标准。
- P1：尝试修正 Diagnosis 的 Goal—Update 边界，但语义验收未通过。
- P1-A：对21项关键策略承诺进行离线证据追溯，确认主要问题发生在从执行事实构造具体策略要求的过程中。

P1-A 的核心结论是：

**Diagnosis 没有稳定保留原始证据的必要性、条件、对象粒度与行为边界，因此可能把成功时伴随的动作、局部观察或合理探索方向，扩大成缺乏充分支持的强制要求。**

本次开展 P1-B，针对已经确认的两个问题进行最小修正：

1. **必要性判断**：区分任务必要操作、条件必要操作、探索性策略，以及成功轨迹中仅仅伴随出现的动作。
2. **边界保持**：从具体轨迹抽象策略时，不无依据地改变触发条件、覆盖单位、完成条件，或排除已有必要行为。

最终目标是使 Diagnosis 仍能提出具体、可执行的新策略，同时减少无依据的强制流程和附带限制。

本次按以下顺序一次性执行：

**规则设计 → 最小实现 → 离线检查 → 三例固定输入验证 → 新旧对照报告。**

不要重新开始多版本 Prompt 搜索。

## 三、第一阶段：设计简洁的策略构造规则

先生成 `P1B_DESIGN.md`。

文档应简洁，重点说明下面两条规则怎样进入 Diagnosis 的现有策略构造过程。

### 规则一：必要性判断

在把执行轨迹中的行为写成 Skill 要求之前，判断该行为的必要性来自哪里。

至少区分：

**A. 任务必要行为**

任务本身要求完成的行为，例如对精确目标完成必要处理并交付。

这种要求可以明确保留。

**B. 条件必要行为**

某项操作只在特定环境状态或执行前提下必要。

必须保留成立条件，不得仅因为成功轨迹执行过，就把该操作推广成无条件前置步骤。

**C. 探索性策略**

为改善当前问题而提出的具体新方法，例如搜索调度、局部换区或近期避循环。

允许提出，且不要求事先通过反事实实验证明最优。

但不应把预期效果当作已验证的必然结果，也不能附加没有独立理由的强制步骤。

**D. 成功伴随动作**

某次成功执行出现过的操作，但当前证据没有证明它必需。

不能仅凭它出现在成功轨迹中，就将其转化为必须保留的操作链。

对于具有明显行为影响的要求，应结合行动前状态、可见动作候选、后续反馈和成功轨迹内部差异，判断其必要性或适用条件。

特别强调：

**可见候选中存在某个替代动作，不等于该替代动作已经通过反事实验证；但它能够限制“没有其他选择”“必须执行完整前置流程”等断言。**

不要要求 Diagnosis 对每个新策略完成独立因果证明。

### 规则二：条件与行为边界保持

Diagnosis 可以将具体轨迹抽象为通用策略，但构造 Update 时，需要保留对策略正确性有影响的条件关系。

重点检查四个方面。

**1. 触发条件**

实际问题是在什么状态下发生的？

例如，“刚检查且没有目标的位置被无效回访”，不能直接扩大成“任何已经检查的位置都不得回访”。

**2. 对象及覆盖单位**

证据针对的是具体位置、容器、类别，还是整个任务？

例如：

- 检查一个位置；
- 检查某类的部分位置；
- 检查该类所有合理位置；
- 检查全部合理候选位置。

这些不应无依据地被视为等价。

**3. 完成条件**

策略改变了搜索方式，不意味着可以同时改变任务完成标准。

搜索策略中的停止、继续、切换与后续交付条件必须一致。

尤其不能把“某些类别已被采样”直接当成“所有合理位置已经覆盖”，也不能在尚未找到目标时无条件进入使用目标的步骤。

**4. 必要行为保留**

新策略不能无依据地排除已有有效行为。

重点考虑：

- 精确目标识别；
- 必要处理与交付；
- 多实例任务的数量要求；
- 有条件的有效回源；
- 搜索与后续处理之间的执行预算关系；
- Actor 实际能够观察和使用的信息。

注意：Update 是相对 Parent 的增量修改。某项原有规则没有在新 Update 中重述，不自动意味着它已被删除。必须区分继承、覆盖、撤回和存在歧义的关系。

### 两条规则怎样使用

不要把这些规则写成新的分类系统、状态机或独立审核阶段。

建议在现有 Diagnosis 的一次生成过程中：

1. 根据当前证据识别行为问题，形成 Goal。
2. 构造具体策略候选。
3. 对候选中具有明显约束作用的要求，检查必要性、适用条件、覆盖单位与必要行为保留。
4. 修正越界要求，保留有动机且可执行的探索策略。
5. 按原 Schema 输出 Goal、Updates、basis、Checks 等现有字段。

这是**同一次 Diagnosis 内部的策略构造过程**，不得增加额外模型调用。

设计文档需说明哪些判断利用已有字段表达，不新增字段。

## 四、第二阶段：一次最小实现

以 P1 已有的独立 Diagnosis Prompt 为基础，结合 P1-A 的结论进行一次最小修改。

不要回退 R05/R06 已经取得的 Goal—Update 解绑改善。

本次主要调整策略生成与策略约束的相关说明，而不是重新设计整个 Prompt。

具体要求：

1. Goal 继续表达行为改善目标、必要任务条件和有效行为保留要求。
2. Updates 继续提出具体、可执行的新策略。
3. 在生成强制操作链时，考虑前置动作是否确有必要，必要性是否依赖特定状态。
4. 在提出搜索或调度规则时，保持触发条件、覆盖单位和结束条件的一致性。
5. 检查新限制是否意外排除了原有有效行为。
6. 对未知策略效果保持合理的不确定性，但不能将 Actor 指令写成无法执行的模糊建议。
7. 不假设 Actor 拥有完整历史访问表或其他未提供的持久状态。

**不要把 R04/R05/R06 的具体答案写入正式 Prompt。**

例如，不得针对三个案例硬编码：

- 某种固定微波炉流程；
- 某个必须采用的搜索算法；
- 固定切换次数；
- 全局类别顺序；
- 特定回源位置；
- 固定预留步数。

Prompt 应采用通用的策略构造要求。

修改完成后先冻结 Prompt 和运行配置，再进行模型验证。禁止根据本次验证结果继续修改第二版、第三版 Prompt。

### 实现边界

本次不允许：

- 修改正式 V23；
- 修改 Diagnosis 输入输出 Schema；
- 增加 `goal_override`；
- 让 Diagnosis 读取 Memory；
- 修改 Grouping、Memory、Preconditioner、Editor、Actor、Replay 或 Gate；
- 新增独立审核 Agent、证据评分器或复杂结构；
- 改变模型参数和运行预算；
- 修改或覆盖 P0/P1/P1-A 历史归档；
- 修改默认正式运行配置。

只允许在独立 V23.2 实验目录中新增必要 Prompt、配置、实验入口、测试和报告。

如果已有运行入口能够复用，应优先复用，不重复开发。

## 五、第三阶段：离线检查

在调用模型前完成确定性测试。

至少检查：

- 正式 V23 和既有 V23.2 文件不变。
- 新 Prompt 正确加载。
- Diagnosis 输入和输出 Schema 不变。
- 历史 Memory 不进入 Diagnosis。
- 模型配置与 P1 固定验证一致。
- 输出仍可由原有解析器和 Schema 校验器处理。
- 下游接口所需的字段没有被删除。
- 冻结输入未被重新构造或修改。

不要把自然语言策略正确性伪装成简单的关键词检测。

本阶段的必要性判断与边界保持，仍然需要对实际输出进行证据级语义分析。

## 六、第四阶段：三例固定输入受控验证

使用 P0 冻结的 R04、R05、R06 原始 Diagnosis 输入。

每例只执行一次新 Diagnosis。

**最多新增3次逻辑模型调用，不自动重试，不进行语义重采样。**

若出现调用错误、截断或 Schema 校验失败，记录实际结果，不通过修改 Prompt 或额外生成来补救。

将新输出称为 D2，分别与：

- D0：正式 V23 原始 Diagnosis；
- D1：P1 修正后的 Diagnosis；

进行比较。

必须继续使用 P0 的 A—E 评价标准，并额外重点核查本次两个修复目标。

### R04：必要性与有效行为保留

检查：

1. Goal 是否仍将具体微波炉操作链固化为必要目标。
2. Update 是否仍无条件要求插入、关门、重开、取出后才能 heat。
3. 是否根据行动前动作候选与环境状态限定前置操作的必要性。
4. 是否保留精确目标、必要热处理和直接交付。
5. 搜索规则是否不合理地排除访问过但仍有目标的来源。
6. 多实例任务是否仍保留完成所需数量的要求。

不能要求模型必须输出某条固定热处理策略。

不能把直接 heat 的可见性当作反事实成功证明。

验收重点是：**不再把成功伴随动作当作无条件必要流程，同时仍能构造具体的处理策略。**

### R05：覆盖单位与完成条件

检查：

1. 是否仍能提出具体搜索策略。
2. 跨类别探索、编号推进或分段搜索是否仍被允许作为假设。
3. 是否区分具体位置与类别的覆盖。
4. 是否仍将每类采样一次直接写成任务结束条件。
5. 搜索结束与未找到目标的分支是否一致。
6. 是否新增排他性回访限制、固定批次或其他无依据要求。
7. 是否仍依赖 Actor 实际无法确认的全局访问状态。

不要将 breadth-first、跨类别轮换或 `few` 自动判为错误。

验收重点是：**允许策略探索，但不能让探索方式附带改变任务完成条件。**

### R06：已有改善的保留与残余边界

检查：

1. Goal 是否继续不绑定 ordered 或 memory-independent 扫描。
2. 是否继续避免类内穷尽与 guarantee progress 等过强承诺。
3. 是否保留具体且有问题动机的搜索候选。
4. 是否正确区分近期未出现和全局未访问。
5. 是否避免在未满足可见条件时要求全局 uninspected family 判断。
6. 搜索策略是否与必要处理、交付及执行预算保持兼容。
7. 已有温度操作改善是否受到新的策略构造约束影响。

不得预设某种搜索算法为标准答案。

不得要求固定切换尺度，也不能将 `few` 自动理解为已经规定两次或三次。

验收重点是：**保留 P1 已经观察到的合理改善，同时减少缺乏依据的策略范围和信息前提。**

## 七、评价与归因要求

本次必须区分三个层次：

**1. 事实理解是否正确**

有没有准确区分行动前可见动作、实际执行动作、执行后结果及当前执行条件？

**2. 策略构造是否合理**

提出的具体规则是否保持必要性、条件、覆盖粒度与完成边界？

对于有合理动机、但未验证效果的新策略，可以判为允许探索，不能机械要求已经成功证明。

**3. 实际行为效果是否得到证明**

本阶段没有 Candidate Replay，因此不能声称新 Skill 已经提升成功率、减少执行步数或避免实际退化。

尤其不要将 Goal 解绑、Updates 数量变化或某些关键词消失，直接当作整体方法成功。

新旧对照需要同时报告：

- 已纠正的问题；
- 仍然存在的问题；
- 新增的不合理要求；
- 合理的探索假设；
- 当前无法判断的效果。

由于 R04/R05/R06 已经用于机制设计，这三例的改善不能证明新规则具有跨任务泛化能力。后续如需检验稳定性，应另选未参与设计的训练案例，不得使用最终 Test 调参。

## 九、完成标准与停止条件

执行顺序：

1. 阅读 P0、P1、P1-A 的实际材料。
2. 完成 `P1B_DESIGN.md`。
3. 对独立 Diagnosis Prompt 进行一次最小修改。
4. 冻结 Prompt、输入和运行配置。
5. 运行离线确定性测试。
6. 对 R04、R05、R06 各运行一次 Diagnosis。
7. 比较 D0、D1、D2。
8. 完成证据级语义评价和归档。
9. 报告结论并停止。

如果语义验收仍未通过：

- 如实归档失败。
- 不自动进一步修改 Prompt。
- 不新增第二版候选。
- 不以重新生成寻找较好的随机输出。
- 分析失败是否仍属于必要性和边界保持问题，以及现有约束为何未能在输出中落实。
- 明确后续是否有必要研究证据组织方式或其他实现，而不是默认继续强化 Prompt。

如果通过：

- 也只能说明这次固定输入验证达到了预期；
- 不直接等同于稳定泛化或真实 Skill 执行收益；
- 提出后续未参与设计案例及 P2 的验证建议，但本次不执行。

本次禁止调用 Preconditioner、Memory 更新、Editor、Actor、Candidate Replay、Gate，也不运行完整自进化。

最终向我汇报：

1. 设计了哪两条策略构造规则；
2. 实际修改了哪些 Prompt 内容和代码；
3. R04、R05、R06 相对 D0、D1 的具体变化；
4. 哪些错误被修复，哪些仍然存在；
5. 是否出现新的策略过强承诺；
6. 是否保持了具体策略探索能力；
7. 是否达到 P1-B 语义验收标准；
8. 新增调用、Token 成本和历史保护结果；
9. 是否建议进入 P2，以及依据是什么。

**完成 P1-B 后停止，不自动进入 P2 或其他研究阶段。**

## 十、最终研究问题

本次 P1-B 要验证的不是模型能否写出更多关于证据的解释，而是：

> Diagnosis 能否在提出具体 Skill 更新时，根据当前执行证据判断操作的必要性，并在策略抽象过程中保留原始条件、覆盖单位、执行能力和必要行为边界？

特别注意：

**不能为了消除未经验证的承诺，就消除新策略探索；也不能因为某种新策略有合理动机，就接受其中所有附带的强制要求。**

本次需要找到两者之间更可靠的策略构造方式。
