# SuiteCRM Operational Skill

## Planning and navigation

- For airline requests, when a conditional cabin-plus-baggage change is authorized only if the package total is at most a stated limit and the reservation has an existing prior paid amount, compute each candidate package as its new package total minus the already paid reservation amount, and compare that incremental charge to the limit. Select Business if its incremental charge is at most the limit; otherwise select Economy if its incremental charge is at most the limit; otherwise make no mutation. Do not apply passenger, cabin, or baggage writes until the correct branch is selected and the user explicitly confirms the complete proposal.
- For airline requests, when multiple bookings must be paid with a limited set of user-authorized payment methods that includes a travel certificate that becomes unavailable after use, do not allocate the certificate to an earlier booking if it is needed for a later booking. Propose, obtain confirmation for, and execute an allocation that completes all bookings sequentially using only currently available user-authorized payment methods; for example, use a gift card for the earlier lower-cost booking and reserve the certificate for the later booking it must cover. Stop before any booking call with a payment method that is not currently available; if no allocation can complete all bookings within the approved methods, explain the constraint or transfer as appropriate.
- For airline requests, when multiple bookings are paid with a single-use travel certificate and one or more divisible gift cards, allocate the travel certificate to only one booking and prioritize the booking with the highest fare that does not exceed the certificate balance; use the gift card for lower-fare bookings. Confirm the payment plan with the user before executing. If the certificate cannot cover any single booking or remaining gift card balances cannot cover the other bookings, stop and ask for alternative payment methods.
- For airline requests, when a conditional partial flight change keeps one or more segments unchanged, compute the new reservation total using the original reserved price for each kept segment and the candidate current price only for the changed segment. Compare that total to the original reservation total to establish the correct branch and exact payment or refund consequence before selecting a candidate or calling update_reservation_flights; obtain explicit user confirmation before executing the update.
- For airline requests, before requesting confirmation for a cabin-class change whose fare difference must be listed, compute the difference from the original per-passenger fare stored on the reservation and the current per-passenger fare for the new cabin multiplied by passenger count; do not use total payment_history as the baseline. State the exact expected charge in the complete proposal, obtain explicit confirmation, and ensure the confirmed amount matches the subsequent tool result before proceeding.
- For airline requests, before presenting a cancellation as eligible, requesting confirmation, or calling cancel_reservation, verify that at least one full permitted cancellation condition is satisfied: booking within the last 24 hours, airline cancellation, business-class flight, or travel insurance with a covered health or weather reason. Travel insurance alone is not sufficient for a change-of-plan or other non-covered reason. If no condition is met, explain that cancellation is not permitted, stop, and do not call cancel_reservation or state that a refund will be issued.

## Execution patterns

- For retail requests, when a confirmed multi-change request on a single pending order includes modify_pending_order_items together with modify_pending_order_address or modify_pending_order_payment, complete and verify the requested whole-order payment or shipping-address modifications first, then execute modify_pending_order_items last in one collected call; verify the final order state and report all requested changes as completed. Once modify_pending_order_items returns status 'pending (item modified)', make no further modify_pending_order_address or modify_pending_order_payment calls for that order.
- For retail requests, after any balance-changing action in the same conversation, such as a cancellation refund, and before denying a gift-card-funded pending-order payment modification or transferring, re-read current user/payment-method data and recompute the available gift card balance against the order total. If the updated balance is sufficient, explain the modification details, obtain explicit confirmation, and call modify_pending_order_payment. If it is still insufficient, deny that method and offer only permitted alternatives.

## Form entry and verification

- For retail requests, before calling modify_pending_order_items, present the exact items to modify, price consequence, payment method, and unchanged state, and explicitly remind the customer to confirm that all items to be modified have been provided; wait for explicit confirmation before executing the one-time item modification.

## Error recovery and stopping

- For retail requests, when asked about credit-card refund timing after a delivered-order return, state only facts supported by the policy, tool outputs, and user inputs; do not invent or carry over a quantified refund timeline. If the specific credit-card refund timing is not provided, state that it is not available.
- For airline requests, before soliciting cancellation confirmation or calling cancel_reservation, check whether any portion of the reservation has already been flown. If any flight has already been flown, do not rely on cabin class or other cancellation eligibility; inform the user that the cancellation cannot be handled because part of the trip has already been flown, call transfer_to_human_agents, and send the required transfer message. Do not call cancel_reservation.
